# CLAUDE.md 변경 감사

지침 파일은 규칙 목록이 아니라 **서로 맞물린 시스템**이다. 한 규칙의 조건을 바꾸면 그 조건을 참조하는 다른 규칙의 발동 범위가 같이 움직이고, 검증을 한 줄 강화하면 저위험 작업의 비용이 올라가고, 근거를 더 대게 하면 응답이 길어진다. 그래서 "이 변경이 좋은가"만 물으면 대가를 못 본다. 이 스킬은 **무엇을 대가로 지불했는지 강제로 적게** 만든다.

체크리스트가 아니라 매트릭스인 이유가 여기 있다. 체크리스트는 각 항목을 독립적으로 통과시키지만, 실제 결함은 항목 사이에서 샌다.

---

## 0. 전제조건 — 판단의 배경

감사 의견을 쓰기 전에 이 전제를 확인한다. 전제가 다르면 같은 변경도 다르게 평가된다.

| 전제 | 내용 | 판단에 미치는 영향 |
|---|---|---|
| 모델 | Claude Opus 5 — thinking 기본 ON, 응답이 기본적으로 길고, 시키지 않아도 자기 검증하고 위임한다 | "검증하라"·"double-check"류 추가는 개선이 아니라 과잉 유발. 길이 통제는 프롬프트로만 되고 effort로는 안 된다 |
| 하네스 | Claude Code CLI — 자체 시스템 프롬프트가 상당 부분을 이미 커버 | 시스템 프롬프트와 겹치는 규칙은 버전 드리프트 위험을 안는다. 중복 발견 시 지적한다 |
| 주입 | `~/.claude/CLAUDE.md`로 배포되어 전 프로젝트·전 턴 상주 | 추가 한 줄의 비용이 매 턴 발생한다. 규칙 총량 증가는 그 자체로 대가다 |
| 작업 | 코딩 + 문서작업, 솔로 운영 | 팀 협업 규약·리뷰 프로세스는 평가 대상이 아니다 |
| 언어 | 규칙은 영어, 응답은 한국어 | 길이·간결성 판단은 한국어 출력 기준으로 한다 |

전제가 바뀌었다고 판단되면(모델 교체, 하네스 변경) 감사 전에 그 사실을 먼저 보고한다 — 낡은 전제 위의 감사는 결론이 뒤집힌다.

## 1. 네 축과 하나의 불변조건

### 축 — 움직이면 반드시 대가가 있다

| 축 | 왼쪽 | 오른쪽 | 지키려는 것 |
|---|---|---|---|
| **A** | 검증 강제 | 경량·저비용 | 검증된 결과물 ↔ 저위험 작업의 마찰 |
| **B** | 자율 완결 | 확인·정지 | 끝까지 감 ↔ 객관적 판단을 위해 멈춤 |
| **C** | 정직·근거 명시 | 간결 | 거짓 없는 결과물 ↔ 읽는 사람의 인지부하 |
| **D** | 판정 통일 | 지점별 정밀 | 일관된 판단 ↔ 각 규칙 고유 조건의 보존 |

축은 좋고 나쁨이 아니라 **위치**다. 왼쪽이 항상 옳다면 축이 아니라 규칙일 것이다. 예를 들어 축 A를 끝까지 왼쪽으로 밀면 오타 수정에도 전체 테스트 스위트를 돌리게 되고, 끝까지 오른쪽으로 밀면 배포 전 검증이 사라진다.

### 불변조건 — 어느 방향으로도 이득이 없다

**무결성**: 두 규칙이 같은 대상에 서로 다른 조건이나 수치를 부과하지 않는다.

이건 축이 아니라 게이트다. 같은 대상에 "한두 문장"과 "두세 문장"이 동시에 걸려 있으면 어느 쪽을 따를지 매 턴 판단해야 하고, 그 판단은 매번 다르게 나온다. 위반이면 방향·크기와 무관하게 수정 대상이다.

---

## 2. 매트릭스를 채우는 두 규칙

**한 축을 움직였는데 나머지가 전부 비어 있으면 대개 놓친 것이다.** 축은 독립적이지 않다. D를 왼쪽으로 밀어 여러 지점을 하나의 정의로 묶으면, 그 정의는 각 지점 조건의 합집합이 되기 쉽고 — 합집합이 넓어진 만큼 B(정지 조건)나 A(검증 범위)가 따라 움직인다. 빈칸을 보고했다면 그 축을 실제로 확인했는지 되묻는다.

**대가 칸이 빈 변경은 의심한다.** 개선만 있고 대가가 없는 변경은 오타 수정이거나, 대가를 아직 못 찾은 것이다. 경험상 후자가 훨씬 흔하다. 순수 개선이라고 판단했다면 그 근거를 한 줄로 쓴다 — "문구만 바꾸고 조건 목록은 동일" 같은 확인 가능한 형태로.

---

## 3. 다섯 단계

### 1단계 — as-is 원문 수집

변경 대상의 **현재 조건을 파일에서 그대로 옮긴다.** 기억으로 쓰지 않는다. 이미 편집했다면 `git show HEAD:<path>` 또는 이전 버전 파일에서 가져온다.

이 단계가 형식적으로 보이지만, 2단계의 외연 비교는 as-is 조건 목록이 정확해야만 성립한다. 기억으로 적은 as-is는 대개 to-be를 닮아 있어서 차이가 안 보인다.

### 2단계 — 매트릭스 채우기

네 축 각각에 방향(←/→/이동 없음), 크기(작음/보통/큼), 대가를 적는다. 크기는 정량화되지 않는 정성 판정이므로, 사용자가 이견을 낼 수 있도록 근거를 함께 쓴다.

특히 확인할 것: **to-be 조건이 as-is에 없던 기준을 포함하는가.** 정의를 신설하거나 여러 지점을 묶을 때, 원래 어느 지점에도 없던 조건이 슬쩍 들어가면 네 곳의 발동 범위가 한꺼번에 넓어진다.

### 3단계 — 불변조건 검사

`scripts/check.sh <파일경로>`를 돌려 후보를 뽑고, 나온 라인들을 눈으로 대조한다. 스크립트는 세 가지를 본다 — 위험 판정 표현의 중복, 길이·수치 상한의 중복, 정의된 용어의 사용처.

스크립트가 잡지 못하는 것도 있다. 사전에 등록한 표현만 매칭하므로 새로 생긴 동의어는 놓치고, 두 규칙이 같은 대상을 가리키는지는 사람이 판단해야 한다. 스크립트 출력이 0건이어도 "통과"가 아니라 "등록된 패턴에서는 발견 없음"으로 보고한다.

특히 **원래 없던 조건이 새로 들어온 경우는 3단계로 잡히지 않는다** — 문자열의 중복이 아니라 조건 목록의 변화이기 때문이다. 그건 2단계 외연 비교의 몫이다. 반대로 검사 1은 정의문 자체와 비유적 용법(`measures your change's blast radius` 같은)도 함께 잡으므로, 출력 전부가 유효한 후보는 아니다. 라인을 열어보고 역할을 판별한 뒤 보고에 쓴다.

### 4단계 — 실패 시나리오

**이 변경 때문에 잘못 동작하는 구체적 상황을 하나 쓴다.** 사용자가 실제로 할 법한 요청 + 변경 전 동작 + 변경 후 동작 형태로.

시나리오를 못 쓰겠다면 둘 중 하나다. 변경이 정말 무해하거나(오타·문구 정리), 변경을 아직 이해하지 못했거나. 후자를 배제할 수 없으면 판정을 "보류"로 낸다.

### 5단계 — 판정

**적용** / **수정 후 적용** / **보류** 중 하나. 불변조건 위반은 자동으로 "수정 후 적용"이다. 축 이동이 의도와 다른 방향으로 새어 나갔으면 그 절만 되돌리는 부분 수정을 먼저 제안한다 — 변경 전체를 롤백하면 얻은 것까지 잃는다.

## 4. 보고 형식

사용자에게 돌려주는 감사 의견은 이 네 블록으로 고정한다. 블록 순서를 바꾸지 않는 이유는, 판정을 먼저 읽고 근거를 나중에 읽으면 매트릭스가 판정의 사후 정당화처럼 보이기 때문이다.

```markdown
## 매트릭스
| 축 | 방향 | 크기 | 대가 |
|---|---|---|---|
| A 검증↔경량 | ← / → / ➖ | 작음·보통·큼 | (없으면 근거를 쓴다) |
| B 자율↔확인 | | | |
| C 정직↔간결 | | | |
| D 통일↔정밀 | | | |

## 불변조건
✅ 통과 (등록된 패턴 기준) / ❌ 위반 — <어느 규칙과 무엇이 충돌하는지>

## 실패 시나리오
<구체적 요청> → 변경 전: <동작> / 변경 후: <동작>

## 판정
적용 / 수정 후 적용 / 보류 — <한 줄 근거>
```

변경이 여러 건이면 건마다 이 네 블록을 반복한다. 여러 건을 한 매트릭스에 합치면 어느 변경이 어느 축을 움직였는지 사라진다.

## 5. 실증 — 이 매트릭스가 잡아낸 실제 결함

축과 단계가 자의적이지 않다는 근거다. 2026-07-27 CLAUDE.v.4.9 작업에서 실제로 발생했고, 매트릭스를 먼저 채웠다면 커밋 전에 걸렸을 두 건이다.

**사례 1 — high-stakes 정의를 신설하며 조건 하나를 추가**

다섯 곳에 흩어진 위험 판정 문구를 Scope 절의 정의 하나로 묶으면서, 원래 어느 지점에도 없던 "changes a shared interface other code depends on"을 정의에 넣었다. Rule 10의 blast radius 나열(순위 매기기)에서 가져온 것인데, 그건 판정 기준이 아니라 검증 깊이의 순위였다.

| 축 | 방향 | 크기 | 대가 |
|---|---|---|---|
| D 통일↔정밀 | ← 통일 | 큼 | 다섯 지점의 고유 조건이 합집합으로 확대 |
| B 자율↔확인 | → 확인 | 보통 | **의도하지 않음** — 시그니처 변경이 stop 조건에 편입 |

D를 움직인 대가가 B로 새어 나갔다. 실패 시나리오는 이랬다 — 사용자가 "이 함수 시그니처 바꿔줘"라고 하고 더 나은 접근이 보이면, 변경 전에는 한 문장 말하고 진행했지만 변경 후에는 멈추고 답을 기다린다. 흔한 작업이라 마찰이 반복된다.

**사례 2 — push back에 "two or three sentences" 상한 추가**

반대 의견에 근거를 싣게 하려고 문장 수 상한을 바꿨는데, Response Discipline이 caveat을 이미 "a sentence or two"로 제한하고 있었다. 같은 대상에 1–2와 2–3이 동시에 걸린 상태 — 불변조건 위반이라 방향·크기를 볼 것도 없이 수정 대상이었다. 3단계의 수치 표현 검사가 이걸 잡는다.

두 사례의 공통점은 **변경 자체는 타당했다**는 것이다. 문제는 지불한 대가를 안 본 것이었다.

## 참고

- 감사 대상 파일의 최신 정본은 `ClaudeCode/CLAUDE.v.*.md` 중 버전이 가장 높은 것이다. 배포본은 `~/.claude/CLAUDE.md`이며, 감사 후 배포했다면 두 파일이 바이트 단위로 일치하는지 확인한다.
- 이 스킬은 규칙 사본을 갖고 있지 않다. 판단은 항상 실제 파일을 읽어서 한다 — 사본을 두면 정본과 어긋나고, 어긋난 사본으로 한 감사는 틀린 결론을 낸다.
