# Doc Writer

프로젝트 문서를 타입별 네이밍 규칙과 타입별 규격에 따라, 고정 템플릿 없이 프로젝트 특성·상황에 맞게 유연하게 생성한다.

**적용 조건**: 이 스킬은 **저장되는 문서·파일 산출물을 만들거나 갱신하려는 의도가 분명할 때만** 동작한다. "분석해줘"·"조사해봐"·"검토해줘"·"계획 짜줘"처럼 작업 수행만 요청한 경우(결과를 대화로 답하면 되는 경우)에는 문서를 만들지 말고, 산출물이 필요해 보이면 "문서로 남길까요?"라고 먼저 확인한다.

**`사용자`는 IT·AI 도메인 실무자다.** 이 스킬이 `사용자`라고 부르는 독자는 관리 책임을 함께 지지만, 문서를 읽는 자리에서는 **엔지니어**이며 코드·아키텍처·도구 체계를 직접 다룬다. 따라서 이해를 돕는 방법은 **평이화가 아니라 정밀화**다 — 용어를 풀어 쓰는 대신 정확한 이름으로 부르고, 개념을 설명하는 대신 좌표와 계약을 준다. 일반 독자를 위한 비유·단계적 개념 도입·기초 용어 해설은 이 스킬의 산출물에 넣지 않는다. 아래 모든 규칙에서 "독자가 이해한다"는 이 수준을 뜻한다.

**report-style 과의 경계 (2026-08-12 확정)**: 문서 산출물의 **기본 스킬은 이 스킬**이고, 문체 SoT는 `references/writing-principles.md` §7(평서형 `~다` 종결)이다. `report-style` 은 **공식 보고 3종 — 담당보고·본부보고·부문보고** 에만 걸린다. 두 스킬의 어미 규칙은 정반대이므로(§7.1 평서형 ↔ report-style §2.1 명사형) 한 문서에 겹쳐 적용하지 않으며, 이 스킬로 쓴 문서에 `report-style/scripts/check.sh` 를 돌려 명사형으로 고치는 작업은 **사용자가 공식 보고 전환을 명시할 때만** 수행한다. 명시 없이 문체를 바꾸지 않는다.

**이 스킬 파일 자신에 적용하는 범위**: `SKILL.md` 와 `references/` 는 문서 산출물이 아니라 지시문이므로 §7 전체를 적용하지 않는다. 적용하는 것은 **§7.3(구어·비유·의인화 회피) 하나**이며, 위반 수정 비용이 한 단어이고 grep 으로 판정되기 때문이다. §7.7(제목의 부연 dash 금지)과 §8(산문 화살표 체인 금지)은 적용하지 않는다 — 제목의 부연 dash 와 핵심 커버리지의 화살표 체인은 이 파일들의 규약이다.

## 워크플로우

문서 생성 요청 시 아래 순서를 따른다:

```
요청 수신 → 타입 식별 → 타임스탬프 확인 → 파일명 생성 → 경로/중복 검증 → 타입 규격 채택 → 프론트매터 작성 → 규격 기반 작성 → 마감 점검(scripts/check.sh)
```

위는 **새 문서 생성** 흐름이다. **기존 문서 갱신** 시에는 타입 식별·파일명 생성·경로 검증을 건너뛰고, 본문을 수정한 뒤 프론트매터의 `updated`(오늘 날짜, `date`로 확인)와 필요 시 `status`·`revisions`만 갱신한다. **마감 점검은 건너뛰지 않는다** — 신규와 갱신에 같은 규칙이 걸리며, 갱신에서는 이번에 고친 줄만 판정한다(문체 규약은 소급 적용하지 않는다). 본문 수치를 다시 잰 갱신이면 `measured` 도 함께 올린다 — 재지 않았으면 그대로 둔다.

### 1. 타입 식별

사용자 요청에서 문서 타입을 파악한다. 명시적 PREFIX가 없으면 맥락으로 추론하고 사용자에게 확인한다.

**`PLAN` 은 타입을 고른 뒤 모드를 한 번 더 고른다** — 저장소를 고치는 **개발 계획**과 과제·조직·일정을 움직이는 **추진 계획**은 독자도 완료 판정 방법도 다르다. 요청의 대상(저장소·코드 ↔ 과제·조직)과 수행자(Claude ↔ 사람·팀)로 판별하고, **기울지 않으면 쓰기 전에 한 문장으로 확인한다.** 판별표와 두 모드의 규격은 [references/doc-types.md](references/doc-types.md) §PLAN 에 있다.

| Prefix | 용도 | 문서군 |
|--------|------|--------|
| `PRD` | 제품 요구사항 | 협업 |
| `PLAN` | 구현·실행 계획 — **개발 / 추진 두 모드** | 협업 |
| `ADR` | 아키텍처 결정 기록 | 협업 |
| `HANDOFF` | 세션 인계 (다음 세션 재개용 스냅샷) | 협업 |
| `RESEARCH` | 외부 대상 조사 (도구·제품·논문·사례) | 이해 |
| `STRATEGY` | 방향성 정의 (RESEARCH 이후 · PLAN 이전) | 이해 |
| `ANALYSIS` | 우리 대상 진단 (코드·구조·문서·조직) | 이해 |
| `REPORT` | 상태·진행·완료 보고 | 이해 |
| `DOCUMENTATION` | 구조·개념 설명 (시스템·방법론) | 이해 |
| `GUIDE` | 따라 하는 문서 (사용 절차·준수 규약) | 이해 |
| `REFERENCE` | 소재·포인터 색인 (다시 찾아갈 곳) | 이해 |
| `NOTE` | 간단 메모 | 메모 |

**문서군은 독자가 아니라 쓰임으로 나뉜다** — 읽고 나서 무엇을 하는가. 아래가 문서군 정의의 SoT이며, 타입별 규격은 [references/doc-types.md](references/doc-types.md) 에 있다.

- **협업** (PRD·PLAN·ADR·HANDOFF): **Claude가 실행에 쓰는 문서.** 독자 = 사용자·이후 세션의 Claude. 무엇을 만들고 어떤 순서로 하며 무엇을 결정해 두었는지를 남겨, 다음 세션이 모호함 없이 이어받아 실행하게 하는 것이 가치다. writing-principles §1–7 적용. HANDOFF는 그중에서도 **다음 세션의 Claude**가 1차 독자다.
- **이해** (RESEARCH·STRATEGY·ANALYSIS·REPORT·DOCUMENTATION·GUIDE·REFERENCE): **사용자가 대상을 이해하려고 읽는 문서.** 독자 = 사용자. Claude가 만든 코드·진행 내용·외부 조사를 사용자가 정확히 파악하게 하는 것이 이 문서군의 일이며, 완성 기준은 **읽고 나면 대상이 그대로 서는 상태**다 — 구조와 인과가 잡히고, 어디까지가 확인된 사실인지 갈리며, 무엇을 다루지 않았는지가 드러나는 것. 그 판정 항목이 아래 §8 이해 준비 점검이다. writing-principles §1–7 적용, 특히 §1 User-Centered·§6 Self-Contained를 강하게 따른다.
  - **판단은 이 문서군의 몫이 아니다.** 무엇을 할지는 사용자가 **여러 문서를 종합해** 정하며, 문서 하나가 그 결론을 대신하지 않는다. 각 타입 커버리지에 있는 추천·권장 사항·다음 단계는 이해를 세운 뒤 붙이는 **첨언**이지 문서의 중심이 아니다 — 그 절이 커지면서 대상 서술을 밀어내면 무게중심이 잘못 옮겨간 것이다.
- **메모** (NOTE): 개인 임시 기록. 자유 형식, 정해진 가이드 없음(writing-principles §7도 §8도 강제하지 않는다).

> **이해 문서는 저장소 밖으로 나갈 수 있다.** 사용자가 이 문서를 근거로 조직 보고를 쓰거나 팀에 규칙을 배포하는 일이 실제로 일어난다. 그렇다고 외부 전달본으로 쓰는 것은 아니다 — 전달은 `report-style` 스킬과 별도 보고본의 몫이고(바로 아래 주석), 이해 문서가 책임지는 것은 **그 재료가 틀리지 않은 것**이다. §8-6 확실성 표시가 그 자리다.

> 문서군은 **작성 시점의 목적**으로 나뉜다. 수명이 끝나 아카이브된 문서(`status: archived`)는 별도 문서군이 아니라 **원래 문서군에 그대로 속한다** — 위 원칙은 아카이브 시점에 소급 적용되지 않으며, 본문은 당시 그대로 보존한다(§9).

> **조직 보고는 이 스킬의 자리가 아니다.** `REPORT` 의 독자는 사용자이며, 개발 완료·검증 결과·테스트 결과를 하나의 타입으로 다룬다. 외부 조직에 내는 공식 보고 3종(담당보고·본부보고·부문보고)은 골격과 문체를 함께 규정하는 `report-style` 스킬이 담당한다.

> **RESEARCH·ANALYSIS·REPORT는 대상과 근거로 구분된다.** 셋 다 무언가를 조사해 결론을 내지만, 무엇을 조사했고 무엇을 근거로 그 결론을 내렸는가가 다르다.
>
> ```
>                        대상이 우리 밖             대상이 우리 것
>                    (도구·제품·논문·사례)      (우리 코드·문서·조직)
>                 ┌──────────────────────────┬──────────────────────────┐
>  읽어서 안다    │         RESEARCH         │         ANALYSIS         │
>  (문서·웹·코드) │   옵션과 트레이드오프    │   현 상태 진단과 권고    │
>                 ├──────────────────────────┼──────────────────────────┤
>  돌려서 안다    │         RESEARCH         │          REPORT          │
>  (실행·측정)    │ 벤치마크 재현·실측 비교  │      검증·정찰 기록      │
>                 └──────────────────────────┴──────────────────────────┘
> ```
>
> 판정이 서지 않으면 순서대로 적용한다 — ① 우리 것을 직접 돌려 본 기록이면 `REPORT` ② 대상이 우리 밖이면 `RESEARCH` ③ 나머지는 `ANALYSIS`. 이 경계는 **소급 적용하지 않는다** — 이미 다른 타입으로 쓰인 문서는 이름을 바꾸지 않는다(바꾸면 `related_docs` 링크가 깨진다. §9와 같은 원리).

> **문체 규약은 소급 적용하지 않는다.** 한국어 문장 스타일(writing-principles §7)은 문서군을 가리지 않고 적용되지만, 이미 쓰인 문서를 문체 때문에 다시 수정하지는 않는다.

> **아카이브는 타입이 아니라 상태다.** 수명이 끝난 문서는 새 타입으로 다시 쓰지 않는다 — 원래 타입(`PRD`·`REPORT` 등)과 파일명을 **그대로 둔 채** 프론트매터 `status` 만 `archived` 로 바꾸고 아카이브 폴더로 옮긴다. 아래 §9 참조.

### 2. 타임스탬프 확인

**반드시 `date` 명령으로 현재 시각을 확인한다.** LLM 지식 기준일을 사용하지 않는다.

```bash
date "+%Y-%m-%d %H:%M"
```

### 3. 파일명 생성

**네이밍 규칙:**

- **형식**: `{PREFIX}-{BRIEF-DESCRIPTION}-{YYYY-MM-DD-HHMM}.md`
- **대소문자**: PREFIX와 DESCRIPTION은 **ALL UPPERCASE**
- **구분자**: 하이픈(`-`)으로 단어 구분
- **DESCRIPTION**: 핵심 내용을 2-4단어로 요약
- **영문 고정**: 한국어 요청이어도 DESCRIPTION은 핵심 키워드를 영문으로 변환한다 (예: "인증 개선 계획" → `PLAN-AUTH-IMPROVEMENT-...`)

**예시:**

| 요청 | 파일명 |
|------|--------|
| "사용자 인증 PRD 작성해줘" | `PRD-USER-AUTH-FEATURE-2026-02-24-1430.md` |
| "DB 마이그레이션 계획" | `PLAN-DATABASE-MIGRATION-2026-02-24-1430.md` |
| "GraphQL vs REST 비교 조사" | `RESEARCH-GRAPHQL-VS-REST-2026-02-24-1430.md` |
| "이번 세션 인계 문서 남겨줘" | `HANDOFF-AUTH-REFACTOR-2026-02-24-1430.md` |

### 4. 경로 및 중복 검증

- **기본 위치**: `_docs/` 폴더. **이는 기본값일 뿐이며, 지정된 위치가 있으면 그쪽이 우선한다** — 지정이 없을 때만 `_docs/` 를 쓴다. 타입별 예외는 없다 — 지정이 없으면 HANDOFF도 `_docs/`.
  - **지정을 읽는 순서**: ① 사용자의 직접 지시("여기에 저장해") ② 프로젝트 규약(`CLAUDE.md` 등에 적힌 문서 규율·저장 위치) ③ 이미 있는 작업 트랙별 폴더(예: `poc/<트랙>/_docs/`, `lab/<패키지>/_docs/`). 가장 구체적인 것을 따르고, 셋 다 없을 때 `_docs/` 를 만든다.
  - **기본값으로 동작할 때는 `docs/` 에 직접 쓰지 않는다.** `docs/` 는 프로젝트의 **정식 결과물**만 두는 자리이고, 무엇을 그리로 올릴지는 **사용자가 선별**한다 — 승격은 사용자가 `git mv` 로 한다. 이 승격 절차 역시 기본 규약이므로, 프로젝트가 `docs/` 하위를 문서 위치로 지정했다면 그 지정을 따른다.
- 대상 디렉토리 존재 여부 확인 → 없으면 생성
- 동일 PREFIX + 유사 DESCRIPTION 파일 존재 여부 확인 → 발견 시 아래 기본 처리를 따르되, 애매하면 사용자에게 확인

**같은 주제의 문서가 이미 있을 때 — 타입별 기본 처리** (사용자 지시가 있으면 그것이 최우선):

- **살아있는 문서** (PRD·PLAN·RESEARCH·STRATEGY·ANALYSIS·REPORT·DOCUMENTATION·GUIDE·REFERENCE): 새 파일을 만들지 않고 **기존 문서를 갱신**한다. 문서가 곧 현재 상태다. 특히 RESEARCH·ANALYSIS는 한 번에 끝나지 않는다 — 내용 확장이나 새 관점의 추가는 기존 문서에 섹션을 더하는 방식으로 갱신한다. **REFERENCE는 갱신이 기본 동작이다** — 포인터가 늘거나 옮겨지면 같은 파일의 해당 행만 고친다. **REPORT도 같다** — 같은 PLAN·같은 요청 줄기에 추가 작업이 붙으면 새 보고서를 만들지 않고 이 문서를 갱신한다(대상이 바뀌면 새 REPORT).
- **시점 스냅샷** (HANDOFF): 같은 주제라도 **새 파일**을 만든다. 인계는 시점 기록이 가치이므로 갱신으로 덮지 않는다. 이전 문서가 유효성을 잃으면 `status: superseded` 처리(§9).
- **불변 기록** (ADR): 승인(`active`) 후에는 본문을 수정하지 않는다. 결정이 바뀌면 **새 ADR**을 쓰고 기존 ADR을 `superseded` 처리한다. 제안이 채택되지 않으면 `status: rejected` 처리하고 기각 사유를 본문에 남긴다.

### 5. 타입 규격 채택

[references/doc-types.md](references/doc-types.md) 에서 해당 타입 섹션을 열어 작성 규격으로 채택한다:

- 그 타입의 **독자·핵심 질문·관점**을 작성 관점으로 삼는다
- 그 타입의 **핵심 커버리지**를 작성 기준으로 삼는다
- 타입 섹션의 **검사 tell·경계 tell**로 작성 중 자기 점검한다
- NOTE 타입은 규격 없이 자유형으로 작성

### 6. 프론트매터 작성

모든 문서는 본문 최상단에 YAML 프론트매터를 포함한다. 형식:

```yaml
---
type: strategy
audience: 사용자 · Claude
keywords: [매크로 lowering, macro lowering, 컴파일 백엔드, compile.py]
related_docs:
  - docs/RESEARCH-COMPILER-BACKEND-OPTIONS-2026-06-25-1610.md (선행 조사 — 이 방향의 근거)
  - core/compiler/compile.py (구현 지점)
  - CLAUDE.md (루트 §4 확장 사다리)
created: 2026-06-30 14:30
updated: 2026-07-10
measured: 2026-07-04
status: active
description: "먼저 결론 한 문장(무엇을 결정·판정했는가). 그다음 배경과 개요 1~2문장."
revisions:
  - v1.3 (07-10) 컴파일 단계에서 매크로 lowering 분리 · 계약 표 2행 교체
  - v1.2 (07-04) 기각안 B를 [참고]로 이동 · 근거 링크 3건 보강
  - v1.1 이하 (06-30~07-02) 초안 확정 — 상세는 `git show a1b2c3d:<이 파일>`
open_issues:
  - 매크로 확장 순서를 컴파일 전후 어디에 둘지 미정 — 벤치 결과 나오면 확정
  - 계약 표 3행의 타입명이 구현과 불일치 — 구현 쪽 리네이밍 대기
---
```

위 예시는 **살아있는 문서**(PRD·PLAN·RESEARCH·STRATEGY·ANALYSIS·REPORT·DOCUMENTATION·GUIDE·REFERENCE)의 형태다. **ADR은 이 예시를 따르지 않는다** — 승인(`active`) 후 본문을 수정하지 않으므로 `revisions` 가 쌓이지 않고, 결정이 바뀌면 새 ADR을 쓴다(§4).

**필드 정의:**

| 필드 | 필수 | 설명 |
|------|------|------|
| `type` | 필수 | 문서 타입(소문자): `prd`, `plan`, `adr`, `handoff`, `research`, `strategy`, `analysis`, `report`, `documentation`, `guide`, `reference`, `note`. **아카이브는 타입이 아니다** — `status` 로 표시한다 |
| `audience` | 필수 | 주 독자층. 협업 문서는 `사용자·Claude`, 이해 문서는 `사용자` (메모는 생략 가능). **`PLAN` 은 모드로 갈린다** — 개발 계획은 `사용자 · Claude`, 추진 계획은 `사용자`. 이해 문서에서 값이 늘 같으므로, 무엇을 얼마나 깊이 쓸지는 이 필드가 아니라 **타입 규격의 핵심 질문**이 정한다(doc-types.md) |
| `keywords` | 필수 | 이 문서를 **찾을 때 쓰일 호칭** 3~6개를 인라인 배열로. 정식명·통용 약어·코드 식별자를 함께 넣는다 — `[MyK, My K, billing2, ACC, Agent Composer Core]`. `description` 은 결론 한 문장이라 그 문서가 채택한 호칭 하나만 담기고, 나머지 호칭으로 찾으면 이 문서가 잡히지 않는다. 그 손실을 메우는 자리다 |
| `related_docs` | 선택 | 관련 문서·코드 경로. 각 항목 뒤 괄호로 관계를 주석. 없으면 필드 생략 |
| `created` | 필수 | 최초 작성 시각 `YYYY-MM-DD HH:MM`. **`date` 명령으로 확인**(파일명 타임스탬프와 동일) |
| `updated` | 선택 | 최종 수정일 `YYYY-MM-DD`. 기존 문서 갱신 시에만 추가 |
| `measured` | 선택 | 본문 측정값의 기준 시점 `YYYY-MM-DD`. **수치가 근거인 문서**(RESEARCH·ANALYSIS·REPORT 등)에만 두고, 수치가 없거나 본문에서 근거로 쓰이지 않으면 필드째 생략한다. 본문에 시점을 괄호로 병기하지 않기 위한 자리다(§수치와 상태) |
| `status` | 필수 | 문서 상태: `draft` / `active` / `superseded` / `rejected` / `archived`. **값은 이 다섯 중 하나로 시작한다** — 덧붙일 사정이 있으면 뒤에 ` — 부연` 을 잇는다(`active — 수정 대장 운영 중`). 열거값이 문두에 있어야 `grep "^status: active"` 로 걸러진다 |
| `description` | 필수 | 결론 한 문장을 먼저, 이어서 배경·개요 1~2문장. 따옴표로 감싸고 **한 줄로 끝낸다** — 블록 스타일(`\|`·`>`)로 쓰거나 줄바꿈으로 이어 쓰면 `grep "^description:"` 이 첫 줄만 가져가 나머지가 검색에서 사라진다 |
| `revisions` | 선택 | 회차별 변경 요지 로그. 한 항목 = 한 회차, 최신이 맨 위. 한 항목은 두 줄 이내. 어느 문서에 둘지는 프로젝트 지침을 따른다 |
| `open_issues` | 선택 | 아직 정해지지 않았거나 처리를 기다리는 사항. 한 항목에 무엇이 미결인지와 무엇이 있으면 해소되는지를 함께 적는다. 해소되면 그 항목을 지우고, 비면 필드째 지운다 |

- `related_docs`는 **포인터**일 뿐이다. 본문이 의존하는 핵심 내용은 여전히 본문에 인라인한다(writing-principles §6 Self-Contained).
- `description`은 "결론 먼저" 원칙을 따른다 — 독자가 첫 줄에서 문서의 결론을 파악할 수 있어야 한다.
- **`keywords` 는 검색 표면이고 `description` 은 결론 층이다.** 둘의 성격이 반대라 한 필드에 겸할 수 없다 — `description` 에 별칭을 나열하면 결론 한 문장이 덮이고, 나열하지 않으면 그 문서는 자기가 채택한 호칭으로만 찾힌다. `keywords` 는 그 별칭들의 자리다.
  - **넣는 것은 "이 문서를 찾을 때 입력할 말"이다.** 문서가 다루는 대상의 정식명, 실제로 통용되는 약어와 띄어쓰기 변형(`MyK`·`My K`), 저장소에서 그 대상을 가리키는 식별자(레포명·모듈명·Jira 키)까지 넣는다. 주제어를 요약하는 자리가 아니므로 `분석`·`검토` 같은 일반어는 넣지 않는다 — 어느 문서에나 걸려 필터 구실을 못 한다.
  - **표기가 갈리는 대상일수록 값이 크다.** 한 대상을 부르는 말이 하나뿐이면 파일명만으로도 찾히고, 여럿이면 파일명은 그중 하나만 담는다. 후자에서만 이 필드가 일한다.
  - **본문을 고쳐도 다시 세지 않는다.** `description` 의 집계 수치와 달리 `keywords` 는 대상의 호칭이라 본문 개정과 무관하게 유효하다. 대상 자체가 개명됐을 때만 옛 이름을 남긴 채 새 이름을 더한다 — 옛 이름을 지우면 그 이름으로 적힌 과거 문서에서 이 문서로 오는 길이 끊긴다.
- **`revisions` 는 로그 층이고 `description` 은 상태 층이다.** 회차마다 갱신되는 문서에는 성격이 반대인 둘이 섞이는데(→ [수치와 상태](#수치와-상태--오래-사는-문서의-규율-모든-타입-공통) 세 번째 항목), 로그를 받을 필드가 없으면 갈 곳 잃은 개정 경위가 `description` 으로 흘러들어 결론 한 문장을 덮는다. `revisions` 는 그 로그의 자리다.
  - **담는 것은 "무엇이 바뀌었나"뿐이다** — 절·항목·수치 단위로 적는다. 판단 근거·시행착오·재사용 절차는 로그가 아니라 지식이라 회차가 지나도 유효하므로 본문이나 별도 필드에 둔다. 한 항목이 두 줄을 넘으면 대개 로그가 아닌 것이 섞인 신호다.
  - **지난 항목은 고치지 않는다.** 아카이브 본문을 수정하지 않는 원리(§9)를 살아 있는 문서로 확장한 것으로, 그때 그렇게 바꿨다는 사실이 이 필드의 가치다.
  - **오래된 회차는 묶어 압축한다.** 최근 몇 개만 개별 항목으로 두고 그 이전은 한 줄로 합치되, 상세를 되찾을 포인터(커밋 해시·원본 경로)를 그 줄에 남긴다. 압축은 삭제가 아니라 포인터로 바꾸는 일이다.
- **`open_issues` 는 지워지는 층이다.** `revisions` 가 고치지 않는 사료라면 `open_issues` 는 해소되는 순간 사라져야 하는 미결이다. 성격이 반대인 둘을 한 필드에 두면 이미 처리된 사항이 이력에 섞여 계속 남고, 다음 독자는 그것을 아직 열린 문제로 읽는다.
  - **항목마다 해소 조건을 함께 적는다** — "무엇이 미결인가"만 적으면 언제 지워도 되는지 아무도 판정할 수 없다. 판단 대기라면 누구의 판단인지, 외부 사정 대기라면 무엇이 끝나야 하는지까지 적는다.
  - **비면 필드째 지운다.** 빈 목록을 남겨 두면 미결이 없다는 사실과 아직 확인하지 않았다는 사실이 같은 모습으로 보인다.
- **NOTE**(개인 메모)는 프론트매터를 생략할 수 있다 — 필요 시 `type`·`created`만 둔다.
- **`status` 는 문서의 수명 상태**다: `draft`(작성 중) → `active`(유효) → `superseded`(후속 문서로 대체됨) / `archived`(역할이 끝나 보관됨). 제안이 채택되지 않으면 `draft` → `rejected`(기각 — 주로 ADR, 기각 사유는 본문에 기록).
  - **폴더 위치로 `status` 를 추정하지 않는다.** `_archive/` 는 역할이 끝난 문서와 **잠시 보류한 문서**를 함께 담는다 — 진행을 멈추고 작업 폴더를 현재 과제 중심으로 정리하느라 옮겨 둔 문서는 다시 꺼내 이어 쓴다. 따라서 경로가 아카이브라는 사실만으로 그 문서를 낡았다고 판정하거나 `status` 를 고치지 않으며, 반대로 `status` 만 보고 폴더를 옮기지도 않는다.
  - **보류라면 그 사정을 부연에 남긴다** — `archived — 보류(재개 예정)`. 종료와 보류가 같은 폴더에 같은 값으로 앉아 있으면 다음에 여는 사람이 둘을 구분할 근거가 없다.
- **프론트매터와 본문은 독자가 다르다.** 프론트매터는 기계·에이전트가 읽는 메타 층이고, 본문은 사람이 읽는 층이다. 본문을 잘라 회의 자료·외부 전달본으로 옮겨도 프론트매터는 저장소에 남아 **출처와 문서 간 관계를 보존한다.**
- **따라서 본문 자립(§8-3)과 `related_docs` 유지는 상충하지 않는다.** 오히려 본문에서 외부 참조를 걷어낸 문서일수록 프론트매터가 **유일한 연결 고리**이므로 반드시 남긴다. 본문이 참조하지 않는 관계라면 그 사정을 괄호 주석에 적어 둔다(예: "본문은 자립을 위해 참조하지 않는다 — 원 기록이 필요하면 여기서 찾는다").

### 7. 규격 기반 작성

고정 템플릿을 강제하지 않는다. 채택한 타입의 관점과 **핵심 커버리지**를 기준으로, 프로젝트 특성·규모·상황에 맞게 구조를 그때그때 구성한다:

- 타입의 "핵심 커버리지"를 기준으로 삼되, 고정 순서가 아니라 취사선택·재배열한다.
- 불필요한 요소는 생략하고, 상황이 요구하면 목록에 없는 요소를 추가한다.
- 사용자가 특정 구조를 요청하면 그것을 최우선한다.
- 작성 시 공통 품질 원칙(독자 중심, 명확성, 근거와 예시, 점진적 구조, 훑어읽기, 자립성)을 적용한다.
- **배치를 주장하는 자리는 도식으로 그린다**(writing-principles §8) — 무엇이 어디에 속하는가(구조·계층), 무엇이 어디로 옮겨가는가(흐름·분기·상태 전이), 이전과 이후가 어떻게 다른가. 셋 중 하나면 설명하지 말고 ASCII 도식을 넣고, 배치 주장이 아닌 곳에는 넣지 않는다. 형태별 골격은 [references/ascii-diagrams.md](references/ascii-diagrams.md).
- 한국어로 쓰는 모든 문서에 한국어 문장 스타일(writing-principles §7)을 적용한다 — 평서형 `~다` 종결, 존댓말 금지, 괄호 병기 여섯 용법(§7.8), 판정 우선 서술(§7.9), 개념 도입 문장(§7.10), 동작 주체와 효과 문장(§7.11), 표 셀의 문장 형태(§7.12), 설득·수사 문장 배제(§7.13). **이해 문서**는 여기에 더해 독자 중심으로 쓰고, 작성 시점부터 §8 이해 준비 점검을 준수한다.

### 8. 이해 준비 점검 (이해 문서 전용)

이해 문서(RESEARCH·STRATEGY·ANALYSIS·REPORT·DOCUMENTATION·GUIDE·REFERENCE)의 완성 기준은 **"읽고 나면 대상이 정확히 서는 상태"**다. 기록이 충실한 것과 이해가 서는 것은 다르다 — 조사한 것을 빠짐없이 적어도, 무엇이 무엇 때문인지와 어디까지가 확인된 것인지가 갈리지 않으면 독자는 원자료를 다시 읽어야 한다. 작성 시점부터 아래 일곱을 준수한다.

1. **경로 누출 금지** — 본문·`related_docs`에 개인 절대경로(`/Users/...`)를 넣지 않는다. 저장소 상대 경로 또는 URL만 쓴다. 저장소가 다른 기기·환경으로 옮겨져도 링크가 살아야 하기 때문이다.
2. **용어 자립** — 판정 기준은 **독자가 이 저장소·이 세션 밖의 고유명은 모른다**는 것이다. 도메인 개념(LangGraph·CVSS·EOL·스토리 포인트 등)은 전제하고 풀이하지 않는다 — 독자는 실무자다. 풀이 대상은 셋뿐이다: 내부 약어, 이 프로젝트의 고유 식별자(모듈명·잡 이름·설정 키), 외부 제품이 자기만의 뜻으로 쓰는 낱말. 도메인 개념을 풀어 쓰면 아는 것을 다시 읽히는 비용만 든다.
3. **문서 자립 · 선형 자립** — 이 문서만 읽고, 위에서 아래로 한 번 읽어 대상을 이해할 수 있어야 한다(writing-principles §6·§6.1). 세션 대화나 다른 문서를 알아야 이해되는 서술을 남기지 않으며, 문서 안에서도 절 번호로 독자를 이동시키지 않는다 — 앞뒤 절의 내용이 필요하면 그 내용을 한 줄로 요약해 그 자리에 쓴다. **이 요구는 본문에만 적용된다** — `related_docs` 는 비우지 않고, 외부 문서의 출처 표기(`대상 문서 §3.4`)는 이동 지시가 아니므로 해당하지 않는다.
   - **검사 tell**: 본문의 자기 절 번호를 전부 지웠을 때 문장이 그대로 성립하는가. 성립하지 않으면 그 절의 내용이 이 문장에 빠져 있는 것이다.
4. **근거 표시** — 수치·버전·날짜의 기준 시점은 프론트매터 `measured` 로 밝히고, 본문에는 값만 남긴다(§수치와 상태). 시점 없는 수치는 독자가 사실 여부를 되물어 오게 만들고, 그것이 곧 반복 수정의 시작이다.
5. **결론 우선 · `## 0. 한 줄 요약` 필수** — 이해 문서는 제목 다음 첫 절을 `## 0. 한 줄 요약` 으로 열고, 그 문서에서 가장 핵심이 되는 내용을 **1~2문장**으로 적는다. 사용자가 이 문서를 읽고 무엇을 판단하게 되는지가 그 안에 있어야 하며, 배경·조사 과정·조건은 넣지 않는다 — 그 자리는 뒤 절이다. 프론트매터 `description` 과 이 절은 **같은 결론**을 가리킨다. 조사 과정을 따라가야 결론에 닿는 문서는 독자에게 같은 조사를 다시 시킨다.
   - **번호는 `0` 으로 고정한다.** 본 서술은 1번부터 시작하므로, 요약을 앞에 두면서 기존 절 번호를 다시 매기지 않는다.
   - **협업 문서(PRD·PLAN·ADR·HANDOFF)와 NOTE에는 두지 않는다** — 이 절은 사용자가 판단·이해를 위해 읽는 문서의 자리다.
   - **검사 tell**: 0번 절만 읽고 이 문서가 무엇에 대해 무엇을 말하는지 옮길 수 없거나, 프론트매터 `description` 의 첫 문장과 다른 결론을 가리키면 아직 요약이 아니다.
6. **확실성 표시** — 아래 네 상태를 구분해 적는다. 셋만 쓰면 "원문에 없는 것"이 "내가 안 본 것"과 섞여, 독자가 원문을 열어 보면 해소된다고 오해한다.

   | 상태 | 뜻 | 표기 | 독자가 할 일 |
   | --- | --- | --- | --- |
   | 확인 | 실행하거나 원문을 읽어 확인 | 단정 | 없음 |
   | 추정 | 근거는 있으나 미검증 | "추정 — 미검증" | 검증 방법이 함께 적혀 있어야 한다 |
   | 미확인 | 볼 수 있었으나 보지 않음 | "이 문서가 답하지 않는 것" 절 | 그 자료를 열면 해소 |
   | **원문 부재** | **대상 자료에 그 정보 자체가 없음** | **"대상 문서에 기재돼 있지 않다"** | **원문을 고쳐야 해소** |

   넷째 상태의 이름은 대상에 따라 다르다 — 대상이 우리 밖이면 **원문 부재**, 우리가 만든 것을 보고하는 REPORT면 **미측정**이다. 재지 않아서 없는 것이므로 그렇게 적고, 무엇을 재지 않았는지가 다음 실행의 입력이 된다.

   **이해 위에는 다른 것이 얹힌다** — 다음 문서, 다음 결정, 때로는 조직 보고. 틀린 이해는 틀렸다는 표시 없이 그대로 옮겨 가고, 어디서 어긋났는지는 한참 뒤에 드러난다.
7. **판정 기준 선행** — 대상을 평가·판정하는 서술이 있으면 그 기준(요구사항 · 목표치 · 합격선)을 대상 서술 절에서 먼저 세운다. 기준을 세우지 않고 낸 판정은 작성자의 기준으로 읽히며, 대상이 실제로 받은 요구사항과 다르면 판정 전체가 무효가 된다. 대상이 "다섯 중 하나를 고르라"는 요구를 받았는데 "원인을 설명하지 못했다"로 판정하면 그 지적은 성립하지 않는다.
   - **검사 tell**: "미달 · 부족 · 실패 · 미성립"이라고 쓴 문장마다 그 기준이 앞 절 어디에 있는지 지목할 수 있는가. 못 하면 기준이 문서 밖(작성자 머릿속)에 있다.

협업 문서(PRD·PLAN·ADR·HANDOFF)에는 이 점검을 강제하지 않는다 — 단 **1번·4번·6번·7번은 모든 문서에 적용**한다.

- **1번**: 저장소가 다른 환경으로 이동해도 링크가 살아야 한다.
- **4번**: 출처 없는 수치는 시간이 지나면 실제와 어긋나고 그 사실이 드러나지 않는다(→ [수치와 상태](#수치와-상태--오래-사는-문서의-규율-모든-타입-공통)).
- **6번**: 협업 문서는 다음 세션의 Claude가 실행 근거로 삼는다. 미검증을 확정으로 적으면 그대로 실행된다.
- **7번**: 판정이 들어가는 문서는 타입을 가리지 않는다. PLAN의 `→ verify:` 도 합격선이 없으면 판정할 수 없다.

메모(NOTE)에는 적용하지 않는다.

### 9. 아카이브 처리 (수명이 끝난 문서)

역할이 끝난 문서를 지우지 않고 보관하는 절차. **새 문서를 쓰는 일이 아니므로 타입 규격·네이밍 규칙과 무관하다.**

- **타입과 파일명은 그대로 둔다.** `PRD-...md` 는 아카이브돼도 여전히 `type: prd` 인 `PRD-...md` 다. 아카이브는 **타입이 아니라 상태**이므로 이름을 바꾸지 않는다(바꾸면 기존 `related_docs` 링크가 전부 깨진다).
- **프론트매터 2개 필드만 수정한다**: `status: archived`(또는 후속 문서가 대체한 경우 `superseded`), `updated: {오늘 — `date` 로 확인}`.
- **파일을 아카이브 폴더로 옮긴다**: 문서가 있던 자리 기준으로 `_docs/_archive/`(정식 결과물이면 `docs/_archive/`). 프로젝트에 다른 규약이 있으면 그것을 따른다. `git mv` 로 이력을 보존한다.
- **본문은 수정하지 않는다.** 요약·윤문·수치 갱신 금지 — 당시 값이 지금과 달라도 그대로 둔다. 아카이브의 가치는 **그때 그렇게 적혔다는 사실**이다.
- **대체 관계가 있으면 밝힌다**: `superseded` 로 내릴 때는 `related_docs` 에 후속 문서를 추가하고 괄호로 `(이 문서를 대체)` 를 붙인다.
- **문서 인덱스를 갱신한다**: 프로젝트에 문서 인덱스(예: `CLAUDE.md` 문서 표)가 있으면 경로와 상태 표시를 함께 고친다 — 안 고치면 인덱스가 즉시 실제 위치와 어긋난다.

## 수치와 상태 — 오래 사는 문서의 규율 (모든 타입 공통)

문서의 수치는 두 방향으로 틀린 값이 된다 — 쓰인 순간 정확해도 **그 뒤 코드가 바뀌어 실제와 어긋나거나**, 애초에 **잘못 세어져 처음부터 틀리거나**. 아래 넷 중 앞의 셋이 노후화를 막고 마지막 하나가 최초 오류를 막으며, 모두 문장이 아니라 설계로 막는 규율이고 문서군을 가리지 않는다.

- **측정값의 기준 시점은 프론트매터 `measured` 한 곳에 둔다.** 본문에는 값만 적는다 — `serve.py 42줄` 이지 `serve.py 42줄(2026-08-01 실측)` 도, `wc -l devgui/serve.py` 도 아니다. 값마다 시점이나 재는 명령을 괄호로 달면 문장마다 군더더기가 붙어 **독자가 핵심을 파악하는 속도가 떨어지고**, 정작 시점은 값의 개수만큼 흩어져 갱신 때 일부만 고쳐진다. 한 곳에 모으면 문서 전체가 "언제 기준 값인가"에 한 줄로 답한다 — 시점 없는 측정값은 **틀렸다는 사실 자체가 관측되지 않는다.**
  - **본문 수치를 다시 재지 않은 갱신에서는 `measured` 를 수정하지 않는다.** `updated` 만 움직이는 것이 정상이고, 둘이 벌어져 있다는 것 자체가 수치가 갱신되지 않았다는 신호다. 재측정했으면 그때 함께 올린다.
- **파생값을 저장하지 않는다.** 합계·건수·분류처럼 다른 표에서 세면 나오는 값은 원본의 복사본이다. 원본이 바뀌면 반드시 어긋나므로, 적어야 하면 세는 근거를 함께 적는다(예: "현황 표 기준"). **프론트매터 `description` 의 집계 수치가 가장 먼저 실제와 어긋난다** — 본문을 고칠 때 아무도 프론트매터를 다시 세지 않는다.
- **누적 문서는 로그 줄과 상태 줄을 나눈다.** `status: active` 이면서 회차마다 갱신되는 문서에는 성격이 반대인 둘이 섞인다. 회차 기록은 **사료라 고치지 않고**(§9 의 원리를 살아 있는 문서로 확장), 현재 상태는 **한 곳에만 두고 나머지는 그리로 참조한다.** 같은 사실을 표와 본문 두 곳에 실값으로 두면 쓰는 시점이 다르므로(발견 시 ↔ 처리 시) 갱신은 반드시 한쪽만 된다.
- **결론의 근거가 되는 집계는 쓰기 전에 다른 축으로 한 번 더 센다.** **출처는 면제 사유가 아니다** — 조사 단계에서 이미 센 값도, 대화로 이미 보고한 값도, 다른 문서에 적혀 있던 값도 문서에 실을 때 다시 센다. 문서에 들어간 숫자는 오래 살고 다른 문서로 복사되므로, 여기가 마지막 관문이다.
  - **다른 축**이란 합계를 그 내역과 대조하거나, 도구의 출력을 그것이 덮는다고 주장하는 원자료와 대조하는 것이다. 같은 명령을 두 번 돌린 것은 두 번이 아니라 한 번이다 — 범위 오류가 그대로 재현된다.
  - 둘이 어긋나면 **틀린 것은 두 번째 셈이 아니라 그 숫자다.** "다시 센 쪽이 잘못 셌겠지"로 넘기는 순간 오류가 그대로 실린다.

> **한 문장으로**: 복사본은 원본과 어긋나도 그 사실이 드러나지 않고, 포인터는 따라가면 고쳐진다. 값을 적기 전에 **"6개월 뒤 독자가 이걸 어떻게 다시 확인하나"** 를, 결론의 근거가 되는 값이라면 **"지금 다른 방법으로 세도 같은 값이 나오나"** 를 먼저 답한다.

## 마감 점검

**규칙 본문은 각 항목이 가리키는 절에 있고, 여기에 다시 적지 않는다.** 규칙을 요약해 옮겨 두면 본문을 고칠 때 이 목록만 남아 어긋나므로(§수치와 상태 "파생값을 저장하지 않는다"), 이 절은 판정 질문과 참조만 담는다. 문서를 저장하기 전에 하나씩 판정한다.

1. 타임스탬프를 `date` 명령으로 확인했는가 — §2 · §6 `created`
2. 파일명이 PREFIX·DESCRIPTION 전부 대문자에 하이픈 구분인가 — §3
3. 저장 위치를 지정 우선순위대로 골랐고, 같은 주제의 기존 문서를 확인했는가 — §4
4. 타입 규격을 채택하고 핵심 커버리지·검사 tell을 기준으로 삼았는가(`PLAN` 이면 모드까지 판별했는가) — §5 · [doc-types.md](references/doc-types.md)
5. 프론트매터가 타입에 맞게 채워졌는가 — §6
    - **`scripts/check.sh <문서.md>` 의 `[프론트매터 구조]` 축이 0건인가.** 필수 필드 누락·`type` 열거값 이탈·`status` 문두 이탈·`description` 줄 끊김·`keywords` 개수 부족을 함께 센다. 이 축은 프론트매터를 **원본 그대로** 읽는다(9번의 문체 축은 프론트매터를 여전히 보지 않는다 — 성격이 다른 두 검사가 같은 스크립트에 들어 있다)
6. 이해 문서면 이해 준비 점검 일곱 항목을, 협업 문서면 그중 1번·4번·6번·7번을 통과하는가 — §8
7. 측정값·파생값·누적 기록·재집계 넷을 지켰는가 — §수치와 상태
8. 서술어가 확인하러 갈 대상을 가리키고, 등급어에 근거 괄호가 붙었는가 — writing-principles §2.1
9. 한국어 문장 스타일을 지켰는가(평서형 종결·괄호 병기·구어와 비유 회피·설득 문장 배제) — writing-principles §7
    - **`scripts/check.sh <문서.md>` 를 실행해 모든 축 0건을 확인한다.** 존댓말 종결·구어 어휘·비유·격식 한자어·직역체·설득 문장·절대경로·산문 화살표 체인·자기 절 번호를 한 번에 센다. NOTE(개인 메모)에는 실행하지 않는다
    - **스크립트가 잡지 못하는 축이 셋 남는다** — 낱말 목록에 걸리지 않는 비유, 빠진 도식, 확실성 표시. 실행 결과 마지막에 그 셋이 출력되므로 저장 전에 직접 통독해 판정한다
    - 회피 예시를 그대로 인용한 줄과 코드블록 안의 매칭은 오탐이다. 출력된 줄을 보고 본문만 판정한다
10. 배치 주장이 도식으로 그려졌고 장식 도식과 산문 화살표 체인이 없는가 — writing-principles §8.3
11. 본문에 자기 절 번호 참조가 남아 있지 않은가 — writing-principles §6.1
    - `grep -oE "§[0-9]+(\.[0-9]+)?" <파일> | wc -l` 과 `grep -oE "(대상 문서|[A-Za-z_-]+\.md) §[0-9]+(\.[0-9]+)?" <파일> | wc -l` 의 차가 자기 참조 수다. 0이 아니면 각 자리에 그 절의 내용을 한 줄로 써 넣는다
