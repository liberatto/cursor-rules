# Doc Writer

프로젝트 문서를 타입별 네이밍 규칙과 Persona에 따라, 고정 템플릿 없이 프로젝트 특성·상황에 맞게 유연하게 생성한다.

**적용 조건**: 이 스킬은 **저장되는 문서·파일 산출물을 만들거나 갱신하려는 의도가 분명할 때만** 동작한다. "분석해줘"·"조사해봐"·"검토해줘"·"계획 짜줘"처럼 작업 수행만 요청한 경우(결과를 대화로 답하면 되는 경우)에는 문서를 만들지 말고, 산출물이 필요해 보이면 "문서로 남길까요?"라고 먼저 확인한다.

## 워크플로우

문서 생성 요청 시 아래 순서를 따른다:

```
요청 수신 → 타입 식별 → 타임스탬프 확인 → 파일명 생성 → 경로/중복 검증 → Persona 채택 → 프론트매터 작성 → 페르소나 기반 작성
```

위는 **새 문서 생성** 흐름이다. **기존 문서 갱신** 시에는 타입 식별·파일명 생성·경로 검증을 건너뛰고, 본문을 수정한 뒤 프론트매터의 `updated`(오늘 날짜, `date`로 확인)와 필요 시 `status`·`revisions`만 갱신한다.

### 1. 타입 식별

사용자 요청에서 문서 타입을 파악한다. 명시적 PREFIX가 없으면 맥락으로 추론하고 사용자에게 확인한다.

| Prefix | 용도 | 문서군 | Persona |
|--------|------|--------|---------|
| `PRD` | 제품 요구사항 | 협업 | PM |
| `PLAN` | 구현·실행 계획 | 협업 | Analyst |
| `RESEARCH` | 리서치 결과 | 협업 | Researcher |
| `STRATEGY` | 방향성 정의 (RESEARCH 이후 · PLAN 이전) | 협업 | Architect |
| `ANALYSIS` | 기술·비교·대안 분석 | 협업 | Analyst |
| `ADR` | 아키텍처 결정 기록 | 협업 | Architect |
| `HANDOFF` | 세션 인계 (다음 세션 재개용 스냅샷) | 협업 | — (자체 커버리지) |
| `REPORT` | 상태·진행·완료 보고 | 전달 | PM |
| `GUIDE` | How-to 가이드 | 전달 | Engineer |
| `DOCUMENTATION` | 일반 문서 | 전달 | Engineer |
| `NOTE` | 간단 메모 | 메모 | — (자유형) |

**문서군**에 따라 독자와 적용 원칙이 다르다 (writing-principles 최상단 참조):
- **협업** (PRD·STRATEGY·PLAN·RESEARCH·ANALYSIS·ADR·HANDOFF): 독자 = 사용자·Claude. 세션 간 공유 컨텍스트. §1–7 적용. HANDOFF는 그중에서도 **다음 세션의 Claude**가 1차 독자다.
- **전달** (REPORT·DOCUMENTATION·GUIDE): 최종 독자 = 외부 사람(다른 개발자·조직, 비전문 독자 포함 가능). 현재는 주로 사용자 본인이 읽더라도 **처음 보는 외부 독자 기준**으로 써서, 그대로 또는 최소 수정으로 전달 가능한 상태를 유지한다. 독자 중심, §1–7 적용, §8 전달 준비 점검 적용.
- **메모** (NOTE): 개인 임시 기록. 자유 형식, 정해진 가이드 없음(§7도 강제하지 않는다).

> **한국어 문장 스타일(§7)은 문서군을 가리지 않는다.** 평서형 `~다` 종결·존댓말 금지·괄호 병기 규약은 협업·전달 문서에 똑같이 적용된다. 두 문서군의 차이는 문체가 아니라 **독자 중심 서술과 자립성 요구의 강도**(§8)다. 이 규약은 **소급 적용하지 않는다** — 이미 쓰인 문서를 문체 때문에 다시 손대지 않는다.

> **아카이브는 타입이 아니라 상태다.** 수명이 끝난 문서는 새 타입으로 다시 쓰지 않는다 — 원래 타입(`PRD`·`REPORT` 등)과 파일명을 **그대로 둔 채** 프론트매터 `status` 만 `archived` 로 바꾸고 아카이브 폴더로 옮긴다. 아래 §9 참조.

### 2. 타임스탬프 확인

**반드시 `date` 명령으로 현재 시각을 확인한다.** LLM 지식 기준일을 사용하지 않는다.

```bash
date "+%Y-%m-%d %H:%M"
```

### 3. 파일명 생성

**네이밍 규칙:**

- **형식**: `{PREFIX}-{BRIEF-DESCRIPTION}-{YYYY-MM-DD-HHMM}.md`
- **대소문자**: PREFIX와 DESCRIPTION은 **ALL UPPERCASE**
- **구분자**: 하이픈(`-`)으로 단어 구분
- **DESCRIPTION**: 핵심 내용을 2-4단어로 요약
- **영문 고정**: 한국어 요청이어도 DESCRIPTION은 핵심 키워드를 영문으로 변환한다 (예: "인증 개선 계획" → `PLAN-AUTH-IMPROVEMENT-...`)

**예시:**

| 요청 | 파일명 |
|------|--------|
| "사용자 인증 PRD 작성해줘" | `PRD-USER-AUTH-FEATURE-2026-02-24-1430.md` |
| "DB 마이그레이션 계획" | `PLAN-DATABASE-MIGRATION-2026-02-24-1430.md` |
| "GraphQL vs REST 비교 조사" | `RESEARCH-GRAPHQL-VS-REST-2026-02-24-1430.md` |
| "이번 세션 인계 문서 남겨줘" | `HANDOFF-AUTH-REFACTOR-2026-02-24-1430.md` |

### 4. 경로 및 중복 검증

- **기본 위치**: `_docs/` 폴더. **이는 기본값일 뿐이며, 지정된 위치가 있으면 그쪽이 우선한다** — 지정이 없을 때만 `_docs/` 를 쓴다. 타입별 예외는 없다 — 지정이 없으면 HANDOFF도 `_docs/`.
  - **지정을 읽는 순서**: ① 사용자의 직접 지시("여기에 저장해") ② 프로젝트 규약(`CLAUDE.md` 등에 적힌 문서 규율·저장 위치) ③ 이미 있는 작업 트랙별 폴더(예: `poc/<트랙>/_docs/`, `lab/<패키지>/_docs/`). 가장 구체적인 것을 따르고, 셋 다 없을 때 `_docs/` 를 만든다.
  - **기본값으로 동작할 때는 `docs/` 에 직접 쓰지 않는다.** `docs/` 는 프로젝트의 **정식 결과물**만 두는 자리이고, 무엇을 그리로 올릴지는 **사용자가 선별**한다 — 승격은 사용자가 `git mv` 로 한다. 이 승격 절차 역시 기본 규약이므로, 프로젝트가 `docs/` 하위를 문서 위치로 지정했다면 그 지정을 따른다.
- 대상 디렉토리 존재 여부 확인 → 없으면 생성
- 동일 PREFIX + 유사 DESCRIPTION 파일 존재 여부 확인 → 발견 시 아래 기본 처리를 따르되, 애매하면 사용자에게 확인

**같은 주제의 문서가 이미 있을 때 — 타입별 기본 처리** (사용자 지시가 있으면 그것이 최우선):

- **살아있는 문서** (PRD·STRATEGY·PLAN·RESEARCH·ANALYSIS·GUIDE·DOCUMENTATION): 새 파일을 만들지 않고 **기존 문서를 갱신**한다. 문서가 곧 현재 상태다. 특히 RESEARCH·ANALYSIS는 한 번에 끝나지 않는다 — 내용 확장이나 새 관점의 추가는 기존 문서에 섹션을 더하는 방식으로 갱신한다.
- **시점 스냅샷** (REPORT·HANDOFF): 같은 주제라도 **새 파일**을 만든다. 보고·인계는 시점 기록이 가치이므로 갱신으로 덮지 않는다. 이전 문서가 유효성을 잃으면 `status: superseded` 처리(§9).
- **불변 기록** (ADR): 승인(`active`) 후에는 본문을 수정하지 않는다. 결정이 바뀌면 **새 ADR**을 쓰고 기존 ADR을 `superseded` 처리한다. 제안이 채택되지 않으면 `status: rejected` 처리하고 기각 사유를 본문에 남긴다.

### 5. Persona 채택

문서 타입에 지정된 Persona를 작성 관점으로 채택한다:

- Persona의 **톤, 관점, 핵심 질문**을 따른다
- Persona의 타입별 **핵심 커버리지**를 작성 기준으로 삼는다
- NOTE 타입은 Persona 없이 자유형으로 작성

상세 Persona 정의 및 타입별 핵심 커버리지: [references/personas.md](references/personas.md)

### 6. 프론트매터 작성

모든 문서는 본문 최상단에 YAML 프론트매터를 포함한다. 형식:

```yaml
---
type: adr
audience: 코어 엔진 개발자 · 아키텍처 결정권자
related_docs:
  - docs/STRATEGY-AGENT-STUDIO-CORE-ENGINE-2026-06-29-2152.md (3사상 — 이 결정이 지켜야 할 계약)
  - core/compiler/compile.py (구현 지점)
  - CLAUDE.md (루트 §4 확장 사다리)
created: 2026-06-30 14:30
updated: 2026-07-10
status: active
description: "먼저 결론 한 문장(무엇을 결정·판정했는가). 그다음 배경과 개요 1~2문장."
revisions:
  - v1.3 (07-10) 컴파일 단계에서 매크로 lowering 분리 · 계약 표 2행 교체
  - v1.2 (07-04) 기각안 B를 [참고]로 이동 · 근거 링크 3건 보강
  - v1.1 이하 (06-30~07-02) 초안 확정 — 상세는 `git show a1b2c3d:<이 파일>`
open_issues:
  - 매크로 확장 순서를 컴파일 전후 어디에 둘지 미정 — 벤치 결과 나오면 확정
  - 계약 표 3행의 타입명이 구현과 불일치 — 구현 쪽 리네이밍 대기
---
```

**필드 정의:**

| 필드 | 필수 | 설명 |
|------|------|------|
| `type` | 필수 | 문서 타입(소문자): `adr`, `prd`, `strategy`, `plan`, `research`, `report`, `guide`, `analysis`, `handoff`, `note`, `documentation`. **아카이브는 타입이 아니다** — `status` 로 표시한다 |
| `audience` | 필수 | 주 독자층. 협업 문서는 `사용자·Claude`, 전달 문서는 **최종 외부 독자층**(전달 대상 — 지금 읽는 사람이 아니라) (메모는 생략 가능) |
| `related_docs` | 선택 | 관련 문서·코드 경로. 각 항목 뒤 괄호로 관계를 주석. 없으면 필드 생략 |
| `created` | 필수 | 최초 작성 시각 `YYYY-MM-DD HH:MM`. **`date` 명령으로 확인**(파일명 타임스탬프와 동일) |
| `updated` | 선택 | 최종 수정일 `YYYY-MM-DD`. 기존 문서 갱신 시에만 추가 |
| `status` | 필수 | 문서 상태: `draft` / `active` / `superseded` / `rejected` / `archived` |
| `description` | 필수 | 결론 한 문장을 먼저, 이어서 배경·개요 1~2문장. 따옴표로 감쌈 |
| `revisions` | 선택 | 회차별 변경 요지 로그. 한 항목 = 한 회차, 최신이 맨 위. 한 항목은 두 줄 이내. 어느 문서에 둘지는 프로젝트 지침을 따른다 |
| `open_issues` | 선택 | 아직 정해지지 않았거나 처리를 기다리는 사항. 한 항목에 무엇이 막혀 있는지와 무엇이 있으면 풀리는지를 함께 적는다. 해소되면 그 항목을 지우고, 비면 필드째 지운다 |

- `related_docs`는 **포인터**일 뿐이다. 본문이 의존하는 핵심 내용은 여전히 본문에 인라인한다(writing-principles §6 Self-Contained).
- `description`은 "결론 먼저" 원칙을 따른다 — 독자가 첫 줄에서 문서의 결론을 파악할 수 있어야 한다.
- **`revisions` 는 로그 층이고 `description` 은 상태 층이다.** 회차마다 갱신되는 문서에는 성격이 반대인 둘이 섞이는데(→ [수치와 상태](#수치와-상태--오래-사는-문서의-규율-모든-타입-공통) 세 번째 항목), 로그를 받을 필드가 없으면 갈 곳 잃은 개정 경위가 `description` 으로 흘러들어 결론 한 문장을 덮는다. `revisions` 는 그 로그의 자리다.
  - **담는 것은 "무엇이 바뀌었나"뿐이다** — 절·항목·수치 단위로 적는다. 판단 근거·시행착오·재사용 절차는 로그가 아니라 지식이라 회차와 함께 늙지 않으므로 본문이나 별도 필드에 둔다. 한 항목이 두 줄을 넘으면 대개 로그가 아닌 것이 섞인 신호다.
  - **지난 항목은 고치지 않는다.** 아카이브 본문을 손대지 않는 원리(§9)를 살아 있는 문서로 확장한 것으로, 그때 그렇게 바꿨다는 사실이 이 필드의 가치다.
  - **오래된 회차는 묶어 압축한다.** 최근 몇 개만 개별 항목으로 두고 그 이전은 한 줄로 합치되, 상세를 되찾을 포인터(커밋 해시·원본 경로)를 그 줄에 남긴다. 압축은 삭제가 아니라 포인터로 바꾸는 일이다.
- **`open_issues` 는 지워지는 층이다.** `revisions` 가 고치지 않는 사료라면 `open_issues` 는 해소되는 순간 사라져야 하는 미결이다. 성격이 반대인 둘을 한 필드에 두면 이미 처리된 사항이 이력에 섞여 계속 남고, 다음 독자는 그것을 아직 열린 문제로 읽는다.
  - **항목마다 해소 조건을 함께 적는다** — "무엇이 막혀 있는가"만 적으면 언제 지워도 되는지 아무도 판정할 수 없다. 판단 대기라면 누구의 판단인지, 외부 사정 대기라면 무엇이 끝나야 하는지까지 적는다.
  - **비면 필드째 지운다.** 빈 목록을 남겨 두면 미결이 없다는 사실과 아직 확인하지 않았다는 사실이 같은 모습으로 보인다.
- **NOTE**(개인 메모)는 프론트매터를 생략할 수 있다 — 필요 시 `type`·`created`만 둔다.
- **`status` 는 문서의 수명 상태**다: `draft`(작성 중) → `active`(유효) → `superseded`(후속 문서로 대체됨) / `archived`(역할이 끝나 보관됨). 제안이 채택되지 않으면 `draft` → `rejected`(기각 — 주로 ADR, 기각 사유는 본문에 기록).
- **프론트매터와 본문은 독자가 다르다.** 프론트매터는 기계·에이전트가 읽는 메타 층이고, 본문은 사람이 읽는 층이다. 본문을 잘라 회의 자료·외부 전달본으로 옮겨도 프론트매터는 저장소에 남아 **출처와 계보를 보존한다.**
- **따라서 본문 자립(§8-3)과 `related_docs` 유지는 상충하지 않는다.** 오히려 본문에서 외부 참조를 걷어낸 문서일수록 프론트매터가 **유일한 연결 고리**이므로 반드시 남긴다. 본문이 참조하지 않는 관계라면 그 사정을 괄호 주석에 적어 둔다(예: "본문은 자립을 위해 참조하지 않는다 — 원 기록이 필요하면 여기서 찾는다").

### 7. 페르소나 기반 작성

고정 템플릿을 강제하지 않는다. 채택한 Persona의 관점과 **핵심 커버리지**를 기준으로, 프로젝트 특성·규모·상황에 맞게 구조를 그때그때 구성한다:

- Persona의 "핵심 커버리지"를 기준으로 삼되, 고정 순서가 아니라 취사선택·재배열한다.
- 불필요한 요소는 생략하고, 상황이 요구하면 목록에 없는 요소를 추가한다.
- 사용자가 특정 구조를 요청하면 그것을 최우선한다.
- 작성 시 공통 품질 원칙(독자 중심, 명확성, 근거와 예시, 점진적 구조, 훑어읽기, 자립성)을 적용한다.
- **배치를 주장하는 자리는 도식으로 그린다**(writing-principles §8) — 무엇이 어디에 속하는가(구조·계층), 무엇이 어디로 옮겨가는가(흐름·분기·상태 전이), 이전과 이후가 어떻게 다른가. 셋 중 하나면 설명하지 말고 ASCII 도식을 넣고, 배치 주장이 아닌 곳에는 넣지 않는다. 형태별 골격은 [references/ascii-diagrams.md](references/ascii-diagrams.md).
- 한국어로 쓰는 모든 문서에 한국어 문장 스타일(writing-principles §7)을 적용한다 — 평서형 `~다` 종결, 존댓말 금지, 괄호 병기 여섯 용법(§7.8), 판정 우선 서술(§7.9), 개념 도입 문장(§7.10), 동작 주체와 효과 문장(§7.11), 표 셀의 문장 형태(§7.12). **전달 문서**(REPORT·DOCUMENTATION·GUIDE)는 여기에 더해 독자 중심으로 쓰고, 작성 시점부터 §8 전달 준비 점검을 준수한다.

상세 Persona 정의 및 타입별 핵심 커버리지: [references/personas.md](references/personas.md)
공통 작성 및 품질 원칙: [references/writing-principles.md](references/writing-principles.md)

### 8. 전달 준비 점검 (전달 문서 전용)

전달 문서(REPORT·DOCUMENTATION·GUIDE)의 완성 기준은 **"지금 그대로 외부에 전달해도 되는 상태"**다. 작성 시점부터 아래를 준수하고, 사용자가 실제 전달 의사를 밝히면(예: "이 가이드 팀에 공유할 거야") 문서 전체를 이 기준으로 재점검한다:

1. **경로 누출 금지** — 본문·`related_docs`에 개인 절대경로(`/Users/...`)나 수신자가 접근할 수 없는 로컬 경로를 넣지 않는다. 저장소 상대 경로 또는 URL만 사용한다.
2. **용어 자립** — 전문 용어·약어는 첫 등장 시 풀어 설명한다. 최종 독자가 비전문가일 수 있음을 전제한다.
3. **문서 자립** — 이 문서만 읽고 이해·실행이 가능해야 한다(writing-principles §6). 프로젝트 내부 맥락(다른 문서·세션 대화·CLAUDE.md 내용)을 알아야 이해되는 서술을 남기지 않는다. **이 요구는 본문에만 적용된다** — `related_docs` 는 비우지 않는다(§6 마지막 두 항목).
4. **근거 내장** — 수치·버전·날짜는 본문 안에 출처나 확인 방법을 함께 적는다. 독자가 사실 여부를 되물어 오면 그것이 곧 반복 수정의 시작이다.

협업 문서에는 이 점검을 강제하지 않는다 — 단 **1번(개인 절대경로 금지)과 4번(근거 내장)은 모든 문서에 적용**한다. 전자는 저장소가 다른 환경으로 이동해도 링크가 살아야 하기 때문이고, 후자는 출처 없는 수치가 시간이 지나면 조용히 거짓이 되기 때문이다(→ [수치와 상태](#수치와-상태--오래-사는-문서의-규율-모든-타입-공통)).

### 9. 아카이브 처리 (수명이 끝난 문서)

역할이 끝난 문서를 지우지 않고 보관하는 절차. **새 문서를 쓰는 일이 아니므로 타입·Persona·네이밍 규칙과 무관하다.**

- **타입과 파일명은 그대로 둔다.** `PRD-...md` 는 아카이브돼도 여전히 `type: prd` 인 `PRD-...md` 다. 아카이브는 **타입이 아니라 상태**이므로 이름을 바꾸지 않는다(바꾸면 기존 `related_docs` 링크가 전부 깨진다).
- **프론트매터 2개 필드만 손댄다**: `status: archived`(또는 후속 문서가 대체한 경우 `superseded`), `updated: {오늘 — `date` 로 확인}`.
- **파일을 아카이브 폴더로 옮긴다**: 문서가 있던 자리 기준으로 `_docs/_archive/`(정식 결과물이면 `docs/_archive/`). 프로젝트에 다른 규약이 있으면 그것을 따른다. `git mv` 로 이력을 보존한다.
- **본문은 건드리지 않는다.** 요약·윤문·수치 갱신 금지 — 당시 값이 지금과 달라도 그대로 둔다. 아카이브의 가치는 **그때 그렇게 적혔다는 사실**이다.
- **대체 관계가 있으면 밝힌다**: `superseded` 로 내릴 때는 `related_docs` 에 후속 문서를 추가하고 괄호로 `(이 문서를 대체)` 를 붙인다.
- **문서 인덱스를 갱신한다**: 프로젝트에 문서 인덱스(예: `CLAUDE.md` 문서 표)가 있으면 경로와 상태 표시를 함께 고친다 — 안 고치면 인덱스가 즉시 거짓말이 된다.

## 수치와 상태 — 오래 사는 문서의 규율 (모든 타입 공통)

문서는 쓰인 순간 정확해도 **그 뒤 코드가 움직이면 조용히 거짓이 된다.** 아래 셋은 그 노후화를 문장이 아니라 설계로 막는 규율이며, 협업·전달 문서를 가리지 않는다.

- **측정값에는 시점 또는 재는 방법을 붙인다.** `serve.py 42줄` 이 아니라 `serve.py 42줄(2026-08-01 실측)` 또는 아예 `wc -l devgui/serve.py`. 둘 다 없으면 그 수치는 적지 않는다 — 시점 없는 측정값은 **틀렸다는 사실 자체가 관측되지 않는다.** 반대로 날짜와 델타를 달고 적힌 값(`390 → 393 passed`)은 과거로 읽히므로 썩지 않는다. **차이는 값의 정확성이 아니라 독자가 언제 값인지 알 수 있는가**다.
- **파생값을 저장하지 않는다.** 합계·건수·분류처럼 다른 표에서 세면 나오는 값은 원본의 복사본이다. 원본이 바뀌면 반드시 갈라지므로, 적어야 하면 세는 근거를 함께 적는다(예: "현황 표 기준"). **프론트매터 `description` 의 집계 수치가 가장 먼저 썩는다** — 본문을 고칠 때 아무도 프론트매터를 다시 세지 않는다.
- **누적 문서는 로그 줄과 상태 줄을 가른다.** `status: active` 이면서 회차마다 갱신되는 문서에는 성격이 반대인 둘이 섞인다. 회차 기록은 **사료라 고치지 않고**(§9 의 원리를 살아 있는 문서로 확장), 현재 상태는 **한 곳에만 두고 나머지는 그리로 참조한다.** 같은 사실을 표와 본문 두 곳에 실값으로 두면 쓰는 시점이 다르므로(발견 시 ↔ 처리 시) 갱신은 반드시 한쪽만 된다.

> **한 문장으로**: 복사본은 조용히 썩고 포인터는 따라가면 고쳐진다. 값을 적기 전에 **"6개월 뒤 독자가 이걸 어떻게 다시 확인하나"** 를 먼저 답한다.

## 규칙

1. **타임스탬프**: 항상 `date` 명령 실행. 절대 추측하지 않는다.
2. **대소문자**: 파일명 PREFIX와 DESCRIPTION은 전부 대문자.
3. **하이픈**: 공백 대신 하이픈 사용.
4. **경로 확인**: 파일 생성 전 상위 디렉토리 존재 확인.
5. **Persona 충실**: 지정된 Persona의 관점을 일관되게 유지.
6. **핵심 커버리지**: 고정 템플릿 대신 Persona의 핵심 커버리지를 기준으로 필요한 요소를 다룬다.
7. **프론트매터**: 모든 문서 최상단에 YAML 프론트매터를 포함한다. `created`는 `date`로 확인한다.
8. **품질 원칙**: 공통 작성 및 품질 원칙을 적용한다.
9. **내용 우선**: 구조는 가이드일 뿐, 실질적 내용이 더 중요하며 프로젝트 상황에 맞게 구조를 조정한다.
10. **전달 준비**: 전달 문서(REPORT·DOCUMENTATION·GUIDE)는 §8 점검을 작성 시점부터 적용한다. 개인 절대경로 금지와 근거 내장은 모든 문서에 적용한다.
11. **수치 내구성**: 측정값에는 시점 또는 재는 명령을 붙이고, 파생값(합계·건수·분류)은 저장하지 않으며, 누적 문서는 로그와 상태를 가른다(§수치와 상태).
12. **서술 구체성**: 결과·평가·수량·상태를 뭉뚱그리지 않는다 — 독자가 확인하러 갈 대상을 지목할 수 있게 쓴다(writing-principles §2.1). 등급어(매우 낮음·훨씬 강력)는 근거 괄호와 함께만 쓴다.
13. **문체·병기**: 한국어 문서는 평서형 `~다`로 맺고 존댓말을 쓰지 않는다. 첫 등장 시 병기 방향은 개념이 `한글(원어)`, 약어가 `약어(풀이)`다(writing-principles §7.1·§7.8). 문서군에 관계없이 적용하되 **소급 적용하지 않는다**.
14. **도식화**: 배치 주장(소속·이동·전후)은 설명하지 말고 ASCII 도식으로 그린다. 형태 없는 내용에 도식을 씌우지 않고, 산문 안 화살표 체인으로 도식을 대신하지 않는다. 저장 전에 배치 주장을 훑어 빠진 도식과 장식 도식을 가른다(writing-principles §8, 골격은 references/ascii-diagrams.md).
15. **문장 형태**: 개념은 완결 정의 한 문장으로 열고, 기능 앞에 그 기능이 없을 때의 문제를 한 문장 둔다. 동작에는 주체(에이전트·스크립트·사람)를 적고, 구조 설명 뒤에는 그 구조가 막는 실패를 한 문장으로 닫는다. 표 셀은 종결어미 없는 명사구로 쓰고 같은 열의 형태를 맞춘다(writing-principles §7.10~§7.12).
