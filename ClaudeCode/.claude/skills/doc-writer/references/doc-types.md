# Document Types

문서 타입별 규격. 작성 시 해당 타입의 **독자·핵심 질문·관점**을 작성 관점으로 채택하고, **핵심 커버리지**를 작성 기준으로 삼는다.

이 파일이 **타입별 사실의 단일 SoT**다 — 독자·핵심 질문·관점·톤·강조·피할 것·작성 원칙·핵심 커버리지·경계 판정이 전부 여기 한 곳에 있다. `writing-principles.md` 는 타입을 가리지 않는 문장·구조 규칙만 담고, `SKILL.md` 는 절차와 문서군 정의를 담는다.

---

## 공통 작성 원칙

- 객관적이며 중립적인 관점으로 작성
- 너 자신의 의견, 전망, 판단, 예상 등을 최소화
- **고정 템플릿 없음**: 각 타입의 "핵심 커버리지"는 강제 섹션 목록이 아니라, 해당 타입이 통상 다뤄야 하는 요소다. 프로젝트 특성·규모·상황에 맞게 취사선택하고 순서·제목·깊이를 유연하게 조정한다.
- 불필요한 요소는 생략하고, 상황이 요구하면 목록에 없는 요소를 추가한다. 사용자가 특정 구조를 요청하면 그것을 최우선한다.
- **독자 행은 협업 문서에만 둔다**(문서군 정의는 SKILL.md §1). 협업 문서에서 독자는 실제 수신자가 아니라 **누구의 관심사를 다룰 것인가를 정하는 렌즈**이고, 실제로 읽는 것은 사용자와 이후 세션의 Claude다. **이해 문서는 독자가 늘 사용자**라 그 행이 정보를 담지 않으므로 두지 않는다 — 무엇을 얼마나 깊이 쓸지는 그 자리 대신 **핵심 질문**이 정한다.
- **협업 문서는 두 독자를 동시에 만족시킨다** — 사용자가 읽고 이해할 수 있어야 하고, 다음 세션의 Claude가 이 문서만 읽고 실행 컨텍스트를 복원할 수 있어야 한다. 앞은 목차·흐름·어휘가 맡고 뒤는 좌표와 연결이 맡는다. 하나만 만족하면 사람은 읽고도 무엇을 승인하는지 모르거나, Claude는 읽고도 어디를 건드릴지 모른다. **HANDOFF는 예외다** — 다음 세션의 Claude가 1차 독자인 시점 스냅샷이라 압축을 우선한다.
- **협업 문서에는 실행 좌표를 붙인다** — 요구사항·단계·결정을 저장소의 실제 지점(파일 경로·심볼·명령·설정 키)과 잇는다. 아직 없는 것을 다루는 문서라면 **생길 자리**를 적는다. 좌표가 없으면 다음 세션은 그 지점을 다시 찾는 데서 시작하고, 사용자는 그 일이 얼마나 큰일인지 가늠할 수 없다.
- **협업 문서는 선행 문서를 본문 첫 절에서 한 줄로 잇는다** — 어느 RESEARCH·STRATEGY·ANALYSIS의 어느 결론에서 나왔는지. 프론트매터 `related_docs` 는 기계가 따라가는 포인터이고, 본문 한 줄은 사람과 Claude가 이해를 잇는 자리다. 선행 문서가 없으면 무엇을 근거로 삼았는지를 대신 적는다.
- **이해 문서는 이해 준비 점검 여섯 항목으로 마감한다**(SKILL.md §8). 특히 **결론 우선**(결론이 첫 화면에)과 **확실성 표시**(확인·추정·미확인 구분)는 타입별 커버리지와 별개로 항상 걸린다.
- **커버리지의 추천·권장 사항·다음 단계는 첨언이다** — 대상을 세운 뒤에 붙이며, 문서의 중심이 아니다. 무엇을 할지는 사용자가 여러 문서를 종합해 정한다(SKILL.md §1).
- **이해 문서의 목차는 수행 순서가 아니라 이해가 쌓이는 순서로 잡는다.** 조사·분석·실행을 한 순서와 독자가 대상을 파악하는 순서는 다르다. 도구·검색 경로·재현 절차처럼 **다시 하기 위한 정보**는 뒤로 내리고, 대상이 무엇인지부터 세운다. 이 순서의 본보기는 DOCUMENTATION이다 — 무엇인가 → 어떻게 나뉘는가 → 어떻게 흐르는가.
- **발견·지적·수치에는 대상의 좌표를 붙인다** — 어느 구성 요소, 어느 흐름 단계, 어느 파일의 일인지. 좌표가 없으면 독자는 앞 절로 되돌아가 스스로 맞춰 봐야 하고, 그 되돌아감이 곧 이해가 끊기는 지점이다.
- **문체는 문서군을 가리지 않는다** — 평서형 `~다` 종결·괄호 병기는 협업·이해 문서에 똑같이 적용된다(writing-principles §7). 달라지는 것은 독자 중심 서술과 자립성 요구의 강도다.

## PRD — 제품 요구사항 (협업)

| 항목 | 정의 |
|------|------|
| **독자** | 사용자 · 이후 세션의 Claude |
| **핵심 질문** | "무엇을 왜 만들며, 무엇이 되면 성공인가?" |
| **관점** | 무엇을 왜 만드는가 → 무엇이 되면 성공인가 → 지금 무엇이 있는가 → 무엇을 만드는가. 문제를 세운 뒤라야 요구사항이 근거를 갖는다 |
| **톤** | 목적 중심, 판정 가능한 지표, 명확하고 간결 |
| **강조** | 해결하려는 문제, 정량 성공 지표, 최종 이용자가 얻는 것, 우선순위, 요구사항이 닿는 지점 |
| **피할 것** | 구현 방식 지정(→ PLAN의 몫), 요구 대신 구현을 적는 서술, 솔루션 선도(문제 정의가 먼저), 닿는 지점 없는 요구사항 |

**작성 원칙:**

- 문제를 먼저 정의하고, 솔루션은 그 다음
- 정량적 성공 지표를 반드시 포함
- 목적을 앞세워 첫 화면에서 "왜/무엇"이 파악되게 한다 — 사용자와 다음 세션의 Claude가 나중에 재확인하는 용도다.
- **`사용자`가 누구인지 구분해 쓴다** — 이 스킬에서 `사용자`는 이 문서를 읽는 본인이다. 제품을 쓰는 쪽을 뜻할 때는 `최종 이용자`·`응시자`·`실무자`처럼 그 대상을 직접 부른다. 한 문서에서 같은 낱말이 두 대상을 가리키면 요구사항의 주어가 흔들린다.
- **요구사항마다 닿는 지점을 적는다** — 이미 있는 것을 고치는 요구인지 새로 만드는 요구인지, 어느 모듈·화면·API에 붙는지. 없으면 Claude는 착수 지점을 다시 찾아야 하고, 사용자는 이 요구가 얼마나 큰일인지 가늠할 수 없다.
- **검사 tell**: 요구사항 하나를 골라 지금 어느 파일을 열어야 하는지(또는 어디에 새로 생기는지) 짚을 수 없으면 닿는 지점이 빠진 것이다.

**핵심 커버리지:**

- 배경·문제 정의(선행 문서가 있으면 첫 줄에 연결) → 목표·성공 지표(정량) → **지금 무엇이 있는가**(이 요구가 닿는 기존 기능·모듈, 없으면 새로 생길 자리) → 요구사항(Must-have / Nice-to-have, **각 항목에 닿는 지점**). 필요 시 최종 이용자 시나리오(`As a… I want… So that…` 형식은 선택), 비기능 요구사항·제약·의존성·타임라인.

## PLAN — 구현·실행 계획 (협업)

| 항목 | 정의 |
|------|------|
| **독자** | 사용자(승인·감시) · 이후 세션의 Claude(실행) |
| **핵심 질문** | "무엇을 어떤 순서로 만들고, 무엇으로 완료를 판정하는가?" |
| **관점** | 지금 무엇이 어떤 상태인가 → 무엇을 고치려는가 → 무엇이 되면 끝인가 → 어떤 순서로 하는가. 각 단계는 판정 가능한 상태로 끝남 |
| **톤** | 실행 명세 수준. 값·이름·경로를 지목하고, 판정은 돌려 볼 수 있게 |
| **강조** | 이 계획이 딛고 선 선행 문서, 완료 조건, 각 단계가 건드리는 지점, **새로 만드는 것의 계약과 데이터 구조**, 실행 가능한 검증 명령, 범위 경계, 승인이 필요한 결정 지점 |
| **피할 것** | **값 자리에 값이 없는 서술**("기본값을 적용한다"), 파일명만 있고 계약이 없는 신설 항목, 서술로만 적힌 검증 기준, 선행 근거 없이 시작하는 계획, 경계 없는 단계 나열, 결정을 미룬 채 진행하는 설계 |

**작성 원칙:**

- **어느 문서의 어느 결론에서 나온 계획인지 첫 절에 한 줄로 적는다** — 계획만 남으면 다음 세션은 이 순서가 왜 이 순서인지 모른 채 실행하고, 사용자는 무엇을 승인하는지 모른 채 승인한다.
- 현황을 세운 뒤 이 계획이 고치려는 것을 적고, 그다음 완료선(무엇이 되면 끝인가)을 정의한다.
- 각 단계에 `→ verify:` 로 통과 판정 기준을 붙인다. 실행 없이 판정할 수 없는 문구는 검증 기준이 아니다.
- **각 단계에 건드리는 지점을 적는다** — 파일 경로·심볼·설정 키. `→ verify:` 가 완료를 판정한다면 이 항목은 착수 지점을 정한다.
- **값이 필요한 자리에 값을 적는다.** "기본 계수를 적용한다"·"적절한 타임아웃을 둔다"는 명세가 아니라 의도다. 실행하는 쪽은 값을 지어내고, 그 값은 문서와 어긋난 채 코드에 남는다. 아직 정하지 못한 값은 비워 두지 말고 **승인이 필요한 선택지**로 올린다.
- **새로 만드는 것에는 계약을 적는다** — 스크립트·모듈·엔드포인트를 신설하는 단계는 파일명만으로 부족하다. 입력(인자·표준입력·읽는 파일), 출력(표준출력·쓰는 파일의 경로), 종료 코드, 실패 시 동작을 적는다. 없으면 다음 세션이 인터페이스를 지어내고, 뒤 단계가 그것과 어긋난 전제로 쓰인다.
- **데이터 구조는 예시가 아니라 명세로 적는다** — JSON·스키마를 바꾸는 단계는 예시 한 덩어리로 끝내지 않고 필드마다 타입·필수 여부·기본값·명명 규칙을 적는다. 예시는 그 명세를 읽은 뒤 확인하는 용도다.
- **`→ verify:` 는 붙여 넣어 돌릴 수 있는 명령으로 적는다** — 판정 기준 서술은 명령 뒤에 기대 결과로 둔다. 명령이 없으면 검증할 때마다 명령을 다시 조립해야 하고, 조립이 달라지면 판정도 달라진다. 실행할 수 없는 검증(사람의 눈 확인·외부 회신)은 그렇다고 밝힌다.
- **본 계획 범위 밖**을 절로 분리한다 — 경계를 적지 않으면 실행 중 인접 작업이 계속 딸려 들어온다.
- 사용자 결정이 필요한 지점은 **승인이 필요한 선택지**로 한곳에 모은다. 계획 안에 흩어 두면 어느 것이 결정 대기인지 실행 시점에 드러나지 않는다.
- **검사 tell**: 각 단계의 `verify:` 를 읽고 통과·실패를 스스로 판정할 수 없으면 검증 기준이 아니라 다짐이다.
- **검사 tell**: 단계 하나를 골라 그 절만 읽고 코드를 쓸 때, 지어내야 하는 값·이름·경로가 하나라도 있으면 그 단계는 명세가 아니라 의도다.

**핵심 커버리지:**

- **현황·전제**(지금 무엇이 어떤 상태이며 이 계획이 딛고 선 선행 문서는 무엇인가) → 이 계획이 고치려는 것 → 완료선 → 구현 전략(접근·아키텍처 결정) → **단계별 실행**. 필요 시 본 계획 범위 밖, 산출물, 리스크·대응, 선행 의존성, 승인이 필요한 선택지.

각 단계는 아래 넷으로 적는다. 셋째가 실행 명세의 자리이며, 그 단계가 무엇을 신설하느냐에 따라 하위 항목을 취사선택한다.

```
1. 이 단계가 끝나면 무엇이 성립하는가   저장소의 상태로 적는다. 필요성 설명은
                                        구현 전략에 있으므로 여기서 반복하지 않는다
2. 건드리는 지점                        파일 경로 · 심볼 · 설정 키 · 행 번호
3. 변경 명세                            · 계약 — 입력(인자·stdin·읽는 파일) /
                                          출력(stdout·쓰는 파일 경로) / 종료 코드
                                        · 데이터 구조 — 필드 · 타입 · 필수 여부 ·
                                          기본값 · 명명 규칙
                                        · 실패 시 동작 — 경계 입력 · 폴백 · 중단 조건
                                        · 확정된 값 — 계수 · 임계치 · 타임아웃
4. → verify:                            돌릴 수 있는 명령 + 기대 결과
```

## ADR — 아키텍처 결정 기록 (협업)

승인(`active`) 후 본문을 수정하지 않는 불변 기록. 결정이 바뀌면 새 ADR을 쓴다(SKILL.md §4).

| 항목 | 정의 |
|------|------|
| **독자** | 사용자 · 이후 세션의 Claude |
| **핵심 질문** | "왜 이 결정이며, 대안 대비 어떤 이점이 있는가?" |
| **관점** | 무엇에 막혀 있었는가 → 무엇을 골랐는가 → 어디서 지켜지는가 → 무엇이 뒤따르는가. 제약을 이해한 뒤라야 결정이 납득된다 |
| **톤** | 구조적, 장기 관점, 결정 중심 |
| **강조** | 결정을 강제한 제약, 고려된 대안, 트레이드오프, 이 결정이 지켜지는 지점, 장기 영향 |
| **피할 것** | 맥락 없는 결정, 대안 미검토, 지켜지는 자리를 밝히지 않은 결정, 되돌릴 수 없는 결정의 경량 처리 |

**작성 원칙:**

- 결정의 맥락(제약, 요구사항, 팀 상황)을 충분히 서술
- 검토한 대안과 기각 사유를 명시
- **이 결정이 어디서 지켜지는지 적는다** — 어느 모듈·설정·규약·리뷰 절차에서. 결정이 값을 정한 것이면(타임아웃·재시도 횟수·버전 하한) 그 값을 본문에 적는다. 결정만 적고 적용 지점을 적지 않으면 다음 세션은 그 결정을 읽고도 어디서 지켜야 하는지 몰라 그대로 어긴다.
- 결정의 긍정적/부정적 결과를 모두 기록
- **검사 tell**: 이 ADR을 읽고 지금 어느 파일을 열어야 하는지 짚을 수 없으면 적용 지점이 빠진 것이다.

**핵심 커버리지:**

- 맥락(제약·요구사항 — 선행 문서가 있으면 첫 줄에 연결) → 검토한 대안(기각 사유 포함) → 결정·근거 → **적용 지점**(이 결정이 지켜지는 코드·설정·규약의 자리) → 결과(긍정적 / 부정적 / 중립적). 결정 상태는 별도 본문 항목 대신 **프론트매터 `status`로 표현**한다 — 제안=`draft`, 승인=`active`, 후속 ADR로 대체=`superseded`(related_docs에 후속 ADR 명시), 기각=`rejected`(기각 사유는 본문에 기록).

## HANDOFF — 세션 인계 (협업)

현재 세션의 작업 맥락을 **다음 세션의 Claude**가 그대로 이어받아 재개하도록 넘기는 문서. 세션 대화 전체를 분석해 작성한다.

| 항목 | 정의 |
|------|------|
| **독자** | 다음 세션의 Claude |
| **핵심 질문** | "이 세션이 멈춘 지점에서 그대로 재개할 수 있는가?" |
| **관점** | 어디까지 왔나 → 지금 무엇을 해야 하나 → 무엇을 알고 있어야 하나 |
| **톤** | 압축적, 구체적, 즉시 실행 가능 |
| **강조** | 정확한 다음 액션, 결정과 그 이유, 실패한 시도, 변경 파일, 환경 상태 |
| **피할 것** | 배경 설명 나열, 경로·함수명 없는 추상 서술, auto memory 내용 재서술 |

**작성 원칙:**

- **즉시 실행 가능**: 다음 세션이 읽고 바로 작업을 재개할 수 있어야 한다 — 실제 파일 경로·함수명·명령어로 구체적으로 쓴다.
- **What보다 Why**: 결정과 파일 변경에는 그렇게 한 이유를 반드시 붙인다.
- **실패도 기록**: 막다른 길이 같은 실수의 반복을 막는다.
- **메모리와 중복 금지**: auto memory에 이미 저장된 내용은 재서술하지 않고 참조만 한다.
- **900단어 이내, 긴급한 것부터**: 배경 설명은 생략하고 우선순위 순으로 압축한다.
- **말미에 대기 지시**: "구현을 시작하지 말고 명시적 지시를 기다릴 것" 경고로 마무리한다 — 다음 세션이 인계 문서만 읽고 멋대로 착수하는 것을 막는다.

**핵심 커버리지** (이번 세션에 해당 내용이 있는 항목만 포함):

- 세션 요약(주제 + 핵심 성과 2~3문장) → **즉시 다음 단계**(진행 중이던 작업과 정확한 다음 액션) → 핵심 결정·근거(어떤 선택을 왜 했는지, 발견된 사용자 선호 포함) → 막다른 길·교훈(실패한 시도와 원인, 트러블슈팅 중 찾은 우회로 — 실패가 없으면 생략) → 변경 파일(경로 + 무엇을 왜 바꿨는지) → 환경 상태(브랜치·미커밋 변경·venv/설정 — 특이사항 없으면 생략) → 현재 상태(완료 / 진행 중 / 남음) → 주의 사항(블로커·의존성·경고, auto memory 갱신 여부).

## RESEARCH — 외부 대상 조사 (이해)

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "이 영역에 무엇이 있고, 각각은 무엇을 주고 무엇을 요구하는가?" |
| **관점** | 이 영역이 어떻게 생겼는가 → 각 선택지가 무엇인가 → 무엇이 이들을 가르는가. 옵션을 견주기 전에 옵션이 놓인 판을 먼저 세운다 |
| **톤** | 탐구적, 중립적, 비교 분석 중심 |
| **강조** | 선택지가 놓인 판, 각 선택지의 실체(무엇을 하는 물건인가), 비교 축과 그 축을 고른 이유, 출처 명시, 확인한 것과 못 본 것의 구분 |
| **피할 것** | 실체 설명 없이 시작하는 장단점 목록, 조사 절차를 앞세운 목차, 단일 관점 편향, 출처 없는 주장, 성급한 결론 |

**작성 원칙:**

- **견주기 전에 각 선택지가 무엇인지 세운다** — 이름과 장단점만 나열하면 독자는 비교표를 읽고도 무엇과 무엇을 견준 것인지 모른다. 한 문단이면 되지만 그 문단이 없으면 뒤가 전부 공중에 뜬다.
- **비교 축을 밝히고 왜 그 축인지 적는다** — 축이 결론을 결정한다. 축의 근거가 없으면 독자는 결론을 검증할 길이 없어 통째로 받아들이거나 통째로 의심하게 된다.
- **범위는 앞에, 방법은 뒤에 둔다** — 어디까지 보았는가는 결론을 어디까지 믿을지를 정하므로 앞이지만, 어떤 도구로 어떻게 찾았는가는 다시 조사할 때 필요한 정보라 이해의 순서에서는 뒤다.
- 옵션별 장단점을 공정하게 비교
- 추천은 마지막 한 절로 붙인다 — 이해를 세운 뒤의 첨언이며, 이 절이 커져 실체 서술을 밀어내면 무게중심이 옮겨간 것이다.
- **경계 tell**: 결론의 근거가 우리 저장소의 파일 경로·실행 결과이면 이 문서는 RESEARCH가 아니다. 대상이 우리 것이면 ANALYSIS, 직접 돌려 본 기록이면 REPORT다(SKILL.md §1 경계 도식).

**핵심 커버리지:**

- 이 조사가 답하는 것 → **선택지가 놓인 판**(이 영역이 어떤 문제를 다루고 무엇으로 갈리는가) → **선택지별 실체**(각각이 무엇을 하는 물건이며 어떤 전제 위에 서는가) → **비교**(축과 축을 고른 이유 + 기준 × 옵션 표) → 확인한 것과 확인하지 못한 것 → **[첨언] 근거 기반 추천**. 필요 시 조사 방법(출처·도구), 참고 자료·출처 링크 — 둘 다 뒤에 둔다.

## STRATEGY — 방향성 정의 (이해)

RESEARCH 이후 · PLAN 이전에 위치하는 방향 문서. 살아있는 문서로 갱신하며 방향 전환 시 `superseded` 처리 후 새로 쓴다.

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "왜 이 방향이며, 대안 대비 어떤 이점이 있는가?" |
| **관점** | 무엇을 이루려는가 → 지금 무엇에 막혀 있는가 → 그래서 어디로 가는가 → 무엇을 포기했는가. 방향은 제약을 이해한 뒤라야 납득된다 |
| **톤** | 구조적, 장기 관점, 결정 중심 |
| **강조** | 목표의 구체적 모습, 방향을 강제한 제약, 기각한 길과 그 대가, 이 방향이 앞으로 묶어 두는 것 |
| **피할 것** | 제약 설명 없이 선언되는 방향, 대안 미검토, 포기한 것을 밝히지 않는 서술, 상세 실행 계획 침범(→ PLAN의 몫) |

**작성 원칙:**

- **제약을 먼저 세운다** — 방향은 제약의 함수다. 무엇에 막혀 있는지를 독자가 그리기 전에 방향을 선언하면, 그 방향은 근거가 아니라 취향으로 읽힌다.
- **기각한 대안은 왜 안 되는지까지 적는다** — 목록만 있으면 독자는 나중에 같은 길을 다시 떠올리고 같은 검토를 반복한다. 기각 사유가 이 방향을 떠받치는 근거의 나머지 절반이다.
- **이 방향이 앞으로 묶어 두는 것을 적는다** — 방향을 고르면 이후 선택지가 좁아진다. 무엇이 닫혔는지 모르면 독자는 이미 닫힌 문을 계속 후보로 둔다.
- 결정의 긍정적/부정적 결과를 모두 기록
- **검사 tell**: 이 문서를 읽고 "그래서 무엇을 포기했나"에 답할 수 없으면 방향이 아니라 희망을 적은 것이다.

**핵심 커버리지:**

- 목표·노스 스타(무엇이 성공인가 — 구체적 모습으로) → **현재 상황·제약**(무엇에 막혀 있는가. 선행 RESEARCH 결론은 요약 인라인) → **방향 결정**(어디로 가는가 + 검토한 대안과 기각 사유) → **포기한 것**(이 방향이 닫아 둔 선택지와 그 대가) → 원칙·가드레일(이후 세션이 방향을 잃지 않도록 지켜야 할 경계) → **[첨언] PLAN 착수 조건**. **상세 실행 계획은 다루지 않는다**(→ PLAN의 몫).

## ANALYSIS — 우리 대상 진단 (이해)

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "이 대상은 지금 어떤 상태이며, 무엇이 그렇게 만들었는가?" |
| **관점** | 대상이 무엇인가 → 지금 어떤 상태인가 → 무엇이 그렇게 만들었는가. 독자가 대상을 그린 뒤라야 발견이 어디에 붙는지 보인다 |
| **톤** | 근거 기반, 객관적, 구조적 |
| **강조** | 대상의 구조와 동작 흐름, 발견이 붙는 지점, 근거의 위치(파일 경로·수치), 원인 규명, 확인하지 않은 영역 |
| **피할 것** | 대상 설명 없이 시작하는 지적 나열, 방법·도구가 대상 서술보다 앞서는 목차, 좌표 없는 발견, 근거 없는 주장, 감정적 표현 |

**작성 원칙:**

- **대상 서술의 깊이는 독자가 발견을 어디에 얹을지 알 만큼이다** — 지적을 방어할 만큼이 아니다. 둘은 다르다: 전자는 대상의 구조와 동작 흐름이 서야 끝나고, 후자는 지적한 자리만 설명하면 끝난다. 후자로 쓰면 독자는 지적 목록은 읽었으나 대상은 여전히 모른다.
- **방법·도구는 앞이 아니라 뒤에 둔다** — 무엇으로 조사했는가는 다시 조사할 때 필요한 정보다. 앞에 두면 독자가 대상을 그리기도 전에 절차부터 읽는다. 앞에 남기는 것은 **어디까지 보았는가**뿐이다.
- 모든 판단에 근거를 명시
- 대안이 있으면 비교표로 정리
- 리스크와 트레이드오프를 숨기지 않음
- 권장 사항에는 우선순위를 붙인다 — 순서 없는 지적 목록은 독자가 다시 정렬해야 한다.
- **검사 tell**: 결과 절의 지적 하나를 골라 대상의 어느 구성 요소·흐름에 관한 것인지 짚을 수 없으면 대상 서술이 부족한 것이다 — 별도 절이든 지적에 붙인 한 줄이든 형태는 무관하다. 반대로 어떤 지적·결론과도 연결되지 않는 대상 서술 단락이 있으면 그 단락은 ANALYSIS가 아니라 DOCUMENTATION의 몫이다.
- **검사 tell**: "이 분석이 답하지 않는 것"을 한 절로 쓸 수 없으면 분석 범위를 아직 정하지 않은 것이다. 범위를 밝히지 않으면 독자는 다루지 않은 영역까지 결론이 미친다고 읽는다.
- **경계 tell**: 결론의 근거가 전부 외부 출처(URL·제품 문서·논문)이면 이 문서는 ANALYSIS가 아니라 RESEARCH다. 특히 "조사 범위와 신뢰도"로 여는 외부 제품 조사는 RESEARCH의 자리다(SKILL.md §1 경계 도식).

**핵심 커버리지:**

- **대상**(무엇을 진단하는가 — 구조·구성 요소·동작 흐름. 독자가 발견을 얹을 바닥이 될 만큼) → **본 범위**(어디까지 보았고 무엇을 안 보았는가) → **발견**(각 발견에 대상의 좌표와 근거를 함께) → **원인**(무엇이 그렇게 만들었는가) → 이 분석이 답하지 않는 것(범위 밖·미검증 영역) → **[첨언] 권장 사항**(우선순위 명시). 필요 시 방법(도구·데이터), 변경 영향도, 기각한 지적과 사유 — 셋 다 뒤에 둔다.

## REPORT — 상태·진행·완료 보고 (이해)

개발 완료 보고·검증 결과 보고·테스트 결과 보고를 하나로 다룬다. 셋 다 "무엇을 했고, 결과가 어떻고, 무엇이 남았나"를 담으므로 상황 차이는 아래 커버리지에서 어느 항목을 상세히 쓰고 어느 항목을 생략하는가로 조정한다.

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "무엇이 어디까지 됐으며, 그 판정을 무엇이 뒷받침하는가?" |
| **관점** | 무엇을 왜 했나 → 무엇이 만들어졌나 → 그것이 어떻게 동작하나 → 어디까지 됐나 → 무엇이 남았나. 만들어진 것이 보여야 판정이 읽힌다 |
| **톤** | 사실 기록 중심, 판정 명시, 재현 가능 |
| **강조** | 만들어진 것의 구조와 한 번의 동작 흐름, 대상·완료 범위 확정, 판정과 근거 경로(로그·산출물·명령), 남은 것 |
| **피할 것** | 만들어진 것을 보여주지 않는 판정, 실행 절차가 결과보다 앞서는 목차, 근거 경로 없는 판정, 범위를 밝히지 않은 완료 선언, 발견 절의 사후 수정 |

**작성 원칙:**

- 무엇을 왜 했는지를 판정보다 먼저 적는다 — 판정만 남으면 다음 세션이 같은 실행을 처음부터 다시 돌린다.
- **"완료"는 요청·계획의 범위 안에서만 성립한다** — 판정하는 것은 산출물의 완결이 아니라 이 PLAN·이 요청이 요구한 것의 충족이다. 무엇을 기준으로 완료라고 하는지(어느 PLAN의 어느 단계, 어느 요청)를 판정과 함께 적고, 그 범위 밖은 "이 보고서가 답하지 않는 것"에 남긴다. 범위 없는 "완료"는 독자가 제품의 완결로 읽는다.
- **만들어진 것의 구조와 동작을 독자가 그릴 수 있을 만큼 적는다** — 판정에 필요한 만큼이 아니다. 무엇이 완성됐는지 보이지 않으면 "완료"는 판정이 아니라 선언이고, 독자는 결과만 읽고 물건은 여전히 모른다. 구성 요소와 한 번의 실행 흐름까지가 REPORT의 몫이고, 진입 순서를 설계하고 선행 개념을 정의하는 수준이면 갱신되는 구조 문서가 필요한 것이므로 DOCUMENTATION으로 분리한다.
- **선행 계획이 있으면 그 완료선과 단계 번호를 그대로 축으로 삼는다** — 보고서가 자기 목차를 새로 만들면 독자가 계획과 보고를 손으로 맞춰 봐야 하고, 무엇보다 **달성하지 못한 항목이 목차에서 조용히 사라진다.** 미달 항목도 완료선 표에 한 줄로 남기고, 계획의 각 단계에 붙은 검증 기준에는 실측 결과를 1:1로 맞춰 적는다.
- 판정의 근거가 되는 산출물(로그·아티팩트·명령)의 경로를 함께 적는다.
- **방법·재현 절차는 판정 뒤에 둔다** — 어떻게 돌렸는가는 다시 돌릴 때 필요한 정보다. 앞에 남기는 것은 계획의 검증 기준에 맞춘 **실측 결과**이고, 그 결과를 낸 명령과 환경은 뒤다.
- 결함·미해결은 **발견 시점의 기록**으로 남긴다. 이후 처리했더라도 발견 절을 고쳐 쓰지 않고 후속 조치 절을 따로 두어 처리 내역을 적는다(SKILL.md §9 아카이브 원리를 살아 있는 문서로 확장한 것).
- **같은 대상에 추가 요청이 오면 새 파일을 만들지 않고 이 문서를 갱신한다**(SKILL.md §4) — 구조·동작과 남은 것은 현재 상태이므로 제자리에서 고치고, 무엇을 언제 더했는지는 프론트매터 `revisions` 와 후속 조치 절에 쌓는다. 같은 대상이란 같은 PLAN·같은 요청 줄기를 말하며, 대상이 바뀌면 새 REPORT다.
- **검사 tell**: "이 보고서가 답하지 않는 것"을 한 절로 쓸 수 없으면 보고 범위를 아직 정하지 않은 것이다. 범위를 정하지 않은 판정은 어디까지 믿어도 되는지를 독자가 되묻게 만든다.

**핵심 커버리지:**

- 핵심 결론(**선행 계획이 있으면 그 완료선을 항목별로 판정한 표로 연다**) → 무엇을 왜 했나(대상·완료 범위) → **만들어진 것**(구성 요소·한 번의 실행 흐름·**주요 설계 결정과 그 근거**) → **결과·판정**(계획의 단계별 검증 기준에 실측 결과를 1:1로 맞춰) → 남은 것(결함·미해결) → **[첨언] 다음 단계**. 필요 시 방법(도구·환경)·재현 방법 — 둘 다 뒤에 둔다, 진행 현황(완료 / 진행 중 / 미착수), 정량 성과, 한계(확인하지 않은 것), 산출물 위치(**실행이 만들어 낸 결과물의 경로** — 로그·아티팩트·리포트. 코드와 디렉터리 배치는 여기가 아니라 DOCUMENTATION의 몫이며, 다만 그 구조 문서가 아직 없으면 배치를 여기에 두되 문서가 생기면 옮긴다는 조건을 함께 적는다), 후속 조치.

상황에 따라 상세히 쓸 항목이 다르다 — 개발 완료 보고는 만들어진 것의 구조·동작과 **설계 결정 근거**·산출물 위치, 검증 결과 보고는 방법·재현 방법·한계, 테스트 결과 보고는 케이스별 판정과 실행한 단계 범위다. 설계 결정 근거를 남기는 이유는 같은 구조를 다시 쓸 때 필요한 것이 결과가 아니라 **그렇게 고른 이유와 그때 치른 대가**이기 때문이다.

> **조직 보고는 이 타입의 자리가 아니다.** REPORT의 독자는 사용자다. 외부 조직에 내는 공식 보고 3종(담당보고·본부보고·부문보고)은 골격과 문체를 함께 규정하는 `report-style` 스킬이 담당한다(SKILL.md §1).

## DOCUMENTATION — 구조·개념 설명 (이해)

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "이 문서만 읽고 전체 그림을 그릴 수 있는가?" |
| **관점** | 무엇인가 → 어떻게 나뉘는가 → 어떻게 흐르는가. 읽는 순서가 곧 이해 순서 |
| **톤** | 구조 중심, 진입 순서 설계, 정의 우선 |
| **강조** | 첫 화면 요약, 선행 개념 정의, 구성 요소, 실행 흐름, 원천 출처 |
| **피할 것** | 정의 없이 쓰는 내부 용어, 구조만 나열하고 흐름을 안 보여주는 서술, 도메인 개념의 기초 해설 |

**작성 원칙:**

- 첫 절은 요약이다 — 전체 그림을 한 화면에 담고 그 뒤를 상세로 둔다.
- 본문에서 쓸 **내부 용어**(이 시스템의 고유 식별자·약어)는 쓰기 전에 정의한다. 독자는 실무자이므로 도메인 개념은 전제하고, 이 저장소 밖에서는 통하지 않는 이름만 정의한다(SKILL.md §8-2).
- 구성 요소를 나눈 뒤에는 그 요소들을 관통하는 실행 흐름을 한 번 보여준다 — 층만 나열하면 각 층이 언제 동작하는지 알 수 없다.
- **검사 tell**: 처음 나오는 내부 용어 중 정의 없이 쓰인 것이 하나라도 있으면 미완성이다.
- **경계 tell**: 독자가 따라 할 절차나 지킬 규칙이 본문의 중심이면 DOCUMENTATION이 아니라 GUIDE다.

**핵심 커버리지:**

- 첫 화면 요약 → 무엇인가(정의·자리) → 구성 요소(계층·모듈) → **물리 배치**(대상이 코드베이스·저장소일 때 — 디렉터리와 핵심 파일의 지도, 각 자리가 무엇을 담는지) → 실행 흐름(한 번의 동작이 어떻게 흐르는가). 필요 시 현 구조가 된 배경, 선행 개념 정의, 담당자·원천 링크, 사용 예시.

논리 구조와 물리 배치는 다른 것이다 — 계층·모듈을 아무리 정확히 나눠도, 그 계층이 어느 폴더의 어느 파일에 사는지는 독자가 따로 찾아야 한다. 코드베이스를 다루는 문서에서 독자가 가장 먼저 필요로 하는 것이 후자다.

## GUIDE — 따라 하는 문서 (이해)

성격이 다른 둘이 들어온다 — 도구·시스템을 쓰는 **절차형**과, 사람이 지킬 양식·규칙을 적는 **규약형**이다. 톤과 핵심 질문은 같지만 "따라 한다"의 뜻이 실행과 준수로 달라지므로 커버리지가 나뉜다.

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "이것이 무엇을 위한 절차·규칙이며, 이대로 따라 하면 되는가?" |
| **관점** | 무엇을 위한 것인가 → 무엇이 전제되나 → 어떻게 하나. 목적을 모르고 단계만 따라가면 어긋났을 때 되돌아갈 곳이 없다 |
| **톤** | 실용적, 단계별, 재현 가능 |
| **강조** | 이 절차·규칙이 하는 일, 명확한 단계 또는 규칙 항목, 전제조건·적용 범위, 예시, 트러블슈팅 |
| **피할 것** | 목적 없이 시작하는 단계 나열, 추상적 설명, 재현 불가한 절차, 버전 미명시, 판정할 수 없는 규칙 |

**작성 원칙:**

- **이것이 무엇을 위한 것인지 한 문단으로 먼저 세운다** — 무엇이 끝나면 완료인지(절차형), 무엇을 지키려는 규칙인지(규약형). 목적을 모르고 단계만 따라가면 환경이 달라졌을 때 어디를 고쳐야 할지 판정할 수 없다.
- 전제조건을 그다음에 명시한다 — 절차형은 환경·버전·의존성, 규약형은 적용 범위와 예외.
- 절차형은 모든 단계가 복사-붙여넣기로 실행 가능해야 하며, 예상 출력·결과를 함께 제시한다.
- 규약형은 각 규칙에 위반 예와 교정 예를 붙인다 — 규칙만 적으면 지켰는지 판정할 수 없다.
- **용어 자립** — 독자가 이 저장소·이 세션 밖의 고유명은 모른다고 전제하고, 내부 약어와 그 도구가 자기만의 뜻으로 쓰는 낱말만 첫 등장 시 정의한다(병기 방향은 writing-principles §7.8). 도메인 개념은 전제한다.
- **팀에 배포할 규약이면 그 사실을 밝힌다** — 사용자가 이 문서를 그대로 팀에 넘기는 일이 실제로 일어난다(예: 근태·그라운드룰). 적용 범위 절에 누가 지키는 규칙인지를 적어 두면 배포 시점에 다시 쓰지 않아도 된다.
- **검사 tell**(절차형): 명령을 위에서부터 그대로 복사해 새 환경에서 돌렸을 때 멈추는 지점이 있으면 전제조건이 빠진 것이다.
- **검사 tell**(규약형): 어떤 규칙에 위반 예를 붙일 수 없으면 그 규칙은 준수 여부를 판정할 수 없다.
- **경계 tell**: 독자가 따라 할 절차도 지킬 규칙도 없고 이해할 구조만 남으면 GUIDE가 아니라 DOCUMENTATION이다.

**핵심 커버리지:**

- **절차형(도구·시스템 사용법)**: **이 절차가 하는 일**(무엇이 끝나면 완료인가) → 전제조건(환경·버전·권한) → 단계별 실행(복사-실행 가능한 코드/명령 + 예상 출력) → 정상 동작 검증. 필요 시 트러블슈팅.
- **규약형(양식·규칙·문화)**: **이 규칙이 지키려는 것** → 한 장 요약(지켜야 할 것 전체) → 항목별 규칙. 필요 시 규칙별 위반 예·교정 예, 적용 범위·예외, 원문·근거 링크.

## REFERENCE — 소재·포인터 색인 (이해)

무엇이 어디에 있는지를 적어 두는 문서. 내용을 담는 것이 아니라 **다시 찾아갈 곳**을 담는다 — Confluence 페이지ID, 저장소 경로, Jira 키, 인물·조직 매핑, 도메인 용어의 출처. 본문을 지우고 복구 포인터만 남기는 색인 압축의 산출물도 이 타입이다.

| 항목 | 정의 |
|------|------|
| **핵심 질문** | "필요할 때 여기서 원본으로 갈 수 있는가?" |
| **관점** | 무엇이 있는가 → 어디에 있는가 → 어떻게 여는가 |
| **톤** | 목록 중심, 식별자 정확, 설명 최소 |
| **강조** | 소재 식별자(페이지ID·경로·Jira 키·URL), 항목별 한 줄 요지, 접근 수단 |
| **피할 것** | 원본 내용의 재서술, 식별자 없는 항목, 확인 시점 없는 목록 |

**작성 원칙:**

- **항목마다 식별자와 한 줄 요지를 함께 적는다** — 식별자만 있으면 무엇 때문에 여는지 몰라 전부 열어 봐야 하고, 요지만 있으면 열 수가 없다.
- **원본 내용을 옮겨 적지 않는다.** 옮겨 적는 순간 원본이 바뀌어도 이 문서는 그대로이고, 어긋났다는 사실이 드러나지 않는다(SKILL.md §수치와 상태 "파생값을 저장하지 않는다"). 요지가 한 줄을 넘어가기 시작하면 그것은 REFERENCE가 아니라 DOCUMENTATION이나 RESEARCH의 몫이다.
- **포인터의 종류를 밝힌다** — 살아 있는 외부 소스(페이지ID·URL·Jira 키·저장소 경로)인지, 지워진 자체 문서의 복구 포인터(커밋 해시)인지. 후자는 복구 방법(`git show <hash>:<경로>`)을 그 줄에 함께 적는다.
- **접근 수단이 갈리면 적는다** — 권한·계정·토큰이 있어야 열리는 소재는 무엇으로 여는지를 항목이나 머리말에 적는다. 열리지 않는 포인터는 없는 포인터다.
- **최종 확인 시점은 프론트매터 `measured` 에 둔다** — 포인터는 조용히 죽는다. 페이지가 옮겨지거나 지워져도 이 문서는 그대로이므로, 언제 기준으로 살아 있었는지가 유일한 방어다.
- **검사 tell**: 항목 하나를 골라 그 식별자만으로 원본에 도달할 수 없으면 그 행은 포인터가 아니라 메모다.
- **경계 tell**: 독자가 이 문서만 읽고 대상을 이해하기를 기대한다면 REFERENCE가 아니라 DOCUMENTATION이다. 이 문서는 이해를 담지 않고 이해로 가는 길만 담는다.

**핵심 커버리지:**

- 이 색인이 덮는 범위(무엇의 소재인가) → 항목 목록(식별자 + 한 줄 요지 — 표 또는 계층 목록). 필요 시 분류 축, 접근 수단(권한·계정·도구), 죽은 포인터의 처리 이력.
