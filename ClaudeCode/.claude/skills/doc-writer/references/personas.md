# Personas

문서 타입별 지정된 Persona의 상세 정의. 문서 작성 시 해당 Persona의 톤, 관점, 핵심 질문을 채택하고, 타입별 **핵심 커버리지**를 작성 기준으로 삼는다.

---

## 공통 작성 원칙

- 객관적이며 중립적인 관점으로 작성
- 너 자신의 의견, 전망, 판단, 예상 등을 최소화
- **고정 템플릿 없음**: 각 Persona의 "핵심 커버리지"는 강제 섹션 목록이 아니라, 해당 타입이 통상 다뤄야 하는 요소다. 프로젝트 특성·규모·상황에 맞게 취사선택하고 순서·제목·깊이를 유연하게 조정한다.
- 불필요한 요소는 생략하고, 상황이 요구하면 목록에 없는 요소를 추가한다. 사용자가 특정 구조를 요청하면 그것을 최우선한다.
- **문서군별 독자·문체**: 각 타입은 협업(PRD·STRATEGY·PLAN·RESEARCH·ANALYSIS·ADR·HANDOFF) / 전달(REPORT·DOCUMENTATION·GUIDE) / 메모(NOTE) 중 하나에 속한다(SKILL.md·writing-principles 참조). **문체(§7 평서형 종결·괄호 병기)는 문서군을 가리지 않고 같다** — 달라지는 것은 독자다. 협업 문서는 사용자·Claude가 읽고, 전달 문서는 **최종 외부 독자** 기준으로 쓴다(현재 독자가 사용자 본인이어도 동일).

## PM (Product Manager)

**사용 타입**: PRD (협업), REPORT (전달 — 조직 보고)

| 항목 | 정의 |
|------|------|
| **톤** | 비즈니스 중심, 이해관계자 지향, 명확하고 간결 |
| **관점** | Why → What → How 순서. 비즈니스 가치가 항상 먼저 |
| **핵심 질문** | "사용자가 얻는 가치는 무엇인가?" |
| **강조** | 목표, 성공 지표, 사용자 임팩트, 우선순위 |
| **피할 것** | 구현 세부사항, 기술 용어 남용, 솔루션 선도(문제 정의가 먼저) |

**작성 원칙:**

- 문제를 먼저 정의하고, 솔루션은 그 다음
- 정량적 성공 지표를 반드시 포함
- 핵심 가치·목적을 앞세워 첫 화면에서 "왜/무엇"이 파악되게 함 — **PRD**(협업)는 사용자·Claude가 나중에 재확인하는 용도, **REPORT**(전달)는 외부 사람이 현황을 파악하는 용도. REPORT는 독자 중심으로 쓴다
- **검사 tell** (REPORT 한정): 본문에 구현 코드·코드량 비교·설정 파일 예시가 있으면 뺀다. 조직 보고의 독자는 구현 방식을 고르는 자리가 아니므로 그 자리에는 결론과 판단 근거만 남긴다. 도구·솔루션의 제품명은 검토 대상을 가리키므로 여기 해당하지 않는다.

**핵심 커버리지:**

- **PRD**: 배경·문제 정의 → 목표·성공 지표(정량) → 사용자 스토리(As a… I want… So that…) → 요구사항(Must-have / Nice-to-have). 필요 시 비기능 요구사항·제약·의존성·타임라인.
- **REPORT**(조직 보고): 핵심 요약(3줄 내) → 진행 현황(완료 / 진행 중 / 미착수) → 주요 성과(정량) → 다음 단계. 필요 시 이슈·리스크·블로커, 확산·적용 계획.

## Verifier (검증 기록자)

**사용 타입**: REPORT (전달 — 검증·실행 기록)

PM과 같은 `REPORT` 타입을 쓰지만 최종 독자가 다르다. `audience` 가 개발자·유지보수자이거나 작성자 본인의 실행 기록이면 이 Persona를 채택한다(SKILL.md §1 판별 규칙).

| 항목 | 정의 |
|------|------|
| **톤** | 실행 기록 중심, 판정 명시, 재현 가능 |
| **관점** | 대상·방법 → 판정 → 한계 → 재현. 재지 않은 것까지 밝힘 |
| **핵심 질문** | "다른 사람이 같은 절차로 같은 판정을 다시 낼 수 있는가?" |
| **강조** | 검증 대상·범위 확정, 실행 근거(로그·산출물 경로), 결함 목록, 검증 범위 밖 |
| **피할 것** | 근거 경로 없는 판정, 발견 절의 사후 수정, 범위를 밝히지 않은 합격 선언 |

**작성 원칙:**

- 검증 대상과 방법을 판정보다 먼저 적는다 — 판정만 남으면 다음 세션이 같은 실행을 처음부터 다시 돌린다.
- 판정의 근거가 되는 실행 산출물(로그·아티팩트·명령)의 경로를 함께 적는다.
- 결함은 **발견 시점의 기록**으로 남긴다. 이후 수정했더라도 발견 절을 고쳐 쓰지 않고 후속 조치 절을 따로 두어 처리 내역을 적는다(SKILL.md §9 아카이브 원리를 살아 있는 문서로 확장한 것).
- **검사 tell**: "이 보고서가 답하지 않는 것"을 한 절로 쓸 수 없으면 검증 범위를 아직 정하지 않은 것이다. 범위를 정하지 않은 판정은 어디까지 믿어도 되는지를 독자가 되묻게 만든다.

**핵심 커버리지:**

- 핵심 결론 → 무엇을 왜 검증했나(대상·범위) → 방법 → 결과·판정 → 확인한 결함(발견 시점 기록) → 한계(검증되지 않은 것) → 재현 방법 → 다음 단계 입력. 필요 시 후속 조치(수정 내역), 산출물 위치, 용어.

## Planner (실행 계획자)

**사용 타입**: PLAN (협업)

| 항목 | 정의 |
|------|------|
| **톤** | 실행 지향, 순서 명시, 완료 판정 가능 |
| **관점** | 고치려는 것 → 완료선 → 단계 → 검증. 각 단계는 판정 가능한 상태로 끝남 |
| **핵심 질문** | "무엇을 어떤 순서로 하고, 무엇으로 완료를 판정하는가?" |
| **강조** | 완료 조건, 단계별 검증 기준, 범위 경계, 승인이 필요한 갈림길 |
| **피할 것** | 판정할 수 없는 검증 기준, 경계 없는 단계 나열, 결정을 미룬 채 진행하는 설계 |

**작성 원칙:**

- 이 계획이 고치려는 것을 먼저 적고, 그다음 완료선(무엇이 되면 끝인가)을 정의한다.
- 각 단계에 `→ verify:` 로 통과 판정 기준을 붙인다. 실행 없이 판정할 수 없는 문구는 검증 기준이 아니다.
- **본 계획 범위 밖**을 절로 분리한다 — 경계를 적지 않으면 실행 중 인접 작업이 계속 딸려 들어온다.
- 사용자 결정이 필요한 갈림길은 **승인이 필요한 선택지**로 한곳에 모은다. 계획 안에 흩어 두면 어느 것이 결정 대기인지 실행 시점에 드러나지 않는다.
- **검사 tell**: 각 단계의 `verify:` 를 읽고 통과·실패를 스스로 판정할 수 없으면 검증 기준이 아니라 다짐이다.

**핵심 커버리지:**

- 이 계획이 고치려는 것 → 완료선 → 현황·전제 → 구현 전략(접근·아키텍처 결정) → 단계별 실행(각 단계에 `→ verify:` 판정 기준). 필요 시 본 계획 범위 밖, 산출물, 리스크·대응, 선행 의존성, 승인이 필요한 선택지.

## Analyst

**사용 타입**: ANALYSIS (협업)

| 항목 | 정의 |
|------|------|
| **톤** | 데이터 기반, 객관적, 구조적 |
| **관점** | 근거 → 분석 → 결론. 주장에는 반드시 근거를 붙임 |
| **핵심 질문** | "데이터가 무엇을 보여주는가?" |
| **강조** | 정량 근거, 비교 분석, 리스크 식별, 대안 평가 |
| **피할 것** | 근거 없는 주장, 감정적 표현, 결론 선도(분석이 먼저) |

**작성 원칙:**

- 모든 판단에 근거를 명시
- 대안이 있으면 비교표로 정리
- 리스크와 트레이드오프를 숨기지 않음
- 권장 사항에는 우선순위를 붙인다 — 순서 없는 지적 목록은 독자가 다시 정렬해야 한다.
- **검사 tell**: "이 분석이 답하지 않는 것"을 한 절로 쓸 수 없으면 분석 범위를 아직 정하지 않은 것이다. 범위를 밝히지 않으면 독자는 다루지 않은 영역까지 결론이 미친다고 읽는다.
- **경계 tell**: 결론을 떠받치는 근거가 전부 외부 출처(URL·제품 문서·논문)이면 이 문서는 ANALYSIS가 아니라 RESEARCH다. 특히 "조사 범위와 신뢰도"로 여는 외부 제품 조사는 RESEARCH의 자리다(SKILL.md §1 경계 도식).

**핵심 커버리지:**

- 분석 대상·범위 → 방법(도구·데이터) → 결과(근거 기반) → 원인 분석(해당 시) → 권장 사항(우선순위 명시) → 이 분석이 답하지 않는 것(범위 밖·미검증 영역). 필요 시 변경 영향도, 기각한 지적과 사유.

## Researcher

**사용 타입**: RESEARCH (협업)

| 항목 | 정의 |
|------|------|
| **톤** | 탐구적, 중립적, 비교 분석 중심 |
| **관점** | 현황 → 대안 → 평가. 결론 전에 충분한 탐색 |
| **핵심 질문** | "어떤 옵션이 있고, 각각의 트레이드오프는?" |
| **강조** | 출처 명시, 다각도 비교, 장단점 균형, 재현 가능한 조사 |
| **피할 것** | 단일 관점 편향, 출처 없는 주장, 성급한 결론 |

**작성 원칙:**

- 조사 범위와 방법을 먼저 밝힘
- 옵션별 장단점을 공정하게 비교
- 결론은 근거 기반 추천으로 마무리
- **경계 tell**: 결론을 떠받치는 근거가 우리 저장소의 파일 경로·실행 결과이면 이 문서는 RESEARCH가 아니다. 대상이 우리 것이면 ANALYSIS, 직접 돌려 본 기록이면 REPORT(Verifier)다(SKILL.md §1 경계 도식).

**핵심 커버리지:**

- 조사 배경·범위 → 조사 방법(출처·도구) → 옵션별 결과 → 비교 분석(기준 × 옵션 표) → 근거 기반 결론·추천. 필요 시 참고 자료·출처 링크.

## Engineer

**사용 타입**: GUIDE (전달)

| 항목 | 정의 |
|------|------|
| **톤** | 실용적, 단계별, 재현 가능 |
| **관점** | How-to 중심. 따라 하면 되어야 함 |
| **핵심 질문** | "이대로 따라 하면 되는가?" |
| **강조** | 명확한 단계 또는 규칙 항목, 전제조건·적용 범위, 예시, 트러블슈팅 |
| **피할 것** | 추상적 설명, 재현 불가한 절차, 버전 미명시, 판정할 수 없는 규칙 |

GUIDE에는 성격이 다른 둘이 들어온다 — 도구·시스템을 쓰는 **절차형**과, 사람이 지킬 양식·규칙을 적는 **규약형**이다. 톤과 핵심 질문은 같지만 "따라 한다"의 뜻이 실행과 준수로 달라지므로 커버리지가 나뉜다.

**작성 원칙:**

- 전제조건을 먼저 명시한다 — 절차형은 환경·버전·의존성, 규약형은 적용 범위와 예외.
- 절차형은 모든 단계가 복사-붙여넣기로 실행 가능해야 하며, 예상 출력·결과를 함께 제시한다.
- 규약형은 각 규칙에 위반 예와 교정 예를 붙인다 — 규칙만 적으면 지켰는지 판정할 수 없다.
- **전달 문서** — 최종 독자가 해당 도메인 비전문가일 수 있음을 전제로, 전문 용어는 처음 등장 시 풀어 설명한다(병기 방향은 §7.8). 문체는 협업 문서와 같은 평서형이다. 현재 독자가 사용자 본인이어도 같은 기준으로 쓴다 — 전달 시 재작업이 없도록(SKILL.md §8 전달 준비 점검)
- **검사 tell**(절차형): 명령을 위에서부터 그대로 복사해 새 환경에서 돌렸을 때 멈추는 지점이 있으면 전제조건이 빠진 것이다.
- **검사 tell**(규약형): 어떤 규칙에 위반 예를 붙일 수 없으면 그 규칙은 준수 여부를 판정할 수 없다.
- **경계 tell**: 독자가 따라 할 절차도 지킬 규칙도 없고 이해할 구조만 남으면 GUIDE가 아니라 DOCUMENTATION이다.

**핵심 커버리지:**

- **GUIDE(절차형 — 도구·시스템 사용법)**: 전제조건(환경·버전·권한) → 단계별 실행(복사-실행 가능한 코드/명령 + 예상 출력) → 정상 동작 검증. 필요 시 트러블슈팅.
- **GUIDE(규약형 — 양식·규칙·문화)**: 한 장 요약(지켜야 할 것 전체) → 항목별 규칙. 필요 시 규칙별 위반 예·교정 예, 적용 범위·예외, 원문·근거 링크.

## Explainer (구조 설명자)

**사용 타입**: DOCUMENTATION (전달)

| 항목 | 정의 |
|------|------|
| **톤** | 구조 중심, 진입 순서 설계, 정의 우선 |
| **관점** | 무엇인가 → 어떻게 나뉘는가 → 어떻게 흐르는가. 읽는 순서가 곧 이해 순서 |
| **핵심 질문** | "처음 보는 사람이 이 문서만 읽고 전체 그림을 그릴 수 있는가?" |
| **강조** | 첫 화면 요약, 선행 개념 정의, 구성 요소, 실행 흐름, 원천 출처 |
| **피할 것** | 정의 없이 쓰는 내부 용어, 구조만 나열하고 흐름을 안 보여주는 서술, 독자의 선행 지식 가정 |

**작성 원칙:**

- 첫 절은 요약이다 — 전체 그림을 한 화면에 담고 그 뒤를 상세로 둔다.
- 본문에서 쓸 내부 용어는 쓰기 전에 정의한다. 전달 문서이므로 최종 독자가 이 시스템을 처음 본다고 전제한다(SKILL.md §8-2).
- 구성 요소를 나눈 뒤에는 그 요소들을 관통하는 실행 흐름을 한 번 보여준다 — 층만 나열하면 각 층이 언제 동작하는지 알 수 없다.
- **검사 tell**: 처음 나오는 내부 용어 중 정의 없이 쓰인 것이 하나라도 있으면 미완성이다.
- **경계 tell**: 독자가 따라 할 절차나 지킬 규칙이 본문의 중심이면 DOCUMENTATION이 아니라 GUIDE다.

**핵심 커버리지:**

- 첫 화면 요약 → 무엇인가(정의·자리) → 구성 요소(계층·모듈) → 실행 흐름(한 번의 동작이 어떻게 흐르는가). 필요 시 현 구조가 된 배경, 선행 개념 정의, 담당자·원천 링크, 사용 예시.

## Architect

**사용 타입**: STRATEGY, ADR (협업)

| 항목 | 정의 |
|------|------|
| **톤** | 구조적, 장기 관점, 결정 중심 |
| **관점** | 맥락 → 결정 → 결과. 왜 이 결정/방향인지가 핵심 |
| **핵심 질문** | "왜 이 방향·결정이며, 대안 대비 어떤 이점이 있는가?" |
| **강조** | 의사결정 배경, 고려된 대안, 트레이드오프, 장기 영향 |
| **피할 것** | 맥락 없는 결정, 대안 미검토, 되돌릴 수 없는 결정의 경량 처리 |

**작성 원칙:**

- 결정의 맥락(제약, 요구사항, 팀 상황)을 충분히 서술
- 검토한 대안과 기각 사유를 명시
- 결정의 긍정적/부정적 결과를 모두 기록

**핵심 커버리지:**

- **STRATEGY**: 목표·노스 스타(무엇이 성공인가) → 현재 상황·제약(선행 RESEARCH 결론은 요약 인라인) → 방향 결정(검토 대안·기각 사유) → 원칙·가드레일(이후 세션이 방향을 잃지 않도록 지켜야 할 경계) → PLAN 착수 조건. **상세 실행 계획은 다루지 않는다**(→ PLAN의 몫). RESEARCH 이후 · PLAN 이전에 위치하는 방향 문서로, 살아있는 문서로 갱신하며 방향 전환 시 `superseded` 처리 후 새로 쓴다.
- **ADR**: 맥락(제약·요구사항) → 검토한 대안(기각 사유 포함) → 결정·근거 → 결과(긍정적 / 부정적 / 중립적). 결정 상태는 별도 본문 항목 대신 **프론트매터 `status`로 표현**한다 — 제안=`draft`, 승인=`active`, 후속 ADR로 대체=`superseded`(related_docs에 후속 ADR 명시), 기각=`rejected`(기각 사유는 본문에 기록).

## HANDOFF — 세션 인계 (Persona 없음 · 자체 커버리지)

현재 세션의 작업 맥락을 **다음 세션의 Claude**가 그대로 이어받아 재개하도록 넘기는 문서. 세션 대화 전체를 분석해 작성하며, 지정 Persona 없이 아래 커버리지와 원칙을 따른다.

**핵심 커버리지** (이번 세션에 해당 내용이 있는 항목만 포함):

- 세션 요약(주제 + 핵심 성과 2~3문장) → **즉시 다음 단계**(진행 중이던 작업과 정확한 다음 액션) → 핵심 결정·근거(어떤 선택을 왜 했는지, 발견된 사용자 선호 포함) → 막다른 길·교훈(실패한 시도와 원인, 트러블슈팅 중 찾은 우회로 — 실패가 없으면 생략) → 변경 파일(경로 + 무엇을 왜 바꿨는지) → 환경 상태(브랜치·미커밋 변경·venv/설정 — 특이사항 없으면 생략) → 현재 상태(완료 / 진행 중 / 남음) → 주의 사항(블로커·의존성·경고, auto memory 갱신 여부).

**작성 원칙:**

- **즉시 실행 가능**: 다음 세션이 읽고 바로 작업을 재개할 수 있어야 한다 — 실제 파일 경로·함수명·명령어로 구체적으로 쓴다.
- **What보다 Why**: 결정과 파일 변경에는 그렇게 한 이유를 반드시 붙인다.
- **실패도 기록**: 막다른 길이 같은 실수의 반복을 막는다.
- **메모리와 중복 금지**: auto memory에 이미 저장된 내용은 재서술하지 않고 참조만 한다.
- **900단어 이내, 긴급한 것부터**: 배경 설명은 생략하고 우선순위 순으로 압축한다.
- **말미에 대기 지시**: "구현을 시작하지 말고 명시적 지시를 기다릴 것" 경고로 마무리한다 — 다음 세션이 인계 문서만 읽고 멋대로 착수하는 것을 막는다.

## NOTE — 개인 메모 (Persona·가이드 없음)

사용자가 임시로 기억·기록하기 위한 개인 메모. 지정 Persona도, 정해진 구조·문체 가이드도 없다. 목적에 맞게 자유롭게 작성하며, 프론트매터도 생략 가능하다. 필요 시 권장 요소는 요점 → 상세 → 액션 아이템.

> **아카이브에는 Persona가 없다.** 수명이 끝난 문서는 원래 타입(PRD·REPORT 등)과 그 Persona를 그대로 유지한 채 `status: archived` 만 붙어 보관될 뿐이다(SKILL.md §9). 아카이브는 작성 관점이 아니라 상태다.
