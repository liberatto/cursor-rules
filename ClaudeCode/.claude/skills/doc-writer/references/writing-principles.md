# Writing Principles

Quality principles applied to all documents, regardless of type or Persona.

**독자와 목적 — 문서군 3분류**: 이 스킬이 만드는 문서는 목적에 따라 세 가지이며, 적용 원칙이 다르다.

- **협업 문서** — `PRD` · `STRATEGY` · `PLAN` · `RESEARCH` · `ANALYSIS` · `ADR` · `HANDOFF`. 주 독자는 **작성자(사용자)와 이후 세션의 Claude**. 외부 제출용 보고서가 아니라 프로젝트 진행 중 만들어 두고 다시 참고하는 **작업 산출물이자 세션 간 공유 컨텍스트**다. 결정·근거·현재 상태를 남겨 나중에 재개 가능하게 하는 것이 핵심 가치. 사람은 빠르게 스캔하고 Claude는 새 세션에서 모호함 없이 맥락을 복원하도록 쓴다. **§1–7 적용.**
- **전달 문서** — `REPORT` · `DOCUMENTATION` · `GUIDE`. **최종 독자는 팀 외부의 사람**(다른 개발자·조직, 비전문 독자 포함 가능)이며, 현재는 주로 작성자(사용자) 본인이 읽는다. 그래도 처음 읽는 외부 독자가 이해하고 활용하도록 **독자 중심**으로 쓴다 — 그래야 전달 시점에 수정 없이(또는 최소 수정으로) 넘길 수 있다. **§1–7 적용** — 문체는 협업 문서와 같고, 차이는 독자 중심 서술과 자립성 요구의 강도다. 특히 §1 User-Centered·§6 Self-Contained를 강하게 따르고, SKILL.md §8 전달 준비 점검을 작성 시점부터 준수한다.
- **개인 메모** — `NOTE`. 사용자가 임시로 기억·기록하는 용도. 정해진 가이드 없음 — 목적에 맞게 자유 작성(프론트매터도 생략 가능). §7도 강제하지 않는다.

> 문서군은 **작성 시점의 목적**으로 나뉜다. 수명이 끝나 아카이브된 문서(`status: archived`)는 별도 문서군이 아니라 **원래 문서군에 그대로 속한다** — 아래 원칙은 아카이브 시점에 소급 적용되지 않으며, 본문은 당시 그대로 보존한다(SKILL.md §9).

## 1. User-Centered

- Lead with the user's goal, not the feature.
- Answer "why should I care?" before "how does it work?"
- Anticipate user questions and pain points.

**Per document type** — for 협업 문서 the consumers are you and Claude, so the "Reader" below is a *content lens* (whose concerns to address); for 전달 문서(REPORT·DOCUMENTATION·GUIDE) the "Reader" is the **final external audience** to write for, even while the current reader is the user:

| Type          | Reader                  | Reader's Core Question             |
|---------------|-------------------------|------------------------------------|
| PRD           | Stakeholders            | "Why are we building this?"        |
| STRATEGY      | Future sessions (user & Claude) | "Which direction, and why?" |
| PLAN          | Implementers            | "What do I need to do?"            |
| RESEARCH      | Decision-makers         | "What are the options?"            |
| REPORT        | Managers & stakeholders | "Where do things stand?"           |
| GUIDE         | Practitioners           | "Can I follow this as-is?"         |
| ANALYSIS      | Decision-makers         | "What does the analysis conclude?" |
| ADR           | Future teammates        | "Why was this decided?"            |
| HANDOFF       | Next session's Claude   | "Can I resume exactly where this left off?" |
| NOTE          | Author (personal)       | "What was captured?"               |
| DOCUMENTATION | Practitioners           | "How does this work?"              |

## 2. Clarity First

- Use active voice and present tense.
- Keep sentences under 25 words.
- One main idea per paragraph.
- Define technical terms on first use.

### 2.1 서술어는 확인 가능한 것을 가리킨다

이 문서의 독자는 IT·개발 실무자다. 구체 용어가 필요한 자리에 구어를 쓰면 오히려 이해가 느려진다 — 읽는 사람이 자기 맥락으로 한 번 번역해야 하기 때문이다.

**예외는 비유뿐이다.** 개념을 처음 세울 때 비유에 구어를 쓸 수 있고, 그 경우에도 비유 다음 문장은 정확한 용어로 되돌아온다. 비유가 정의를 대신하면 안 된다.

결과·평가·수량·상태를 뭉뚱그린 서술은 독자가 확인하러 갈 곳을 못 찾는다. 빠진 정보를 채워 쓴다.

| 뭉뚱그림 | 빠진 것 | 고침 |
| --- | --- | --- |
| 붙여 보니 **안 됐다** | 어떤 동작이 어떻게 실패했나 | 테스트 대역에서 통과하던 호출이 실제 연동에서 실패했다 |
| 그때마다 같은 **사고가** 난다 | 무슨 사고인가 | 그때마다 같은 **검사 누락이** 발생한다 |
| **잘 만들어졌다** | 무엇이 검증됐나 (평가어) | **실행 경로는 회귀 테스트로 검증됐다** |
| 테스트가 **여러 개** 있다 | 무엇을 세었나 (단위) | **계약 테스트 파일** 5개 |
| 저장소가 **기본값이다** | 어느 구현체인가 | 저장소가 **`InMemoryStore` 로 고정돼 있다** |
| 성능 **문제이면서** 설계 **문제**다 | 두 술어가 같은 축의 값인가 | 증상은 지연이고, 원인은 인덱스 부재다 |
| 초기 구축 비용이 **매우 낮다** | 무엇을 재서 낮다고 하나 (등급어) | 초기 구축 비용이 **낮다(연동 설정 3회로 기동)** |

**등급어는 근거 괄호와 함께만 쓴다.** `매우 낮음 · 훨씬 강력 · 절대적으로 유리 · 완벽히 격리`처럼 정도를 나타내는 말은 그 자체로는 확인할 대상이 없다. 지우는 대신 **판정 뒤에 근거를 괄호로 붙여** 확인 경로를 만든다 — `Azure 전용(Azure Monitor·KQL·자원 제어에 최적화)`. 근거를 못 적으면 그 등급 판단은 아직 근거가 없는 것이므로 문장에서 뺀다. 괄호 용법은 §7.8 참조.

**범주어로 술어를 채우지 않는다.** `문제 · 이슈 · 측면 · ~ 관련`은 대상을 가리키지 않는다. 한 대상에 성질을 둘 붙일 때는 각각이 어느 축(성격·위치·원인·증상)의 값인지 밝힌다 — 축이 다른 값을 같은 형태로 나열하면 독자는 둘을 같은 축으로 읽는다.

판단 기준: **"이 문장을 읽고 확인하러 갈 대상(파일·명령·심볼)을 지목할 수 있는가."** 못 하면 서술어가 아직 뭉뚱그려져 있다.

## 3. Show, Don't Just Tell

- Include practical examples for every concept.
- Provide complete, runnable code samples.
- Show expected output.
- Include common error cases.

---

## 4. Progressive Disclosure

- Structure from simple to complex.
- Quick start before deep dives.
- Separate must-read content from optional depth explicitly.
- Don't overwhelm — let readers stop at the depth they need.

---

## 5. Scannable Content

- Use descriptive headings.
- Bulleted lists for 3+ items.
- Tables for comparisons.
- Visual hierarchy: headings > bold > body text.

---

## 6. Self-Contained

- Reference only within the document — don't send the reader to another file for context the document needs.
- If external context is essential, inline its substance, not a link.
- A reader should understand the document without opening anything else.
- **Anti-pattern — Leaky Package**: linking out to context the document depends on; reads fine here, breaks when the file is shared or moved.
- The test: Can a reader understand this without opening anything else? If no, inline more.

## 7. Korean Sentence Style (한국어 문서)

**적용 대상: 한국어로 쓰는 모든 문서 타입.** 협업 문서와 전달 문서를 가리지 않으며, 개인 메모(NOTE)에만 강제하지 않는다. 영어로 쓰면 §1–6만 따른다. 문체를 구어체도 존댓말도 아닌 일관된 기술 톤으로 통일해 **사람은 빠르게 스캔하고 Claude는 모호함 없이 파싱·복원**하도록 한다.

> **소급 적용하지 않는다.** 이 절은 이후 작성·갱신하는 문서에만 적용된다. 이미 쓰인 문서를 문체 때문에 다시 손대지 않으며, 특히 아카이브·사료 성격의 기록(§9)은 당시 문체 그대로 둔다.

### 7.1 평서형 종결 — 존댓말을 쓰지 않는다

- 문장 끝은 평서형 `~다`로 맺는다 — `~한다`, `~이다`, `~했다`, `~된다`, `~아니다`.
- `~합니다 / ~입니다 / ~됩니다 / ~드립니다 / ~하세요`는 쓰지 않는다. 문서는 대화가 아니라 기록이다.
- 명사형 종결(`~함`, `~필요`, `~예정`)로 문장 전체를 맺지 않는다. 표 셀·체크리스트·불릿 항목처럼 **문장이 아닌 자리**에서는 명사구가 자연스럽고, 그 경우는 종결어미 문제가 아니다.

| 회피 | 권장 |
| --- | --- |
| 설정을 변경했습니다 | 설정을 변경했다 |
| ~할 수 있습니다 | ~할 수 있다 |
| 지원합니다 / 제공됩니다 | 지원한다 / 제공된다 |
| 불가능합니다 | 불가능하다 / 지원하지 않는다 |
| ~라면 효율적입니다 | ~라면 효율적이다 |
| 비교해 드립니다 | 비교한다 / 아래에 정리한다 |
| 확인해 보세요 | 확인한다 (지시가 필요하면 명령형 `확인할 것`) |

### 7.2 과압축 금지

조사·주어·목적어·연결어(단/즉/반면)를 통째로 생략하면 독자가 재해석해야 하므로 보존한다.

- 압축 상한 = 이 맥락을 모르는 사람(또는 새 세션의 Claude)이 **1회 읽고 이해**하는 선. 넘으면 글자 수보다 이해를 우선해 한 박자 풀어 쓴다.
- 여러 뜻으로 읽히거나 배경 지식이 있어야 복원되면 과압축 — 주어·맥락어 1개를 복원한다.
- 예: "검증 통과" → "FD 누수 검증 통과" / "도구 다양성. 가드레일 통일." → "도구 다양성 허용, **단** 가드레일은 통일".

### 7.3 구어·감정 표현 회피 (중립 기술 톤)

동작과 측정값을 감정 없이 사실로 서술한다. IT 도메인 구어 동사는 의미는 통하지만 문서·로그·번역에 약하므로 표준 IT 동사로 교체한다.

| 회피 | 권장 |
| --- | --- |
| 깔다 | 설치 / 스캐폴딩 / 구성 |
| 박다·박히다 | 고정 / 하드코딩 / 들어감 · 삽입 |
| 못박다 | 명시 / 규정 |
| 잡다 | 지정 / 설정 |
| 건드리다·손대다 | 수정 / 변경 |
| 풀리다·못 푼다 | 해결 |
| 뒤집다 | 반전 |
| 되돌리다 | 롤백(rollback) |
| 가르다·가르고·가른다·갈라 | 나누다 / 분리하다 / 구분하다 (맥락별 선택 — 실물을 떼어 놓으면 `분리`, 몫·범주로 쪼개면 `나눔`, 판단으로 갈래를 정하면 `구분`) |
| 갈리다·갈리는 | 달라지다 / 차이가 발생하다 |
| 두 갈래·세 갈래 | 두 가지 / 세 가지 |
| 무너지다·붕괴·폭락 | 하락 / 감소 / 성립하지 않음 |
| 터지다 | 실패 / 오류 발생 |
| 가려지다 | 드러나지 않음 / 감지되지 않음 |
| 스쳐 지나가다 | 검사하지 않음 / 누락 |
| 숨다·숨을 공간 | 드러나지 않는 범위 |
| 희미해지다 | 재구성 불가 |
| 흔들리다 | 일관되지 않음 / 완화됨 |
| 부풀다 | 과대 산출 |
| 낡다 | 실제와 어긋남 / 갱신되지 않음 |
| 오염시키다 | 변경을 남김 |
| 굴리다 | 운영 / 실행 |
| 감으로 | 임의로 / 근거 없이 |
| 왜 하필 | 어느 자리에 / 무엇 때문에 |
| 쥐여주다 | 제공 / 위임 |
| 얹다 | 추가 / 적용 |
| 뜯어고치다 | 재구현 / 개조 |
| 바닥부터 | 최소 단위부터 / 처음부터 |
| 무기 · 판정승 · 손색없다 | (우열 비유를 빼고 비교 축과 근거로 서술) |

의인 표현도 같다 — "미래의 사람에게 메모를 남긴다" → "전제가 깨진 시점을 알리는 장치".

**비유는 개념을 처음 세우는 자리에만 쓴다**(§2.1). 상태·판정·결과를 적는 자리에는 쓰지 않는다 — 독자가 비유를 자기 맥락으로 한 번 번역해야 하고, 번역 결과가 사람마다 다르다. 실무 문서에서 반복해 나타나는 세 갈래는 이렇다.

| 갈래 | 회피 | 권장 |
| --- | --- | --- |
| 신호·색 | 빨간불이 켜진다 · 초록으로 돌아온다 · 녹색 신호 | 실패로 바뀐다 · 통과로 돌아온다 · 통과 신호 |
| 물리·재난 | 전제가 붕괴한다 · 지표가 무너진다 · 기준이 흔들린다 | 전제가 성립하지 않는다 · 지표가 하락한다 · 기준이 일관되지 않다 |
| 의인화 | 채점표가 거짓말을 한다 · 검사기가 속는다 | 채점표를 신뢰할 수 없다 · 검사기가 결함을 통과시킨다 |

**의인화와 주체 명시를 혼동하지 않는다.** `check_gate.py가 인용 수치를 대조한다`는 §7.11이 요구하는 주체 명시이고, `check_gate.py가 거짓말한다`는 의인화다. 구분 기준은 **그 서술어가 도구의 실제 동작인가**다.

판단 기준: "영문 릴리스 노트·API 문서로 번역해도 자연스러운가."

### 7.4 격식 한자어 회피

문어체 한자어는 일상 실무어로 교체한다. 기준: "중급 IT 실무자가 대화에서 쓰는 말인가."

| 회피 | 권장 |
| --- | --- |
| 구동 | 실행 / 동작 |
| 제고 | 향상 / 개선 |
| 강구 | 마련 |
| 도모 | 추진 |
| 모색 | 검토 |
| 관건 | 핵심 |
| 용이 | 쉬움 |
| 지양 | 피함 |
| 지향 | 목표 |

### 7.5 영어 직역체 회피

영문 자료·AI 산출물 기반 작업에서 직역 표현이 자주 섞인다. 한국어로 처음부터 썼다면 고르지 않았을 표현은 자연스러운 한국어로 바꾼다.

| 회피 | 권장 |
| --- | --- |
| 1급 (first-class) | 정식 지원 / 동등 지원 |
| 배타적이지 않다 (mutually exclusive) | 병행 가능 |
| 오버킬 (overkill) | 과함 |
| swap | 교체 |
| ~를 따라감 (follows) | ~ 환경을 그대로 따름 |
| ~가 성립한다 (holds) | ~해야 한다 / ~가 필요하다 |
| 닫다·닫혔다 (close an issue) | 해소 / 해결 / 처리 |
| 원시체 (primitive) | 확장 수단 / 기본 단위 |

- IT 원어 유지가 정당하면(Brownfield·Scale-Adaptive 등) 첫 등장 시 한국어 부연 1회 병기: `Scale-Adaptive(규모별 적응)`. 병기 방향과 용법은 §7.8.
- **영어 기술어를 한자로 축자 조립해 새 명사를 만들지 않는다.** `primitive → 원시체`처럼 어근마다 한자를 대응시킨 조어는 문법은 맞지만 국어에 없어 독자가 뜻을 추측해야 한다. **판단 기준: 그 말이 한국어 기술 문서에서 같은 뜻으로 쓰인 용례가 있는가.** 없으면 원어를 그대로 두거나(§7.6), 그 말이 문맥에서 가리키는 일을 풀어 쓴다 — `extension primitive` 는 딸린 항목이 전부 확장 방법이므로 `확장 수단`.

### 7.6 기술용어·백틱·강조

- 기술용어는 영어 원문 유지(API·Transformer·Backend). 억지 한글화 금지.
- 첫 등장 시 괄호 병기 — 방향과 용법은 §7.8.
- 파일 경로·명령어·변수명·식별자는 백틱: `docs/`, `npm run build`.
- 굵게 강조는 핵심 결론·수치·제품명에만.

### 7.7 섹션 제목 = 명사구 한 덩어리

- 섹션 제목은 내용을 가리키는 **명사구 한 덩어리**. 동사·의문문·서술문·사설 논조("왜 ~가 필요한가")를 쓰지 않는다.
- 부연 dash(`—`)는 쓰지 않는다. 부연은 제목 안 명사구로 흡수하거나 괄호·콜론으로 처리. `·` `( )` `:` 는 허용.
- 예: "왜 에이전트 분리가 필요한가" → "에이전트 분리의 필요성" / "배경 — 계약 기반 설계" → "배경".

### 7.8 괄호 병기 — 여섯 용법

괄호는 문장을 늘리지 않고 밀도를 올리는 장치다. **판정·근거·원어·예시를 문장 밖으로 빼내** 본문은 짧게 두고 확인 경로는 남긴다. 용법이 섞이면 독자가 괄호를 읽는 규칙을 매번 다시 세워야 하므로 아래 여섯으로 고정한다.

| 용법 | 형태 | 예 |
| --- | --- | --- |
| **번역어(원어)** | 한글이 앞, 영어 원형이 괄호 | 압축(Compaction) · 업무 위임(Handoff) · 동작 흐름(Workflow) |
| **약어(풀이)** | 약어가 앞, 풀이가 괄호 — **방향이 반대다** | MCP(Model Context Protocol) · RCA(원인 분석) · JWT(JSON Web Token) |
| **판정 라벨** | 제목·항목 끝에 결론과 수단 | `동작 흐름 제어: 가능(서브에이전트·훅)` |
| **근거** | 등급·판정어 바로 뒤에 그 판정을 떠받치는 사실 | 초기 구축 비용 낮음(연동 설정 3회로 기동) · 회귀 통과(423 passed) |
| **예시 열거** | 추상 명사 뒤에 구체 사례 | 사내 모니터링 도구(Datadog · Splunk · Dynatrace 등) · (예: 로그 분석 노드, 배포 이력 조회 노드) |
| **실패 모드 열거** | 문제·한계·리스크 뒤에 실제 증상 | 바이브 코딩의 한계(유지보수 불가 · 할루시네이션 · 맥락 상실) · 맥락 유실(컨텍스트 윈도우 초과) |

- **병기는 첫 등장 1회만.** 이후에는 한쪽 표기로 통일한다 — 매번 병기하면 본문이 읽히지 않는다.
- **판정 라벨은 §7.7의 부연 dash 금지에 대한 대체 수단**이다. `배경 — 계약 기반 설계`는 금지지만 `배경(계약 기반 설계)`은 허용한다.
- **근거 괄호는 등급어의 통행 조건**이다(§2.1). 등급어를 쓰려면 이 괄호가 함께 있어야 한다.
- 괄호 안에 문장을 넣지 않는다. 명사구·열거·짧은 조건까지다 — 문장이 필요하면 본문으로 뺀다.

### 7.9 판정 우선 · 대비 서술

- **섹션 첫 문장이 결론이다.** 근거·과정은 그다음 불릿으로 내린다. 독자가 첫 줄에서 판정을 얻지 못하면 그 섹션은 끝까지 읽어야 쓸모가 생긴다.
- **비교에서는 주어를 매 문장 명시한다.** 대상이 둘 이상이면 "이것은 / 반면 그것은" 대신 고유명을 반복한다 — `Azure SRE Agent는 ~ / Anthropic Agent SDK는 ~`. 지시어는 두 문단만 지나면 어느 쪽을 가리키는지 흔들린다.
- **정의형 항목은 콜론 라벨로 연다** — `Kusto 툴: 매개변수를 치환해 실행하는 고정 KQL 쿼리`. 라벨은 명사구, 뒤는 한 문장.
- **경계를 한 문장 안에서 나눈다.** 할 수 있는 것만 적으면 독자는 나머지도 된다고 읽는다 — "GUI와 API로 워크플로·프롬프트·도구를 확장할 수 있지만, 에이전트 루프 자체를 재구현하는 것은 불가능하다".
- **선택 기준을 나열할 때는 어미를 정렬한다** — `~일 때 / ~원할 때 / ~해야 할 때`. 항목마다 어미가 다르면 같은 축의 조건인지 독자가 판별하지 못한다.
- **지침·발화 예시는 큰따옴표로 직접 인용한다** — `"장애 인지 시 사내 플레이북 A를 참고할 것"`. 풀어 설명하면 그대로 복사해 쓸 수 없다.

### 7.10 개념 도입 문장

개념·도구·컴포넌트를 처음 꺼내는 문장은 형태가 정해져 있다. 독자가 그 자리에서 대상의 범주·존재 이유·오해 지점을 한꺼번에 받아 가야 뒤 문단이 설명으로 읽힌다.

**첫 문장은 완결 정의다.** `{이름}은 {누가 무엇을 어떻게 하는} {상위 범주}다` 한 문장으로 범주와 범위를 함께 준다.

> BMad Method는 AI 에이전트 팀이 분석·기획·설계·구현·검증까지 개발 전 과정을 수행하는 AI 기반 애자일 개발(AIDD, AI-Driven Development) 프레임워크다.

상위 범주(프레임워크 · 스크립트 · 게이트 · 결정 테이블)를 빼면 독자는 뒤 문단을 읽는 내내 그 자리를 추측한다. 정의 문장 안에 열거를 넣어 범위를 한 번에 닫는 것도 같은 목적이다.

**기능보다 결핍을 먼저 적는다.** 기능을 설명하기 전에, 그 기능이 없을 때 벌어지는 일을 한 문장 둔다.

> AI는 대화가 길어지면 맥락을 잃는다. BMad는 단계마다 결과물을 문서로 남기고, 다음 에이전트는 그 문서만 읽고 작업을 시작한다.

문제 문장이 없으면 기능 목록은 근거 없는 자랑으로 읽힌다. 이 두 문장 패턴(결핍 → 대응)은 §1의 "왜 신경 써야 하나를 어떻게 동작하나보다 먼저"를 한국어 문장 단위로 실현한 것이다.

**독자가 기본값으로 가정할 그림이 틀렸으면 부정문으로 먼저 끊는다.**

> 하나의 AI가 전 과정을 담당하지 않는다. 실제 개발팀처럼 역할별 에이전트가 자기 책임 범위만 수행한다.

`A가 아니다. B다` 순서를 지킨다. B만 적으면 독자는 원래 갖고 있던 A를 유지한 채 B를 덧붙여 읽는다.

**관계는 입출력으로 적는다.** 단계·컴포넌트가 이어지는 모습은 비유로 그리지 않고 무엇을 받아 무엇을 내는지로 적는다.

> 각 단계의 에이전트는 이전 단계의 문서 하나를 입력으로 받아 다음 단계의 문서를 출력한다. 그 사이에 대화 이력은 넘기지 않는다.

입출력을 적으면 독자가 그 지점에서 실제 파일을 지목할 수 있다. 비유로 대신하면 독자마다 다르게 이해한다.

**구체 수량으로 규모를 보인다.** 추상적인 "큰 문서" 대신 독자가 규모를 가늠할 수 있는 수를 쓴다 — `100페이지짜리 기획서와 수천 줄의 코드를 한 번에 읽으면`. 실측값이면 본문에 값만 적고 기준 시점은 프론트매터 `measured` 에 둔다(SKILL.md "수치와 상태"). 규모 감각을 주려는 예시값이면 예시임이 드러나게 쓴다.

### 7.11 동작 주체와 효과 문장

**동작에는 주체를 적는다.** 무주어 수동태 대신 역할·컴포넌트를 주어로 세운다. 주체가 사람인지 스크립트인지 에이전트인지가 그 문장의 책임 소재다.

| 회피 | 권장 |
| --- | --- |
| PRD가 작성된다 | PM 에이전트가 PRD를 작성한다 |
| 요구사항이 작업 단위로 분해된다 | 스크럼 마스터가 요구사항을 Epic·Story로 분해한다 |
| 누수 여부가 검사된다 | `data_checks.py`가 타깃과 각 피처의 상관을 검사한다 |
| 승인 후 다음 단계로 넘어간다 | 사용자가 승인해야 다음 단계로 넘어간다 |

**구조를 설명한 뒤에는 효과 한 문장으로 닫는다.** 무엇을 어떻게 배치했는지 적고 나면, 그 배치가 막아 주는 실패를 이어서 적는다.

> 개발 에이전트는 해당 Story 파일 하나와 관련 코드 몇 개만 컨텍스트에 올린다. 문서 전체를 읽을 때 생기는 할루시네이션과 토큰 낭비를 함께 줄이는 구조다.

효과 문장이 없으면 독자는 그 구조를 작성자의 취향으로 읽는다. 효과를 적지 못하면 그 구조는 아직 설명할 준비가 되지 않은 것이다.

**개수를 앞에 예고한다.** 제목·리드 문장에 항목 수를 함께 적으면 독자가 읽을 분량과 목록의 끝을 먼저 안다 — `핵심 구성요소 7종` · `전체 워크플로우 4단계` · `게이트 5종`. 적은 개수는 실제 항목 수와 반드시 일치시킨다 — 개수는 목록에서 세면 나오는 파생값이므로 항목을 고칠 때 함께 고쳐야 한다(SKILL.md "수치와 상태").

**용어는 첫 등장에서 병기하고 이후 한쪽으로 통일한다.** `제품 요구사항 문서(PRD)`로 한 번 열고, 그다음부터는 `PRD`만 쓴다. 병기 방향은 §7.8.

### 7.12 표 셀의 문장 형태

표는 같은 축의 값을 나란히 두는 장치이므로, 셀의 **형태가 어긋나면 축이 어긋난 것으로 읽힌다.**

- **셀은 문장이 아니라 명사구다.** 종결어미(`~한다` · `~이다`)를 붙이지 않는다. 이는 §7.1의 명사형 종결 금지에 대한 예외 자리다.
- **한 셀에 항목이 여럿이면 쉼표나 `·`로 2~3개까지, 같은 품사로 정렬한다** — `아이디어 구체화, 시장 조사, product-brief.md 작성`. 3개를 넘으면 표가 아니라 불릿으로 내린다.
- **산출물·명령·식별자는 원형 그대로 넣는다.** `PRD.md 작성 및 검증`처럼 실제 파일명을 쓰고 "요구사항 문서를 만드는 일"로 풀지 않는다 — 표는 독자가 찾아갈 대상을 지목하는 자리다(§2.1).
- **같은 열의 셀은 같은 형태로 맞춘다.** 한 셀만 완결 문장이면 독자는 그 셀을 다른 축의 값으로 읽는다. 열 단위로 훑어 형태가 튀는 셀을 고른다.
- **라벨 열은 이름과 역할을 함께 준다** — `Mary (Analyst)` · `Bob (Scrum Master)` · `G2(데이터 품질)`. 이름만 있으면 표 밖에서 그 행을 인용할 수 없다.
- **판정 열에는 결론어를 먼저 두고 근거를 괄호로 붙인다** — `가능(서브에이전트·훅)` · `미지원(하네스가 유형 거부)`. 근거 없는 `가능`·`양호`는 §2.1의 등급어 규칙에 걸린다.

### 7.13 설득·수사 문장 배제

문서는 독자를 설득하는 자리가 아니라 확인 가능한 사실을 남기는 자리다. 규칙과 설계의 정당성은 근거로 서고 강조·경고로 서지 않는다. 아래 네 갈래는 지운다.

| 갈래 | 회피 | 처리 |
| --- | --- | --- |
| 동기 부여·경고 | "이런 규칙은 비용이 들어 나중에 반드시 흔들린다. 근거를 모르면 그때 지우게 된다" | 문단째 삭제 — 각 규칙의 근거는 해당 항목에 이미 있다 |
| 자기 변호 | "부록에 둔 이유는 개념이 하나 늘기 때문이며, 내용이 약해서가 아니다" | 이유만 남기고 변호 절을 뺀다 |
| 수사 의문·반문 | "기준이 없으면 모든 측정이 '그래서?'로 끝난다" | 결과를 사실로 적는다 — "측정값을 합격 판정에 쓸 수 없다" |
| 과장 강조 | "이 문서는 홀로 서지 않는다" · "이것이 이 세트의 전제다" | 사실로 바꾼다 — "이 문서만으로는 평가를 실행할 수 없다" |

**금지·규칙 문장은 설득이 아니다.** "기준을 측정값에 맞춰 만들지 않는다"처럼 독자가 따를 실행 규칙은 남긴다. 구분 기준은 **그 문장이 행동을 규정하는가, 태도를 요구하는가**다.

판단 기준: **그 문장을 지웠을 때 독자가 잃는 확인 가능한 정보가 있는가.** 없으면 설득 문장이다. 정도를 강조하는 부사(반드시·매우·훨씬)가 붙어 있으면 §2.1의 등급어 규칙을 함께 적용한다.

## 8. 도식 — 배치 주장은 그린다

**도식의 발동 조건은 내용의 복잡도가 아니라 주장의 종류다.** 문서가 **배치(arrangement)** 를 주장하는 자리, 곧 무엇이 어디에 속하는가 · 무엇이 어디로 옮겨가는가 · 이전과 이후가 어떻게 다른가를 말하는 자리에서는 설명하지 말고 작은 도식을 그린다. 나머지는 산문과 표가 맡는다.

| 내용의 형태 | 수단 |
| --- | --- |
| 소속 · 포함 · 계층 (무엇이 무엇 안에 있나) | 도식 — 트리 · 레이어 |
| 이동 · 순서 · 분기 · 상태 전이 (무엇이 어디로 가나) | 도식 — 흐름 · 게이트 · 입출력 |
| 전후 대비 (바꾸기 전과 후가 어떻게 다른가) | 도식 — 전후 2단 |
| 같은 축의 항목 3개 이상 비교 | 표(판정 열 포함 — §7.12) |
| 단일 판정 · 선형 설명 | 산문 |

**형태가 없는 내용에 형태를 씌우지 않는다.** 본문 문장을 그대로 상자에 옮긴 도식, 나열을 화살표로 이은 도식, 노드가 둘뿐인 도식(`A → B`)은 문장이 낫다. 판단 기준: **도식을 지우고 문장만 남겼을 때 잃는 정보가 있는가.** 없으면 그 도식은 장식이다.

**문장 자리의 화살표 체인으로 도식을 대신하지 않는다.** 산문 한가운데 `설정 로드 → 검증 → 실패`처럼 화살표로 이어 붙인 구절은 도식도 문장도 아니다 — 압축한 것처럼 보이지만 각 단계의 주체와 조건이 빠져 독자가 복원해야 한다. 배치를 보여야 하면 **도식 블록으로 그리고**, 그럴 내용이 아니면 주어와 술어를 갖춘 문장으로 쓴다. 화살표는 도식 안, 그리고 §8.1이 허용한 한 줄 체인 자리에만 둔다.

**규모 상하한**: 노드가 3개 미만이면 문장으로 쓴다. 노드 12개 또는 25줄을 넘으면 층을 나눠 두 도식으로 만든다 — 한 화면에 안 들어오는 도식은 표보다 읽기 어렵다.

### 8.1 정렬 규칙 — 한글은 2칸이다

한글 음절의 표시 폭은 2칸(East Asian Width `W`)이고, 박스 문자(`─` `│` `┌` `├`)와 화살표(`→`)는 폰트에 따라 1칸이나 2칸으로 달라지는 `Ambiguous`다(2026-08-07 `python3 -c "import unicodedata; unicodedata.east_asian_width(...)"` 실측). 그래서 한글이 든 줄의 오른쪽으로 열을 맞추면 **읽는 환경에 따라 도식이 어긋난다.**

- **어긋나면 못 읽는 것과 어긋나도 읽히는 것을 구분한다.** 테두리 · 세로선 · 오른쪽 주석 열은 어긋나는 순간 도식이 깨지고, 들여쓰기는 몇 칸 밀려도 읽힌다. **한글은 후자 자리에만 둔다.**
- **한글 라벨이 있으면 우변을 닫지 않는다.** 사방이 닫힌 상자와 여러 줄에 걸친 연결선은 라벨이 ASCII 식별자 · 숫자일 때만 쓴다(`config.yaml` · `run_experiment.py`).
- **한글 오른쪽에 세로선이나 주석 열을 두지 않는다.** 주석 열이 필요하면 그 왼쪽을 전부 ASCII로 채운다(파일 트리가 이 경우다). 예외는 **행마다 한글 글자 수가 정확히 같을 때**뿐이다 — 모든 행이 같은 폭만큼 밀리므로 유지된다. 다만 한 행만 고쳐도 깨지므로 나중에 항목이 늘어날 자리에는 쓰지 않는다.
- **연결선은 ASCII(`+` `-` `|` `v`)로 긋는다.** 유니코드 박스 문자는 행마다 개수가 다르면 폰트에 따라 서로 다른 폭만큼 밀린다. 유니코드 트리 문자(`├──`)는 오른쪽에 맞출 열이 없을 때만 쓴다.
- **정렬을 요구하지 않는 한 줄 체인에는 `→`를 써도 된다.** 아래 줄과 맞출 것이 없으면 폭이 흔들려도 깨질 것이 없다.
- **좌우 2단 배치를 쓰지 않는다.** 전후 대비는 위아래로 쌓는다 — 좌우 2단은 왼쪽 칸의 한글 폭이 오른쪽 칸 전체를 밀어낸다.
- 폭 상한은 **80칸**이며 한글을 2칸으로 세어 맞춘다. 도식은 코드펜스 안에 넣고 **언어 태그를 붙이지 않는다** — 문법 강조가 도식을 색칠하면 오히려 안 읽힌다.

### 8.2 도식과 본문의 분업

- **도식 바로 뒤에 판정 한 문장을 붙인다.** 무엇을 읽어야 하는지 적지 않으면 독자마다 다른 것을 본다 — "게이트가 FAIL이면 사람의 서명 없이는 다음 단계로 가지 않는다".
- **라벨은 본문 용어와 글자 그대로 일치시킨다.** 본문이 `check_gate.py`면 도식도 `check_gate.py`다. 도식에서만 쓰는 약칭을 만들면 독자가 대응표를 스스로 만들어야 한다.
- **화살표의 뜻을 한 도식 안에서 섞지 않는다.** 데이터 흐름 · 실행 순서 · 포함 관계는 각각 다른 도식이다. 한 도식에 섞어야 하면 화살표 옆에 뜻을 라벨로 적는다.
- **도식은 본문을 대체하지 않는다.** 도식이 배치를 보이고 본문이 이유와 근거를 적는다.
- **수량 비교는 도식이 아니라 표다.** ASCII 막대는 값이 5개 이하이고 규모 차이 자체가 결론일 때만 쓴다.

### 8.3 마감 점검

**도식은 있으면 좋은 것이 아니라 저장 전 통과 조건이다.** 문서를 저장하기 전에 배치 주장을 훑는다.

1. **소속 · 이동 · 전후를 말로만 설명한 문단이 남아 있으면 그 자리가 빠진 도식이다.** 형태를 가진 내용은 그 형태로 보인다.
2. **배치 주장이 아닌데 붙은 도식은 뺀다.** 형태가 없는 내용에 형태를 씌운 것이다.
3. **산문 안에 화살표 체인이 남아 있으면 도식으로 올리거나 문장으로 되돌린다.**
4. **각 도식이 §8.1의 정렬 규칙을 지키는지 본다** — 한글 오른쪽에 맞춰야 할 열이 있으면 그 도식은 다른 환경에서 깨진다.
