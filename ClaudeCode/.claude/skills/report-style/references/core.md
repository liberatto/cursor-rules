# 공식 보고 문서 작성 스타일 가이드

> **적용 범위** (2026-08-12 확정): 담당보고·본부보고·부문보고 — 정기 사이클과 그 계위에 올리는 개별 보고 문서. 그 밖의 문서(GUIDE·NOTE·RESEARCH·ANALYSIS·PLAN·PRD·ADR·HANDOFF·DOCUMENTATION)는 `doc-writer` 스킬이 담당하며 어미 규칙이 정반대(평서형 `~다`)이므로 두 규칙을 한 문서에 겹치지 않음.

> **Write so an intelligent colleague unfamiliar with my work understands it top-to-bottom on the first pass — without opening another document.**

> **독립 문서**: 본 가이드는 외부 참조 없이 단독 이해 가능하도록 구성. 하우스 스타일 규칙의 단일 SoT (갱신 이력은 `## 0. 업데이트 로그`).

## 1. 자립성 원칙

실무형 문서의 최상위 원칙.

### 1.1 단독 이해 가능성

- 외부 문서(전략문서·계획문서·직전 리포트 등)를 **참조하지 않고** 본 문서만 읽어 결론 이해 가능해야 함
- 독자가 이해하는 데 필요한 맥락은 **본문 적절한 위치에 직접 서술**
- 외부 문서는 "추가 상세 원하는 독자를 위한 참조", **필수 전제가 아님**

**예시 비교**


| 회피                           | 권장                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| "전략문서 §3의 Phase 1 게이트 통과"    | "Phase 1 성공 게이트(LSTM 대비 nMAPE 5% 이상 개선) 통과"                                                 |
| "역할 분담은 전략문서 §2.1 참조"        | (역할 분담 표를 해당 위치에 직접 작성)                                                                     |
| "자세한 Phase 2 계획은 기존 전략문서 참조" | "Phase 2 주요 범위: MATNet·PatchTST·Chronos-2·TimesFM+XReg 4종 호환성 검증" (상세 항목은 같은 섹션 안에서 이어서 서술) |


### 1.2 섹션 내 완결성 + 위에서부터 읽기 흐름

자립성의 두 번째 축 — **위에서부터 한 번 훑으면 결론까지 이해**되는 구성. 독자가 섹션 사이를 왔다갔다하지 않도록 설계.

**섹션 간 cross-reference 금지**

- `(상세는 §2.2)`, `(→ §6 참조)` 같은 뒤 섹션 참조는 독자에게 점프 부담 강요. **해당 섹션 안에서 자체 완결**로 서술
- `(§1.2에서 정의한 X)` 같은 앞 섹션 역방향 참조도 금지 — 각 섹션·단락은 방향에 관계없이 자체 완결. 필요한 정의·맥락은 해당 위치에서 직접 재서술
- 같은 정보가 두 곳에 흩어지면 한 곳으로 통합 — **Single Source of Truth** 유지

**섹션·문단 순서로 누적 이해 설계**

- 앞 섹션이 뒤 섹션의 전제가 되도록 배치 — §2 배경에서 정의한 용어·전제는 §3 이후 본론에서 추가 설명 없이 사용 가능해야 함
- 본론 섹션 내부에서도 **결과 → 해석 → 함의** 순. 앞 단락이 뒤 단락의 전제가 되도록 단락 순서 잡기
- 작성 후 처음 읽는 동료가 위→아래 한 번에 따라갈 수 있는지 자체 검토

**외부 문서 내용 직접 흡수**

- 외부 문서에서 필요한 내용이 있으면 출처 언급 없이 필요한 만큼만 발췌·재서술하여 현재 작성 중인 문서에 직접 작성
- `전략문서 §3.2 참조`, `아래 분석 문서 참고` 류 출처 유도 멘트 금지 — 독자가 다른 문서를 열지 않아도 이해 완결
- 외부 문서 링크·경로가 꼭 필요한 경우에만 §N 부록 "참조 목록"에 한 곳에 모음 — 본문 산재 금지

### 1.3 자립성 선언 위치

자립성 선언은 문서 최상단 메타블록에 포함. 표준 양식은 §3.1 메타블록 표준 템플릿 참조.

### 1.4 배포용 산출물 자립성 (패키지 경계)

단일 문서를 넘어 **배포·전달되는 산출물**(스킬·플러그인·모듈·독립 문서 등) 전반에 적용되는 자립성 확장. 개별 산출물은 각자 **단독으로 성립**해야 하며, 밖으로 매달린 참조를 두지 않음.

- 참조는 **패키지 경계 안**(해당 문서·스킬·모듈 내부)으로 한정
- 외부 맥락이 꼭 필요하면 링크로 넘기지 말고 **본문에 실질을 인라인**
- 산출물이 배포 대상(스킬·플러그인·독립 문서·사용자가 지정한 목적지)일 때는 이 자립성이 간결·최소수정 원칙보다 **우선** — 먼저 인라인한 뒤 패키지 안에서 다듬음

**회피 패턴 — Leaky Package**: 산출물에 필요한 맥락을 인라인하지 않고 밖으로 링크. 현재 위치에선 동작하나 전달되는 순간 깨짐.

**판단 기준**: 다른 무엇도 열지 않고 이 산출물만 읽어 이해되는가? — NO면 더 인라인.

- 약어는 최초 등장 시 괄호 병기 (`JWT (JSON Web Token)`, `SSE (Server-Sent Events)`)
- 파일 경로·API 경로·명령어·변수명·식별자는 백틱
- 굵은 글씨 강조: 우리 팀 관련 / 조직명·제품명·핵심 수치 / 핵심 결론·합의사항

### 2.5 격식 한자어 회피

문어체·격식 한자어는 가독성 저해. 실무 표현으로 교체.


| 회피  | 권장 대체어                                    |
| --- | ----------------------------------------- |
| 구동  | 동작 / 실행 / 운영                              |
| 제고  | 향상 / 개선                                   |
| 강구  | 마련 / 준비                                   |
| 도모  | 추진 / 진행                                   |
| 모색  | 검토                                        |
| 기저  | 기반 / 바탕                                   |
| 추이  | 흐름 / 변화                                   |
| 관건  | 핵심 포인트                                    |
| 용이  | 쉬움 / 간편                                   |
| 지양  | 피함                                        |
| 지향  | 목표                                        |
| 상정  | 가정                                        |
| 주지  | 공유 / 전파 (교체 대상은 "주지시키다·주지의 사실"만 — "알려주지"는 정상) |
| 수급  | 확보                                        |
| 비등  | 비슷 / 유사                                   |

| 기제  | 동작 원리 / 핵심 기술 / 작동 방식                     |
| 소관  | 맡은 / 담당하는 (예: "담당 소관 시스템" → "담당이 맡는 시스템") |

**판단 기준**: "중급 IT 실무자가 일상 업무 대화에서 이 단어를 쓰는가?" — NO면 교체. 임원·부문 보고는 한 단계 더 좁혀 **"4~50대 IT 경영진이 회의에서 입으로 말하는 단어인가"**로 판정.

#### ⚠ 교체 방향은 언제나 쉬운 쪽 (역행 금지)

§2.5·§2.7·§2.8의 모든 교체에 걸리는 상위 원칙. **회피어를 없애려다 원문보다 어려운 말을 집어넣으면 교체가 아니라 악화다.** 구어를 지우는 데만 신경 쓰면 격식 한자어로 갈아타기 쉽다.

```
✗ 덮지 못함(구어)  →  포괄하지 못함(더 어려움)      ← 역행. 회피어만 바뀌고 독자는 더 힘들어짐
✓ 덮지 못함        →  전부 담당할 수 없음 / 정해진 환경에서만 동작
```

- **교체 후 소리 내어 읽어 본다** — 회의에서 그대로 말할 수 있으면 통과, 문서에서만 쓰는 말이면 다시 고름
- 한 단어로 바꾸기 어려우면 **문장을 풀어 쓴다**(추상 명사 하나보다 평이한 절 하나가 낫다). 예: `각자 기반 밖 환경을 포괄하지 못함` → `각각 Azure·Datadog 위에서만 동작`
- 실측 근거: '26.8.5 AO Agent 본부보고에서 `덮지 못함`→`포괄하지 못함` 교체가 팀장님 지적("이 표현도 어렵다")으로 되돌려짐

#### 교체하지 않는 한자어 (허용 목록)

> ⚠ **과잉 교체 방지용**. 한자어라는 이유만으로 손대면 오히려 전문성이 떨어지고 문장이 늘어짐. 아래는 임원·실무 대화에서 그대로 쓰이므로 **교체 대상 아님**.

| 분류 | 허용 어휘 |
| --- | --- |
| 상태·판단 | 부재 · 판명 · 선결(과제) · 상회 · 좌우 · 곤란 · 과다 |
| 조직·추진 | 소관 외 대부분 — 이관 · 편입 · 실증 · 병행 · 발굴 · 착수 · 주관 · 상시 · 선행 |
| 분석·기술 | 규명 · 수렴 · 내재화 · 파급 · 전수 · 정형 · 유실 · 오탐 · 소요 · 직결 · 양상 · 미지 · 기동 |

- 판정이 나뉘면 **교체하지 않는 쪽**이 기본 — 원문 유지가 손실 0, 교체는 뉘앙스 손실 위험
- 로컬 근거: AO Agent 본부보고 정비('26.7.29) — 22곳 교체 후 팀장님 검수에서 **13곳 원복**(부재·판명·선결·내재화·편입·파급·규명·수렴·양상·미지·기동 등). 남은 교체 = 기제·소관·준용·형상·전건·상회·가중·심화·곤란 계열

### 2.6 작성자·독자 관점

본 저장소 문서는 **팀장(박성수)이 작성자로서 다른 구성원·이해관계자에게 전달하는 상황**을 기본 전제로 함. 작성 도구가 사람이든 AI든, 받는 사람이 읽었을 때 작성자 본인이 정리해 전달하는 자연스러운 뉘앙스 유지. AI 자동 생성 흔적이나 제3자 익명 피동 표현 노출 금지.

#### 2.6.1 작성자 관점 — 능동형 우선

**원칙**

- 작성자 자신의 행위(정리·판단·권고·제안·결정)는 **능동형(~함)** 으로 표현. 피동 `~됨`은 작성자를 지움
- 외부 사실·관찰 결과(데이터 수집 시점, 시스템 발생 이벤트 등)에 대한 피동(`~됨`)은 자연스러우므로 그대로 허용
- "나·내가·박성수·팀장이" 등 1인칭/직위 명시 불필요. 능동형 어미만 살리면 작성자 관점이 드러남
- "본 문서는 ~에 의해 자동 생성됨", "이 가이드는 AI가 정리한 결과임" 등 AI·도구 작성 흔적 일체 표기 금지

**대체어 표 (작성자 행위 동사)**


| 회피 (피동·익명) | 권장 (작성자 관점·능동)     |
| ---------- | ------------------ |
| ~로 작성됨     | ~로 작성함 / ~를 작성     |
| ~가 정리됨     | ~를 정리함 / ~에 정리     |
| ~가 도출됨     | ~를 도출함             |
| ~가 권고됨     | ~를 권고함             |
| ~가 제안됨     | ~를 제안함             |
| ~가 판단됨     | ~로 판단함 / ~로 봄      |
| ~로 결정됨     | ~로 결정함             |
| ~가 검토됨     | ~를 검토함             |
| ~가 평가됨     | ~로 평가함 (작성자 평가일 때) |


**예시**


| 회피                     | 권장                 |
| ---------------------- | ------------------ |
| 본 가이드는 4인 사례를 정리해 작성됨. | 본 가이드에 4인 사례를 정리함. |
| 결제 FD가 챔피언으로 권고됨.      | 결제 FD를 챔피언으로 권고함.  |
| 5축 평가가 도출됨.            | 5축 평가를 도출함.        |
| 데이터는 2024년에 수집됨.       | (그대로 — 외부 사실)      |


#### 2.6.2 독자 관점 — 직접 향함, 메타·자기지시 격리

**독자 후보**


| 독자                    | 문서 유형           |
| --------------------- | --------------- |
| 상무·본부장                | 위로 올리는 보고서      |
| 팀원·유관자                | 설명·전달 가이드·업무 지침 |
| 외부 인원·신규 합류자·LLM 에이전트 | 가이드·매뉴얼         |


**예외**: 사용자가 "내가 보려고 정리하는 메모", "self-note", "checklist for me" 등으로 **명시 요청 시**에만 1인칭·자기지시 톤 허용. 별도 요청 없으면 본 §2.6.2 default 적용.

**원칙**

- **독자에게 직접 말하는 톤** — "이 명령으로 동작 확인", "다음 절차 따름", 명사형 절차문으로 처리
- **메타·배포자 시점 회피** — "수령자에게 ~ 함께 전달함", "단독 전달 시 동작 불가" 같이 작성자·배포자가 챙길 부분은 본문에서 빼고 **메타블록·부록에 한 줄로 격리**
- **자기지시문 회피** — "내가 ~ 해야 함", "박성수는 ~ 검토함" 같이 작성자 자신을 향한 지시·자기 명시는 본문 노출 금지. §2.6.1의 능동 어미만으로 작성자 관점은 충분히 드러남
- **독자 직접 호명 최소화** — "여러분", "독자께서는" 같은 호명 거의 사용 안 함. 명사형 절차문이 default

**회피 → 권장 대체 패턴**


| 회피 (메타·자기지시·배포자 시점)                | 권장 (독자 향함)                        |
| ---------------------------------- | --------------------------------- |
| 수령자에게 가이드 + reference 2종을 함께 전달함   | (메타블록 "함께 받는 자료: …" 한 줄로 격리)      |
| 가이드 단독 전달 시 arx CLI 누락으로 동작 불가     | (부록 "재현 시 필수 자료" 항목으로 격리)         |
| 수령자는 동일 상대 경로에 배치 권장               | 동일 상대 경로 배치 권장 (`lab/poc/...`)    |
| 수령자 측 동작 확인 절차                     | 동작 확인 절차                          |
| 본 가이드를 LLM 에이전트에 입력으로 줄 때 사용할 프롬프트 | LLM 에이전트 입력 프롬프트 표준               |
| 박성수는 다음 단계로 ~ 검토함 (자기 명시)          | (직위·이름 생략, 능동 어미만 유지)             |
| 내가 이 부분 다시 봐야 함                    | (본문에서 제거. 자기 메모면 별도 self-note 분리) |


#### 2.6.3 통합 판단 기준

- **능동·피동 결정**: 이 행위의 주체가 작성자(나)인가, 외부 사건인가? — 작성자 행위면 능동, 외부 사건이면 피동 가능
- **본문·메타 분리**: 이 문장이 독자에게 새 정보를 주는가, 작성자·배포자가 챙길 행동을 알리는가? — 후자면 본문에서 빼고 메타블록·부록으로 격리

### 2.7 영어 직역체 회피

영문 자료·AI 산출물 베이스 작업 시 `first-class / mutually exclusive / overkill / swap / follows` 같은 영어 사고가 한국어로 직역되어 의미 전달이 흐려지는 경우가 잦음. 한국어 자연 표현으로 풀어 옮기고, IT 원어 유지가 정당해도 1차 등장 시 한국어 부연 1회 병기.

**판단 기준**

> AI·번역 도구 없이 한국어로 처음부터 작성한다면 이 단어·표현을 골랐을까? — NO면 교체 또는 풀어쓰기.

**대표 회피 → 권장 (망라 아닌 패턴 트리거)**


| 회피 (영문 직역)                  | 권장 (한국어 자연 표현)                |
| -------------------------- | ----------------------------- |
| 1급 / 1급 시나리오 (first-class) | 정식 지원 / 동등 지원 / 처음부터 정규 지원    |
| 배타적이지 않다 (mutually exclusive) | 둘 중 하나만 고를 필요 없다 / 병행 가능       |
| 오버킬 (overkill)             | 과하다 / 과한 선택                   |
| swap (영문 그대로)              | 교체                            |
| ~를 따라감 (follows)           | ~의 환경을 그대로 따른다                |
| 가능성 (possibility 직역)       | 용이성 / 가능 여부 (문맥별 구분)          |
| 준비도 (readiness 직역)         | 착수 가능성 / 준비 상태 (풀어쓰기)         |


**외래어·원어 1차 등장 시 부연 규칙**

- IT 원어 유지가 정당한 경우(Brownfield·Greenfield·Skill·Scale-Adaptive 등)도 **첫 등장 시 괄호 또는 부제로 한국어 풀이 1회**. 이후 등장은 원어만.
- 형식 예: `Scale-Adaptive(규모별 적응)`, `facilitated workflows(질문으로 안내하는 워크플로우)`, `부분(sparse) 오버라이드`

### 2.8 감정·비유·구어 표현 회피 (중립 기술 톤)

기술 문서는 동작과 측정값을 감정 없이 서술. 소설·대화체의 과장·의인화·구어 표현은 객관성을 떨어뜨림. 사실 진술형으로 교체.


| 회피 유형 | 회피 예 | 권장 |
| --- | --- | --- |
| 과장·감정 동사 | 무너지다 / 폭락 / 붕괴 | 하락 / 감소 / 0%로 떨어짐 |
| 의인화·비유 | 떠받치다·흔들리다·막히다·채워지다·잡아내다 | 담당·기여 / 회귀(regression) 발생 / 미달 / 해소 / 검출 |
| 구어·비격식 | 죄다·잠깐·후하게·한 겹씩·못 만듦·못 푸는 | 모두·일시·유리하게·단계적·생성 불가·해결 불가 |
| 주관 가치판단 | 가짜 매칭·억지 매칭 | 오매칭(false match)·잘못 매칭 |
| **IT 동작 구어** | 깔다·박다·잡다·건드리다·풀리다·뒤집다·되돌리다·꼬리·두 길·가르다 | 스캐폴딩·고정·지정·수정·해결·반전·롤백·말미(tail)·두 가지 방법·나누다/분리하다 |
| **혈통·생물 비유 명사** | 계보 / 족보 / 뿌리 / DNA / 유전자 / 태생 | **유형 / 패턴 / 계열 / 구조 / 출발점** (예: "동일 계보임을 확인" → "동일 **유형**임을 확인") |
| **불필요한 부정 프레이밍** | 경쟁이 아닌 협력 / 대체가 아니라 보완 / ~에 한정되지 않음 | **긍정 서술만 남김** (예: "경쟁이 아닌 분업 구도" → "**협력 구도**") — 아래 별도 항 참조 |
| **수사·마케팅 카피** | 자산이 아니라 체계 / 판을 바꾸다 / 게임체인저 / 혁신적 도약 / 새로운 패러다임 | 사실·구조로 환원 (예: "3단계 등록·배포·통합 체계") |
| **저수준 명령어·도구 축약** | npx로 설치 / 컨플에 올림 / 깃에 푸시 | 기능 수준 추상화 + 기술명 괄호 보조 (예: "배포 패키지(ACP)로 설치") |


**판단 기준**: "장애 리포트·논문에 그대로 실어도 되는 표현인가?" — 감정·비유가 끼면 사실 진술로 교체.

#### 불필요한 부정 프레이밍 회피 (상대가 꺼내지 않은 의혹을 먼저 꺼내지 않음)

**부정으로 지우려는 프레임은 오히려 살아난다.** "경쟁이 아니다"라고 쓰는 순간 독자는 없던 경쟁을 떠올리고, "~에 한정되지 않는다"는 해명은 한정될 수 있다는 의심을 먼저 심는다. 방어 문장은 제기되지도 않은 반론을 문서가 스스로 불러들이는 비용이 있다.

```
✗ Biz플랫폼운영센터 AIOps와는 경쟁이 아닌 분업 구도    ← '경쟁'이라는 프레임을 심음
✓ Biz플랫폼운영센터 AIOps와는 협력 구도

✗ AICE 운영에서 출발한 이름이며, 적용 범위는 특정 시스템에 한정되지 않음
✓ AICE 운영 자동화에서 출발한 이름. {정의 서술}      ← 범위는 뒤 절의 사실이 스스로 보여줌
```

- **판단 기준**: 그 부정을 지우면 문장이 약해지는가? — 안 약해지면 부정은 군더더기다
- **오해 해소는 부정이 아니라 사실 배치로** — 뒤 절에 반례·적용 사례를 놓으면 독자가 스스로 결론에 도달한다(예: 범위 오해는 "타 시스템 적용 시" 서술이 해소)
- **예외** — 상대가 실제로 그 오해를 표명했거나, 문서 다른 곳이 그 오해를 유발할 때는 명시적으로 부정한다. 즉 **부정의 근거가 문서 밖에 실재할 때만** 쓴다
- ⚠ **정당한 대비와 구분** — `기능이 아니라 확산 원가에서 차이 발생`처럼 **독자의 기본 가정을 교정하는 대비**는 유지한다. 없는 프레임을 심는 것(회피)과 잘못된 기본 가정을 바로잡는 것(유지)은 다르다. 이 구분은 기계 점검이 불가능하므로 규칙으로만 둔다

**IT 동작 동사 표준화 (망라 아닌 패턴 트리거)**

IT 도메인에서 빈번하게 쓰이는 일상 동사들은 의미는 통하지만 문서·로그·릴리스 노트에 두면 **격이 떨어지고 검색·번역에 약함**. 표준 IT 동사로 교체.


| 회피 (IT 도메인 구어) | 권장 (표준 IT 동사) | 맥락 예 |
| --- | --- | --- |
| 깔다 / 까는 / 깔아 줌 | 스캐폴딩 / 구성 / 설치 / 프로비저닝 | "환경을 깔다" → "환경을 스캐폴딩한다" |
| 박았다 / 박혀 있다 | 고정했다 / 하드코딩했다 | "시간을 기준축으로 박았다" → "시간을 기준축으로 고정했다" |
| 잡는다 / 잡아 둔다 | 지정한다 / 설정한다 | "run tag만 잡는다" → "run tag만 지정한다" |
| 건드리다 / 손대다 / 손보다 | 수정한다 / 변경한다 | "평가 로직은 건드리지 않는다" → "평가 로직은 수정하지 않는다" |
| 풀리지 않는다 / 못 푼다 | 해결되지 않는다 | "train.py 수정으론 못 푼다" → "train.py 수정으로 해결되지 않는다" |

| 되돌림 / 되돌리다 | 롤백 (rollback) | "아니면 되돌림(discard)" → "아니면 롤백(discard)" |
| 되묻기 / 여러 번 되묻다 | 재질의 / 추가 확인 | "되묻기 금지" → "추가 질의 금지" |

| 얼리다 / 얼린 / 얼림 | 동결한다 / frozen | "얼린 평가기" → "frozen 평가기 (수정 금지)" |

| 밤새 (운영 시간 표현) | 야간 / 무인 / 장시간 | "에이전트가 밤새 반복" → "에이전트가 야간 무인으로 반복" |
| 골라달라 (요청 표현) | 선택을 요청 | "후보면 골라달라고 요청" → "후보면 선택을 요청" |


**예외 — 사용자 자연어 트리거·발화 예시는 보존**:

- 스킬 description의 사용자 발화 키워드(`"환경 깔아줘"`, `"실험 폴더 만들어줘"` 등), README의 호출 예시(`"이 데이터로 ~ 깔아줘"`)는 **트리거 매칭 정확도**를 위해 의역하지 않고 그대로 둠
- 본문 설명·규칙·절차 서술에서만 표준 IT 동사로 교체

**판단 기준**: "이 문장이 영문 릴리스 노트·기술 블로그·API 문서로 번역될 때 자연스럽게 옮겨지는가?" — 깔다·박다·잡다 류는 한국어 일상 동사라 직접 대응 영문 동사가 없고, 표준 IT 동사(scaffold·hardcode·specify·modify·rollback·revert)로 옮길 때 손실이 생김.

### 2.9 주체·조직 표기 (제3자 판독성)

문서는 작성 조직 밖으로 흘러간다. **작성 맥락을 모르는 제3자가 읽어도 "누가 무엇을 하는지" 특정되어야** 하며, 남의 조직을 부르는 방식에는 예의가 걸린다. 아래 3항은 공식 보고서·대외 자료에서 특히 강하게 적용.

#### 2.9.1 1인칭·소속 대명사 회피 — 조직명으로 특정

- `우리`·`우리 팀`·`저희`·`당사`·`자사` 는 **읽는 사람이 누구인지 알 수 없음**. 조직명으로 교체
- 라벨·표 헤더에서도 동일 — `(우리 Agent)` 같은 짧은 표기가 오히려 위험(본문보다 먼저 읽힘)
- **예외**: 회의 발언 인용, self-note(§2.6.2 예외)

| 회피 | 권장 |
| --- | --- |
| `(우리 Agent)` (Summary 라벨) | `(AO Agent)` — 제품·과제명으로 지시 |
| `AO Agent (우리)` (비교표 열) | `AO Agent (서비스플랫폼담당)` |
| `우리 팀이 개발` | `플랫폼엔지니어링팀이 개발` |
| `당사 관측 스택` | `Datadog 관측 스택` (주체가 외부면 그 조직명) |

**판단 기준**: 이 문장만 떼어 다른 조직 사람에게 보여줘도 주체가 특정되는가?

#### 2.9.2 타 팀 명칭은 전체 명칭 (약어 규칙의 예외)

- 타 팀 조직명은 **첫 등장 이후에도 축약하지 않고 전체 명칭 유지**. 축약이 곧 결례
- `융합팀` → `융합서비스플랫폼팀` / `커넥티드팀` → `커넥티드플랫폼팀` / `운영기획팀` → `Biz플랫폼운영기획팀` / `Observability팀` → `Biz플랫폼Observability팀`
- 일반 약어는 "첫 등장 1회 풀이 후 축약"(§2.4)이지만 **조직명은 이 규칙을 따르지 않음**
- 우리 팀(플랫폼엔지니어링팀)도 동일하게 전체 명칭. 도식(SVG) 텍스트도 같은 기준
- 점검: `grep -o "[A-Za-z가-힣]*팀" 원고 | sort | uniq -c` 로 축약형 잔존 확인

#### 2.9.3 타 조직의 진척·역량을 임의로 규정하지 않음

- 남의 조직에 대해 쓸 수 있는 것 = **역할**·**협의한 사실**·**상대가 공유한 내용**까지
- 쓰지 않는 것 = 그 조직의 **진척 단계·성숙도·역량 평가**(예: "양측 모두 기획 단계", "아직 설계 전")
- 상대 조직이 직접 공유한 일정·계획은 그대로 인용 가능(출처가 상대이므로)
- 거리 두는 지칭(`상대`·`상대 측`)도 회피 → 조직명

| 회피 | 권장 |
| --- | --- |
| `상대 추진 체계: 2계층 분업, 양측 모두 기획 단계` | `협업 부서 역할: {센터명} 2개 팀과 각각 협의` |
| `상대 솔루션 채택 결정 시점과 연계` | `{팀명} 솔루션 채택 결정 시점과 연계` |

**판단 기준**: 그 조직 사람이 이 문서를 읽어도 문제 삼지 않을 서술인가?

#### 2.9.4 미완료 작업의 완료형 서술 금지

- 검증·계획 단계 내용을 **완료형으로 쓰지 않음**. 제목·요약에서 특히 자주 발생
- `사람의 작업을 무엇으로 대체했는가` → `데이터·처리 로직 비교: 단계·요소별 처리 방식`(대비 서술)
- `구간을 Agent가 대체` → `구간을 Agent가 자동 수행하는 차이`
- **검증 단계 수치는 전제를 명시** — PoC·시범 결과면 "PoC 검증 기준"을 도입부 한 줄로 밝혀 실운영 실적과 구분

## 3. 구조 규칙

### 3.1 섹션 구성 기본 틀

다음 요소는 모든 문서의 공통 구조:

```
YAML 프론트매터 (type·audience·related_docs·created·updated·status·description)   ← 기계 판독 메타
  ↓
# 제목 + 메타블록 (독립 문서 선언·함께 받는 자료)                                  ← 사람이 읽는 헤더
  ↓
## 0. 업데이트 로그  (Living 문서 또는 장기 유지 문서 시)
```

이후 섹션 구성은 고정 틀 없음. 문서가 담는 내용의 특성과 독자의 이해 흐름에 맞게 필요한 섹션을 직접 정의. 단, 자립성 원칙(§1)과 위에서 아래로 한 번 읽어 결론까지 따라갈 수 있는 순서는 유지.

#### YAML 프론트매터 표준 (필수)

모든 문서는 본문 최상단(`# 제목`보다 위)에 YAML 프론트매터 포함. 문서 구조 메타(유형·독자·참조·작성일·상태·요약)의 **SSoT**.

```yaml
---
type: adr
audience: 코어 엔진 개발자 · 아키텍처 결정권자
related_docs:
  - docs/STRATEGY-AGENT-STUDIO-CORE-ENGINE-2026-06-29-2152.md (3사상 — 이 결정이 지켜야 할 계약)
  - core/compiler/compile.py (구현 지점)
  - CLAUDE.md (루트 §4 확장 사다리)
created: 2026-06-30 14:30
updated: 2026-07-10
status: active
description: "먼저 결론 한 문장(무엇을 결정·판정했는가). 그다음 배경과 개요 1~2문장."
---
```

- **필수 필드**: `type`·`audience`·`created`·`status`·`description`
- `description`은 **결론 한 문장 먼저**, 이어 배경·개요 1~2문장 — 문서 생성 이유·목적이 드러나게 (§0 요약표·메모리 P0 프론트매터 표준과 동일)
- `related_docs`는 `경로 (괄호로 관계 한 줄)` 형태 — 선행 계약·구현 지점·상위 규칙 등. 없으면 생략
- `updated`는 갱신 시에만. `status`는 `active`·`draft`·`archived` 등
- **역할 분리(중복 회피)**: 목적=`description`, 독자=`audience`, 상태=`status`, 작성일=`created`/`updated`, 참조=`related_docs`는 **프론트매터가 SSoT**. 아래 블록quote 메타블록은 사람이 첫 화면에서 읽을 **독립 문서 선언·부속 자료**만 담고, 겹치는 필드는 반복하지 않음(반복 시 프론트매터 우선)

#### 메타블록 표준 템플릿

프론트매터 아래 `# 제목` 직후에 배치 — 사람이 읽는 헤더. 프론트매터가 담은 구조 메타는 반복하지 않고, 독립 선언·부속 자료 중심으로 작성:

```markdown
# {문서 제목}

> **독립 문서**: 본 문서는 외부 참조 없이 단독 이해 가능하도록 구성. §N에 전체 맥락·전제·용어 정의 인라인.
> **함께 받는 자료** (해당 시): {경로 — 단독 전달 시 동작 불가한 부속 자료}
```

- **필수 항목**: 독립 문서 선언 (구조 메타 — 목적·독자·상태·작성일·참조 — 는 프론트매터가 담음)
- **선택 항목**: 함께 받는 자료(해당 시)
- 장기 유지 문서는 사람이 읽는 갱신 이력을 `## 0. 업데이트 로그` 섹션에 별도 서술 (프론트매터 `updated`는 최신 날짜만)

### 3.2 섹션 제목 스타일

섹션 제목은 그 섹션의 **내용 자체를 가리키는 명사구** 한 덩어리. 카피라이팅·사설 논조·수사적 표현 금지.

**원칙**

- **명사구 한 덩어리** — 동사·의문문·서술문 금지 ("~~한다", "~~하는가", "~하기" 모두 회피)
- **사설 논조 금지** — "왜 ~~가 필요한가", "~~의 의미", "~이 답하는 질문" 같이 논설·수사 톤 회피. 그 섹션이 다루는 대상을 그대로 명사구로 표기
- **부연 dash(`—`) 금지** — `## N. 본제목 — 부연설명` 패턴 사용 안 함. 부연이 꼭 필요하면 본제목 안에 명사구로 흡수하거나, 괄호·콜론으로 처리
- **가운뎃점(`·`)·괄호(`( )`)·콜론(`:`)은 허용** — 병렬 명사·간단 부연·종속 라벨 표기에 사용 가능

**회피 → 권장 대체 패턴**


| 회피 (사설·수사·부연 dash)                         | 권장 (담백 명사구)                               |
| ------------------------------------------ | ----------------------------------------- |
| "왜 에이전트 분리가 필요한가"                          | "에이전트 분리의 필요성"                            |
| "본 가이드가 답하는 질문"                            | "가이드 범위" / "다루는 주제"                       |
| "한눈에 보기"                                   | "개요"                                      |
| "가이드 적용 후 얻는 것"                            | "기대 효과"                                   |
| "배경 — 계약 기반 설계"                            | "배경"                                      |
| "검증 — Smoke Test"                          | "Smoke Test"                              |
| "Phase 0 — 사전 결정 (7항목)"                    | "Phase 0: 사전 결정 (7항목)" / "Phase 0. 사전 결정" |
| "[Contract-1] `autoresearch.toml` — 메타데이터" | "[Contract-1] `autoresearch.toml` 메타데이터"  |
| "에이전트별 차이 + 마이그레이션 가이드"                    | "에이전트별 차이와 마이그레이션"                        |


**판단 기준**: 제목만 떼어 들고 다른 문서 목차에 넣어도 어색하지 않은가? — 어색하면 수사적 톤이 끼어 있음.

**예외 — 임원·부문 보고**: 위로 올리는 보고서는 제목이 주장을 담는 **행위 서술형 명사구**를 허용(`운영자가 담당 서비스를 관제하기 쉽게 Agent 통합 환경 제공`). 목적절 + 수단·행위 + 명사형 종결 구조이며, 규칙 본문은 executive.md R11. 일반 실무 문서는 본 절의 담백 명사구가 그대로 기본.

### 3.3 섹션 깊이와 번호 부여

문서 섹션은 **최상위 한 단계에만 번호 부여**, 그 아래 하위 주제는 **번호 없이 제목만**. 깊이는 `###`까지.

**원칙**

- 최상위 섹션(`## N. 제목`)에만 번호 — `## 1. 개요`, `## 4. 사용법` 형태
- 하위 주제는 `### 제목`으로 제목만. `### 3.1`, `### 4.2` 식 다단 번호 금지
- 깊은 다단 번호(`§3.1.2`)는 스캔·구두 참조 부담이 크고, 섹션 추가·삭제 시 번호가 흔들려 cross-reference 취약. 하위는 제목 자체로 식별
- **최대 깊이 `###`** — `####` 이하 금지. 깊이가 깊어지면 가독성 저하. 더 나눌 내용이면 표·리스트·blockquote로 구조화하거나 최상위 섹션을 별도로 분리

**예시 — autoresearch-scaffold README §4**

```
## 4. 사용법              ← 최상위(##), 번호 O
### 호출                  ← 하위(###), 번호 X (제목만) — 최대 깊이
### 동작 흐름             ← 하위(###), 번호 X
### 스캐폴딩 후 루프 시작   ← 하위(###), 번호 X
```

**판단 기준**: 하위 제목을 부르려고 "3점1" 같은 번호를 읽어야 하면 무번호 제목으로 교체. `####`가 필요해지면 섹션 설계를 다시 점검.

### 3.4 파일 명명 규칙

산출물 마크다운 파일명은 아래 컨벤션 준수.

- **형식**: `{PREFIX}-{설명}-{YYYY-MM-DD-HHMM}.md`
- **PREFIX**: `PRD`·`STRATEGY`·`PLAN`·`RESEARCH`·`REPORT`·`GUIDE`·`ANALYSIS`·`ADR`·`NOTE`·`DOCUMENTATION` 등 문서 유형
- **표기**: PREFIX·설명 모두 **대문자**, 하이픈 구분 (예: `REPORT-COMPREHENSIVE-2026-04-13-2041.md`)
- **타임스탬프**: 작성 시각 `YYYY-MM-DD-HHMM` (예: `2026-07-11-1714`)
- **저장 위치**: 프로젝트 폴더맵(`CLAUDE.md`) 우선. 폴더맵에 위치 지정이 없으면 `docs/`

## 4. 시각 요소

### 4.1 ASCII 다이어그램 우선

- 구조·flow·아키텍처는 ASCII로 (mermaid 는 명시적으로 사용자 요청이 있을 때만 적용)
- Git diff 가독성 + Confluence·텍스트 뷰어 호환성
- 박스 드로잉 문자: `┌─┐│▼↓→↔`
- **반드시 코드 블록(`````) 안에 작성** — 일반 텍스트 삽입 시 Confluence에서 비례폭 폰트로 렌더링되어 정렬 깨짐

### 4.2 표 우선

- 매핑·비교·기준·상태·R&R·일정은 전부 표
- 실무자가 **스캔하여 빠른 의사결정** 가능하도록 설계
- 헤더 굵게, 핵심 컬럼 값도 굵게

### 4.3 이모지 마커 체계


| 마커  | 의미       | 용도               |
| --- | -------- | ---------------- |
| 🟢  | 사실·검증 완료 | 확정된 사실, 통과한 게이트  |
| 🟡  | 확인 필요·보류 | 후속 검증 필요, 조건부 결론 |
| 🔴  | 추정       | 근거 부족, 추론 기반 서술  |
| 🚫  | 불가·차단    | 범위 외, 현재 불가능     |
| 💡  | 인사이트     | 발견·해석 하이라이트      |
| ★   | 핵심·주목    | KEEP 이벤트, 합의사항   |
| ✅   | 충족       | 기준 통과 체크리스트      |
| ❌   | 불충족·회피   | 반례·의미하지 않는 것     |


**축 구분**: 🟢/🟡/🔴 = **확신도 축** (사실·확인·추정), ✅/❌ = **게이트 축** (충족·불충족), 🚫 = **상태 축** (범위·가능성).

### 4.4 분류 칩 (표 안 범주 표기)

위 마커가 "얼마나 확실한가·통과했는가"를 말한다면, 분류 칩은 **"어느 범주에 속하는가"**를 말함. 축이 다르므로 이모지 마커로 대신하지 않음.

- 표기 = 짧은 범주 명사 한 덩어리(`관제`·`장애`·`자원·비용`·`변경관리`·`거버넌스`·`PoC`). 문장·설명 금지
- 한 표 안에서 칩 어휘 집합을 고정 — 같은 범주를 두 이름으로 부르지 않음
- Confluence 게시 시에는 status 매크로로 렌더링. 로컬 마크다운에서는 백틱(`` `관제` ``) 또는 셀 그대로 표기
- 진행 단계 표기(`완료`·`진행 중`·`계획`)는 **상태 칩**이며 분류 칩과 다른 열에 둠 — 한 열에 섞지 않음


### 4.5 Blockquote 콜아웃

- `> 💡 ...` — 인사이트
- `> **주의**: ...` — 주의 사항
- `> **키워드 해설**: ...` — 용어 정의 블록

### 5.1 "한 줄 정의" 패턴

대상·개념·팀을 한 줄로 정리.

```markdown

> - 융합서비스플랫폼팀 SPOT 원 보고서와 동일 정규화 축
```
