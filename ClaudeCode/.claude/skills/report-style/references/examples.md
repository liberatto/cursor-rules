# 설명형 문서 예시 8편 (비전문 독자 대상) — report-style 참조

> report-style 스킬 [C] 레이어의 예시 자료. 규칙은 readability.md, 실제 문장의 모양은 이 파일. 비전문 독자용 설명형 문서를 쓸 때 **본문 작성 전에 아래 장르 목록에서 가장 가까운 한두 편을 골라 읽고 그 골격·어조로 작성**. 여덟 편 전부를 매번 읽지 않음 — 파일이 길어 비용이 크고, 먼 장르의 골격은 섞이면 오히려 방해.

---

## 사용법

- 예시는 규칙의 보조가 아니라 **작성의 출발점**. 규칙 목록(readability.md §7.1)은 경계를 정하고, 예시는 그 안에서 문장이 실제로 어떤 모양인지 보임
- 요청받은 주제를 가장 가까운 장르의 골격에 얹어 작성. 장르 여덟 가지 — 아래 표에서 고른 뒤 해당 예시만 읽음

| 장르 | 예시 | 이 골격이 맞는 요청 |
| --- | --- | --- |
| 소개 | 1 | 한 대상의 특징을 정리해 달라 |
| 비교 | 2 | 둘 중 무엇을 고를지 |
| 원리 설명 | 3 | 어떤 기술·개념이 어떻게 동작하는지 |
| 판단·권고 | 4 | 하나를 놓고 도입할지 말지 |
| 경위·원인 | 5 | 무슨 일이 있었고 왜 그랬는지 |
| 숫자 해석 | 6 | 측정값·점수가 실제로 무엇을 뜻하는지 |
| 통념 교정 | 7 | "~라고 들었는데 맞는가" — 독자가 이미 오해를 가진 경우 |
| 절차 안내 | 8 | 독자가 직접 따라 할 순서 |

- **베낄 것 = 골격과 어조.** 결론 문단 → 번호 절 → 절마다 사실 문장 뒤 결과 문장 → 비교는 표 먼저 → 마지막 절은 선택 기준
- **베끼지 말 것 = 주제와 수치.** 여덟 편의 제품명·가격·벤치마크·사건 수치는 예시 작성 시점의 값이며 검증하지 않음(🔴 추정). 새 문서에 그대로 옮기지 않음
- 예시의 첫 문단이 readability.md 규칙 1의 섹션 0(30초 블록)에 해당. 문서가 길어지면 `## 0.` 절로 승격
- 어미는 명사형(core.md §2.1). 예시 원문은 존댓말 대화 답변이었으나 명사형으로 다시 씀 — 골격과 어조는 어미와 무관하게 유지

## 공통 골격

```
결론 문단 (무엇을 다루는 문서인지 + 핵심 한 줄 + "N가지로 정리" 예고)
  |
  v
## N. 명사구 제목 (판정·수치를 괄호나 콜론으로 부연)
  - 사실 문장 (수치 포함)
  - 결과 문장 ("이로 인해 ~", "그 결과 ~")   <- 사실 한 번, 뜻 한 번
  |
  v
비교 문서: 표를 먼저, 이후 절은 표의 행을 풀어 씀
원리 문서: 절마다 원리 · 예 · 결과 세 라벨
판단 문서: 얻는 것 절 → 잃는 것 절(같은 크기) → 권고 절
경위 문서: 시각 붙은 시간순 절 → 원인 절(정상 대비 차이 셋) → 복구 → 이후 변화
숫자 문서: 지표마다 개념 · 비유 · 점수별 체감 → 차이의 체감 여부 → 기준선
통념 문서: 오해가 생기는 이유 → 현실(깨지는 지점 셋) → 실무 피해 → 안전장치
절차 문서: 단계마다 실행 · 의미 · 건너뛰면 세 라벨
  |
  v
## 마지막. 선택 기준 · 권고 · 안전장치 (독자가 다음에 무엇을 할지)
```

## 예시 1: 제품 소개 (한 대상의 특징 정리)

- **베낄 것**: 첫 문단의 "무엇을 계승하고 무엇에 초점"이라는 위치 잡기 · 절 제목 괄호의 수치 부연 · 절마다 사실 → 결과 두 문장
- **베끼지 말 것**: 모델명 · 가격 · 벤치마크 수치

```markdown
# Claude Fable 5.1 핵심 특징

Anthropic이 출시한 최상위 프론티어 모델 **Claude Fable 5.1**은 기존 Fable 5를 계승하면서 비용 절감·장시간 에이전트 성능·세이프가드 오탐 감소 세 가지에 초점을 둔 모델. 핵심 특징을 네 가지로 정리.

## 1. 비용 절감 (컨텍스트 캐시 읽기 75% 인하)

- 기본 토큰 가격(입력 $10/1M, 출력 $50/1M)은 동일하나, 캐시 읽기(Cache Reads) 비용을 $1.00에서 $0.25로 75% 인하
- 이로 인해 이전 대화 기록을 계속 불러오는 일반 작업은 약 25%, 대규모 코드·문서 기반의 복잡한 에이전트 작업은 최대 45%까지 비용 절감

## 2. 장기 지평 에이전트(Long-horizon Agentic) 및 코딩 능력 강화

- 단순 일회성 문답을 넘어, 다단계 리서치나 대규모 저장소(Repository) 분석 같은 장시간 연속 실행 작업에 최적화
- 오류를 임시로 우회하는 수준을 넘어 소프트웨어 문제의 근본 원인을 찾아 해결하는 분석력 강화
- 과학 연구용 벤치마크 Terminal-Bench-Science 0.1에서 **52.6%** 기록. 기존 Fable 5(24.7%)·Opus 5(29.0%)의 두 배 수준

## 3. 과도한 보안 차단(오탐) 감소

- 기존 Fable 5의 반복 문제였던 "세이프가드 접촉 시 하위 모델(Opus 등)로 강제 전환되는 현상"을 개선
- 방어 목적의 소프트웨어 취약점 스캐닝에서 사이버 안전장치 개입이 약 60% 감소, 기초 생물학·의료 관련 정상 요청이 차단되던 빈도도 85% 감소. 그 결과 업무 연속성 향상

## 4. 추론 레벨(Effort) 세분화 및 AI 워터마크 도입

- 작업 난이도에 따라 Low·Medium·High·XHigh·Max 5단계의 추론 레벨을 설정해 토큰 소모량과 비용 조절 가능
- EU AI법 준수를 위해, 사람이 읽을 때는 보이지 않으나 텍스트·파일 출력에 Claude가 작성했음을 증명하는 AI 워터마크 기술을 최초 적용
```

## 예시 2: 두 대상 비교 (선택 기준까지)

- **베낄 것**: 첫 문단의 "같은 점 하나, 다른 점의 방향" 위치 잡기 · 표를 먼저 두고 절 제목에 판정을 싣기 · 절 안에서 두 대상을 굵은 라벨로 매번 명시 · 마지막 절의 상황별 선택 기준
- **베끼지 말 것**: 모델명 · 지수 · 벤치마크 수치 · 프로그램명

```markdown
# Claude Fable 5.1 vs GPT-6 Astra 비교

Anthropic의 Claude Fable 5.1과 OpenAI의 GPT-6 Astra는 2026년 9월 기준 양사의 최상위 모델. 기본 API 가격(입력 $10/1M, 출력 $50/1M)은 동일하나, 강점의 방향과 세부 성능 구조에서 차이 발생. 제삼자 벤치마크 기관(Artificial Analysis 등)과 양사 발표를 기준으로 비교.

## 1. ★ 핵심 비교

| 비교 항목 | Claude Fable 5.1 | GPT-6 Astra |
| --- | --- | --- |
| 종합 지능 | **우세** (Intelligence Index 66) | 61 |
| 컴퓨터 유즈 (OS·브라우저 제어) | 추격 중 (안정성 위주) | **우세** (탐색 속도·다중 앱 제어) |
| 지속 코딩 (에이전트) | **우세** (컨텍스트 창 안 '지속 노트' 관리 유리) | 동등 또는 단일 벤치마크 미세 우세 |
| 수학·과학 추론 | FrontierMath Tier 4: 87.8% | **우세** (FrontierMath Tier 4: 97.6%) |
| 프롬프트 캐싱 비용 | **저렴** ($0.25/1M 토큰) | $1.00/1M 토큰 |
| 사이버 보안 역량 | 오탐 감소 중심 | Critical 등급 판정 (제한 공개) |

## 2. 지능과 추론: 종합 지능은 Fable 5.1, 수학·과학은 Astra

- **Fable 5.1**: 독립 종합 지능 지수(Intelligence Index) 66점. 복잡 문맥 추론과 언어·도구 융합 능력에서 Astra에 앞섬
- **GPT-6 Astra**: 수학·논리에 특화. FrontierMath Tier 4에서 97.6%를 기록해 미해결 수학 문제 해결 사례 보유, ARC-AGI-3 99.9%

## 3. 에이전트와 코딩: 반복 캐싱 vs 컴퓨터 제어 속도

- **Fable 5.1**: 프롬프트 캐시 읽기 비용은 Astra의 4분의 1($0.25). 이전 대화와 코드를 계속 읽으며 수 시간 동작하는 장기 지평(Long-horizon) 에이전트 루프에서는 비용·효율 면에서 Fable 5.1이 유리
- **GPT-6 Astra**: 브라우저·OS 화면을 직접 보고 제어하는 Computer Use 속도가 전 세대 대비 1.9배. 단일 코딩 작업(DeepSWE 등)과 터미널 환경 제어에서는 Astra가 빠름

## 4. 사이버 보안과 안전 정책의 차이

- **Fable 5.1**: 보안 진단·의학 연구 요청을 과도하게 차단하던 오탐(False Positive)을 줄여, 실무자의 연속 업무를 돕는 방향
- **GPT-6 Astra**: OpenAI 최초로 Preparedness Framework 기준 Critical 사이버 역량 판정. 사람 개입 없이 취약점 탐색과 익스플로잇 체인 구성이 가능한 수준이며, 그 때문에 해당 기능은 Daybreak 프로그램 등 검증된 소수 파트너에게만 제한 공개

## 5. 💡 선택 기준

- **Claude Fable 5.1**: 대규모 소스코드 분석, 장시간 실행되는 분석용 상주(persistent) 에이전트 구축, 프롬프트 캐싱을 활용한 비용 최적화가 필요할 때
- **GPT-6 Astra**: 크로스 애플리케이션 제어(화면 UI 직접 조작), 고난도 수학·물리 계산, 초고속 웹 브라우징 기반 자동화가 필요할 때
```

## 예시 3: 원리 설명 (단계별 개념 도입)

- **베낄 것**: 첫 문단의 핵심 원리 한 구절(따옴표) + 단계 수 예고 · 절 제목의 비유 별명(이해를 단축할 때만) · 절마다 원리 · 예 · 결과 세 라벨 · 일상 문장으로 든 예
- **베끼지 말 것**: 단계 수 · 용어 · 예문 자체

```markdown
# LLM 학습 원리 3단계

대규모 언어 모델(LLM)의 핵심 학습 원리는 "다음에 올 단어 맞히기". 방대한 텍스트를 읽으며 이 단어 뒤에 어떤 단어가 오는 것이 가장 자연스러운지 확률을 계산하는 방법을 배우는 과정. 학습은 크게 3단계로 구분.

## 1. 사전 학습(Pre-training) · 무작정 다독하기

아무것도 모르는 AI에게 인터넷의 책·논문·뉴스·위키피디아·소스 코드를 통째로 읽히는 단계.

- **원리**: 다음 단어 예측(Next-Token Prediction). "지구는 태양 주위를 ___"라는 문장을 주면 뒤에 올 단어가 '돈다'일 확률이 높다는 것을 통계적으로 학습
- **결과**: 언어의 문법, 세상의 지식, 코딩 규칙을 이해한 상태. 단 사람의 질문에 '답변'하는 법은 아직 모름(백과사전 그 자체)

## 2. 미세 조정(Supervised Fine-Tuning, SFT) · 과외 선생님에게 배우기

사전 학습된 모델에게 사람이 원하는 '질문과 답변' 형태를 가르치는 단계.

- **원리**: 사람 전문가가 작성한 고품질 [질문 - 올바른 답변] 데이터셋으로 학습
- **예**: [질문] "양자역학이 뭐야?" → [답변] "매우 작은 입자들의 움직임을 연구하는 물리학입니다."
- **결과**: 혼자 소설을 이어 쓰는 수준을 넘어, 사용자의 질문(프롬프트)에 맞는 답을 내놓는 '챗봇' 형태 확보

## 3. 인간 피드백 기반 강화학습(RLHF) · 칭찬과 꾸중으로 다듬기

사람의 가치관에 맞게 안전하고 유용한 답변을 하도록 최종 조율하는 단계. 최근에는 사람 대신 AI가 피드백을 주는 RLAIF 방식도 병행.

- **원리**: AI가 한 질문에 여러 답변 후보를 만들면 사람(또는 평가 모델)이 어떤 답변이 더 유익하고 안전한지 점수(리워드)를 부여. AI는 더 높은 점수를 받도록 답변 방식을 조정하며 학습(강화학습)
- **결과**: 욕설·편향 발언·위험 정보(폭탄 제조법 등)를 제외하고, 사용자에게 가장 친절하고 유용한 답변을 생성하는 상태

## 4. 학습을 가능하게 하는 핵심 기술: 트랜스포머(Transformer)

세 단계 전부의 바탕에 트랜스포머라는 인공신경망 구조가 있음. 핵심은 어텐션(Attention, 주목) 메커니즘.

- **원리**: 문장 안에서 단어와 단어 사이의 관계를 파악하는 기술
- **예**: "그는 은행에 가서 돈을 뽑았다"와 "그는 강가 은행에 앉아 쉬었다"에서 '은행'이 각각 금융기관과 강가를 뜻한다는 것을 앞뒤 문맥으로 구별
- **결과**: 같은 단어라도 문맥에 따라 다른 뜻을 정확히 처리 가능
```

## 예시 4: 판단·권고 (단일 대상의 채택 여부)

- **베낄 것**: 첫 문단에 찬반 결론과 조건을 함께 싣기 · 얻는 것 절과 잃는 것 절을 같은 크기로 · 마지막 절은 양자택일 대신 단계별 권고
- **베끼지 말 것**: 기술명 · 팀 규모 · 기간·인원 수치

```markdown
# MCP 도입 검토: 10명 개발팀 기준

결론은 도입을 적극 검토하되, 전체 시스템 적용이 아니라 **소규모 시범 도입(PoC)부터 시작**. 10명 규모 팀이 다수의 사내 시스템을 다루는 상황이라면 MCP(Model Context Protocol, AI가 사내 시스템에 접속하는 표준 연결 규격)는 장기적으로 팀 생산성을 크게 올릴 수 있는 도구. 다만 기술이 신생 단계이므로 위험 요소를 관리하며 접근 필요.

## 1. 도입했을 때 얻는 것

- **내부 데이터 활용**: AI(예: Claude)가 사내 위키·이슈 트래커·소스 코드·DB 등 흩어진 시스템의 데이터를 직접 조회하고 분석 가능
- **개발·운영 자동화**: 관리자 수준에서 "A 시스템의 최근 오류 로그를 분석해 리포트를 써 달라"고 자연어로 지시하면, AI가 MCP를 통해 해당 시스템에 접속해 데이터를 가져와 분석
- **AI 도구 선택의 자유**: 하나의 표준 규격을 따르므로, 나중에 AI 모델이나 도구를 바꿔도 사내 시스템 연동 코드를 처음부터 다시 만들 필요 없음

## 2. 도입했을 때 잃는 것

- **초기 개발·유지보수 공수**: AI가 사내 시스템과 소통하도록 연결 다리(MCP 서버)를 만드는 데 개발팀 공수 투입 필요
- **보안·권한 관리 위험**: AI가 사내 데이터에 직접 접근하므로, 접근 권한을 잘못 설정하면 민감 정보 유출이나 원치 않는 시스템 변경 발생 가능
- **기술 미성숙**: MCP는 공개된 지 오래되지 않은 초기 기술. 규격이 자주 바뀌거나 참고 사례가 부족해 시행착오 가능

## 3. 💡 권고: 3단계 접근

10명 규모 팀은 대기업보다 빠르고 유연하게 신기술을 시험할 수 있음. 따라서 '전면 도입'과 '도입 보류'의 양자택일이 아니라 단계별 접근 권고.

- **1단계 (시범 도입)**: 팀에서 가장 자주 쓰지만 보안 위험이 적은 시스템 하나(예: 사내 위키 조회 또는 API 문서 검색)를 지정해, 2~3명 규모로 2주간 프로토타입 구축
- **2단계 (평가)**: 팀원들이 실제로 업무 효율 향상을 체감하는지, 보안상 허점은 없는지 검토
- **3단계 (확장)**: 효과가 확인되면 다른 사내 시스템으로 연동을 차례로 확장
```

```markdown
# 2022년 카카오 서비스 장애 경위

2022년 10월 15일에 발생한 카카오 서비스 장애는 국내 IT 역사상 가장 큰 규모의 통신 장애 사건. 디지털 기반 시설이 멈췄을 때 초연결 사회가 얼마나 취약해지는지 보여준 대표 사례. 시간 순서와 단계별 원인을 네 절로 정리.

## 1. 사건의 시작: 판교 데이터센터 화재

카카오의 핵심 시설 중 하나가 불타면서 시작.

- **오후 3시 19분 (화재 발생)**: 경기도 성남시 판교 SK C&C 데이터센터 지하 3층 배터리실에서 전기적 요인으로 화재 발생. 이 데이터센터는 카카오가 전체 서버의 상당수(약 3만 2천 대)를 두고 주 기지로 쓰던 곳
- **오후 3시 33분 (전력 차단)**: 진화 과정에서 데이터센터 전체 전원 차단. 물을 뿌려 진화해야 하므로 감전과 장비 고장을 막기 위한 불가피한 조치
- **오후 3시 30분 이후 (전면 중단)**: 전기가 끊기자 카카오톡 메시지 전송 오류를 시작으로 카카오T(택시)·카카오페이(결제)·카카오내비·다음(Daum) 포털 등 카카오의 모든 서비스가 한꺼번에 중단

## 2. 피해가 커진 원인 세 가지

대형 IT 기업은 한곳이 멈춰도 다른 곳이 바로 이어받도록 시스템을 복제해 두는 '이중화' 작업을 해 둠. 같은 데이터센터에 입주해 있던 네이버도 일부 타격을 입었으나 몇 시간 만에 서비스 정상화. 반면 카카오가 127시간(5일 이상) 동안 완전 복구를 못 한 이유는 세 가지.

- **운영 도구를 한곳에 집중 (운영 도구 이중화 미흡)**: 데이터 자체는 다른 지역 데이터센터들에 나눠 저장해 두었으나, 서버를 제어하고 서비스를 가동하는 '개발자용 운영·배포 시스템'은 판교 데이터센터 한 곳에만 배치. 지휘 통제실이 불타자 다른 지역의 정상 상태 서버조차 동작 불가
- **서비스 간 의존 관계 과다**: 카카오톡·카카오페이·카카오 로그인 등이 서로 복잡하게 연동. 하나가 고장 나자 다른 서비스까지 연쇄 중단
- **데이터센터 전체 중단 훈련의 부재**: 일부분이 고장 나는 상황만 연습했을 뿐, 데이터센터 한 곳이 통째로 사라지는 극단 시나리오에 대한 대비·훈련 없음

## 3. 복구 과정

지휘 통제실이 사라진 상태라 개발자들은 시스템 자동 전환을 포기하고 사실상 수동으로 시스템을 하나씩 재구축.

- **원격 접속의 한계**: 복구를 위해 회사 내부망(VPN)에 접속하려 했으나 이 접속 시스템마저 마비되어 초기 대응이 1시간 이상 지연
- **밤샘 수동 복구**: 개발자들이 직접 다른 데이터센터에 운영 도구를 설치하고 설정을 바꿔 가며 시스템을 하나씩 재가동
- **단계별 정상화**: 화재 약 10시간 뒤인 16일 새벽부터 카카오톡 문자 전송 등 필수 기능 복구. 이후 이미지 전송·쇼핑·금융 서비스가 순차 재개. 5일이 지난 10월 20일에야 모든 서비스 정상화

## 4. 이후의 변화와 대책

전 국민의 일상을 멈추게 하며 독점 플랫폼의 위험을 알린 사건. 이후 정부와 카카오가 대대적인 개선에 착수.

- **최고경영자 사퇴와 피해 보상**: 당시 남궁훈 카카오 대표가 책임을 지고 사퇴. 피해를 입은 소상공인과 일반 사용자에게 수백억 원 규모의 보상(이모티콘 지급·현금 보상) 실행
- **기술 개선 (다중화)**: 운영 도구를 여러 데이터센터에 분산하는 다중화를 완료하고, 한 센터가 통째로 사라져도 즉시 다른 곳이 역할을 이어받는 액티브-액티브(Active-Active) 체계 구축. 2024년에는 재난 방지 설계를 적용한 첫 자체 데이터센터(안산) 완공·운영
- **'카카오 먹통 방지법' 통과**: 방송통신발전기본법 등 3개 법안을 개정해, 카카오 같은 대형 부가통신사업자도 국가 기간통신사(KT·SKT 등)처럼 재난 관리 의무 대상에 포함. 정부가 이들의 데이터센터 관리 상태를 정기 점검·감독
```

```markdown
# AI 벤치마크 점수 해석: MMLU·HumanEval

AI 모델 성능 평가에서 가장 자주 언급되는 두 지표는 AI의 '지식 수준'과 '코딩 능력'을 재는 모의고사. 통계 용어 없이 관리자 관점에서 각 점수의 뜻과 점수 차이의 체감 여부를 정리.

## 1. 각 점수의 뜻

### MMLU (Massive Multitask Language Understanding): 상식·전공 지식 시험

- **개념**: 고등학교 수준 상식부터 대학 수준 의학·법학·역사·컴퓨터 과학까지 57개 과목의 객관식(4지선다) 문제를 풀게 하는 시험
- **비유**: 수능과 전문 자격증 시험을 합쳐 놓은 종합 학력 테스트
- **점수별 체감 수준**:
  - 60%대 (보통): 일반 대화는 무리 없으나, 전문 지식을 물으면 틀린 답(환각)을 자주 냄
  - 75%대 (우수): 웬만한 분야의 전공자 수준 지식. 보고서 초안 작성 가능
  - 85% 이상 (최고 수준): 각 분야 전문가(의사·변호사 등) 집단의 평균 점수(약 80~85%)를 넘는 수준. 복잡한 사업 전략이나 전문 자문에 적합

### HumanEval: 코딩·논리력 시험

- **개념**: AI에게 코딩 문제를 주고 조건에 맞는 파이썬(Python) 코드를 직접 작성하게 한 뒤, 그 코드가 오류 없이 실제로 동작하는지 확인하는 시험
- **비유**: 개발자 채용 코딩 테스트(실기 시험)
- **점수별 체감 수준**:
  - 60%대: 기초 코드만 작성 가능. 현업 개발자가 고쳐 쓰는 양이 더 많음
  - 75%대: 주니어 개발자 수준. 명확한 지시를 주면 기능 하나를 혼자 구현
  - 90% 이상: 시니어 개발자 수준의 논리력. 복잡한 시스템 알고리즘 작성, 사람이 짠 복잡한 코드의 버그 발견 가능

## 2. 1~2%p 차이의 체감 여부

결론은 "고점 구간에서의 1~2%p 차이는 업무에서 크게 체감되나, 일반 구간에서의 차이는 사람이 느끼기 어려움".

- **90%대에서의 1%p 차이 (체감 큼)**: HumanEval 90% → 92%는 "10번 중 1번 틀리던 모델이 12~13번 중 1번 틀리는 수준"으로 바뀐 것. 오답 확률이 20~30% 줄어든 것이므로, 실무자가 AI 결과물을 검토·수정하는 시간(검수 비용)이 크게 감소
- **70%대에서의 1~2%p 차이 (체감 없음)**: 71%나 73%나 10번 중 3번꼴로 틀리는 것은 같음. 사용자에게는 똑같이 '종종 틀린 답이나 버그를 내는 AI'로 인식

## 3. 💡 관리자용 해석 요령

- **텍스트 업무 최소 기준 (MMLU 75% 이상)**: 사내 문서 요약·이메일 작성·기본 고객 응대에 도입 가능한 수준
- **코딩 보조 최소 기준 (HumanEval 80% 이상)**: 개발팀에 'AI 코딩 비서'로 도입해 생산성을 올릴 수 있는 하한선
- **점수만으로 판단하지 않음**: AI 회사가 자기 모델에 유리한 문제만 골라 학습시켜 벤치마크 점수를 올리는 경우가 있음. 점수는 '예선 통과 여부'를 보는 참고 자료로만 쓰고, 본선(도입 검토)에서는 회사의 실제 데이터로 짧게 시험(PoC)하는 것이 가장 정확
```

## 예시 7: 통념 교정 (독자가 이미 가진 오해 바로잡기)

- **베낄 것**: 첫 문단에서 오해를 인용부호로 그대로 적고 한 문장으로 판정 · "왜 그렇게 믿기 쉬운지"를 먼저 인정한 뒤 현실로 · 현실 절은 오해가 깨지는 지점을 셋으로 · 오해가 실무에서 망가뜨리는 결과까지 · 마지막 절은 안전장치
- **베끼지 말 것**: 기술명 · 예시 부서·사고 유형

```markdown
# RAG와 환각: "사내 문서를 연결하면 정확한 답만 나온다"는 오해

결론은 "RAG를 쓰면 AI의 거짓말(환각)을 크게 줄일 수는 있으나, 완전히 없애지는 못함". 사내 문서를 연결해 두어도 엉뚱한 답이나 틀린 답이 여전히 나올 수 있음. 왜 이런 오해가 생기는지, 그리고 이 오해를 바로잡지 않으면 실무에서 어떤 문제가 생기는지 정리.

## 1. 오해가 생기는 이유

RAG(검색 증강 생성, Retrieval-Augmented Generation)의 동작 방식이 '오픈북 시험'과 닮았기 때문.

- **기술 매체의 단순화된 설명**: "AI가 자기 기억(학습 데이터)만으로 답하면 틀린 말을 하니, 사내 문서라는 '교과서'를 쥐여 주고 거기서만 답을 찾게 만드는 기술이 RAG"라는 설명이 많음
- **상식적인 추론**: 똑똑한 AI에게 교과서를 주고 "여기서만 찾아서 답하라"고 했으니 당연히 틀린 답이 나올 리 없다고 생각하게 됨

## 2. 현실: 환각이 다시 발생하는 세 지점

RAG는 완결된 기술이 아니라 [문서 검색 단계]와 [AI의 독해 단계]가 결합된 시스템. 이 과정의 다음 세 지점에서 환각이 다시 발생.

- **엉뚱한 문서를 찾아 줌 (검색의 한계)**: 사용자가 질문하면 시스템이 사내 문서 수천 장 중 관련 없는 문서(과거 버전, 다른 부서 문서)를 찾아 AI에게 넘기는 경우가 많음. AI는 잘못 배달된 교과서를 바탕으로 오답 생성
- **맞는 문서를 보고도 오독함 (AI의 한계)**: 맞는 문서를 찾아 주었더라도 내용이 방대하거나 복잡하면 AI가 문맥을 오해해 엉뚱한 수치를 조합하거나 인과관계를 반대로 해석
- **사내 문서 자체가 틀림 (데이터의 한계)**: 연결해 둔 사내 문서에 예전 규정이나 잘못된 데이터가 적혀 있으면, AI는 그 틀린 내용을 확신에 찬 어조로 정확하게 답변

## 3. 이 오해가 실무에서 망가뜨리는 것

"RAG를 도입했으니 100% 정확하다"는 오해를 가지고 실무에 적용하면, 'AI가 틀린 답을 냈다'로 끝나지 않고 업무 전반에 피해 발생.

- **검수 절차의 실종, 법적·재무 사고로 연결**: 사용자가 AI 답변을 무조건 신뢰. 사내 규정을 묻는 인사팀 직원이나 계약서 조항을 확인하는 법무·영업팀 직원이 AI 답변만 믿고 고객 응대나 계약을 진행했다가 소송이나 과징금 처분으로 이어질 수 있음
- **잘못된 경영 의사결정**: 관리자나 임원이 "사내 데이터 기반 AI 리포트"라는 말만 믿고 수치를 신뢰했다가, 실제와 다른 시장 전망이나 재무 분석을 바탕으로 사업 방향 결정
- **개발팀과 현업 부서 간 신뢰 붕괴**: 현업 부서는 "100% 정확하다고 해서 썼는데 왜 틀리느냐"고 항의하고, 개발팀은 "기술적으로 100%는 원래 불가능"이라고 답하며 부서 간 갈등 발생. 큰 비용을 들인 AI 시스템이 사내에서 아무도 쓰지 않는 상태로 방치
```

## 예시 8: 절차 안내 (독자가 직접 수행)

- **베낄 것**: 첫 문단에서 도구가 무엇인지 한 줄 비유와 단계 수 예고 · 단계마다 실행·의미·건너뛰면 세 라벨(무엇을 치는가 / 그것이 무슨 뜻인가 / 안 하면 무엇이 막히는가) · 선택 단계는 끝에 분리
- **베끼지 말 것**: 도구명 · 명령어 · 단계 수

```markdown
# Claude Code 설치와 팀 저장소 연결 절차

Claude Code는 일반 챗봇과 달리 내 컴퓨터의 터미널(명령창) 안에서 실행되며 팀의 소스 코드를 직접 읽고 수정하는 '인공지능 개발 비서'. 복잡한 명령어는 걷어내고 핵심 개념과 순서 위주로 정리. 설치부터 팀 저장소(예: GitHub)에 붙이는 과정은 4단계.

## 1. 프로그램 설치

- **실행**: 터미널을 열고 Anthropic 공식 홈페이지가 제공하는 설치 명령 한 줄을 붙여 넣음. Mac은 `curl -fsSL https://claude.ai/install.sh | bash`, Windows는 PowerShell에서 `irm https://claude.ai/install.ps1 | iex`
- **의미**: 스마트폰에 앱을 내려받듯, 내 컴퓨터가 Claude Code를 인식하고 실행할 수 있도록 프로그램 파일을 기본 경로에 설치하는 작업
- **건너뛰면**: 터미널에 `claude`라고 입력해도 "그런 프로그램은 없다"는 오류가 나며 다음 단계로 진행 불가

## 2. 계정 로그인·인증 (최초 1회)

- **실행**: 터미널에 `claude`를 입력하면 일회용 인증 링크나 코드가 표시됨. 브라우저에서 열어 팀이 사용하는 Claude 계정(Pro·Team 등)으로 로그인
- **의미**: 이 비서의 '인건비(API 비용)'를 누가 낼지 지정하고, 정당한 권한을 가진 사용자인지 확인받는 과정
- **건너뛰면**: 설치는 되었으나 AI 모델과 연결되지 않은 상태. 어떤 질문도 명령도 불가

## 3. 팀 저장소 폴더로 이동해 실행

- **실행**: 터미널에서 `cd /팀/저장소/경로`로 팀원들과 함께 쓰는 소스 코드 폴더로 이동한 뒤 다시 `claude` 입력
- **의미**: 비서에게 "오늘부터 분석하고 고쳐야 할 소스 코드는 이 방에 있다"고 작업 공간을 지정하는 것. 이때부터 Claude Code가 해당 폴더의 파일 구조와 코드를 읽기 시작
- **건너뛰면**: 아무 곳에서나 실행하면 비서가 엉뚱한 폴더(바탕화면·다운로드 폴더 등)를 분석하느라 정작 팀 코드는 읽지도 못함. 반드시 팀 저장소 폴더 안에서 실행 필요

## 4. 팀 표준 가이드 생성 (`/init`)

- **실행**: Claude Code가 켜진 상태에서 `/init` 입력. AI가 폴더를 훑어보고 프로젝트에 필요한 기본 규칙 파일(`CLAUDE.md`)을 자동 생성
- **의미**: 새로 온 비서에게 "이 팀은 코드를 이런 규칙으로 짜고 테스트는 이렇게 진행한다"는 업무 인수인계 문서를 작성해 저장소에 두는 것. 이 파일은 Git으로 팀원들과 공유
- **건너뛰면**: 동작은 하나 팀 고유의 코드 스타일·규칙을 모른 채 AI 임의로 코드를 작성. 팀원들이 AI가 만든 코드를 일일이 다시 수정해야 하는 부담 발생

## 5. (선택) GitHub 연동 (`/install-github-app`)

팀이 GitHub를 쓰고 있고, AI가 터미널 안에서뿐 아니라 GitHub 웹사이트에서도 직접 코드 리뷰나 자동 수정을 하기를 원한다면 Claude Code 창에 `/install-github-app`을 입력해 연동 가능. 관리자 관점에서는 1~4단계만 마쳐도 개발팀이 개인 컴퓨터에서 Claude Code를 쓰는 데 문제 없음.
```
