### 8.0 임원 보고 문체 한 줄 정의

> **개조식 명사형 + 볼드 키워드 두괄 + 정량 근거 + 표·화살표 중심의 "의사결정 지향 압축 문체"**

- 완결 서술문이 아니라 **명사로 끝나는 압축 구(句)**가 기본 단위 (§2.1 명사형 종결의 임원보고 강화판)
- 모든 항목은 **볼드 키워드를 앞세워** 결론부터 — 첫 단어만 봐도 요지 파악
- 주장마다 **정량 수치·날짜·상태 칩**으로 근거화 — "잘됨"이 아니라 "리드타임 90% 단축"
- 서술 단락 최소화, **표·화살표 흐름**이 본문을 떠받침 (글보다 구조)
- 목표 인상: 임원이 **30초 안에 핵심·의사결정 포인트**를 잡는 보고서

### 8.1 임원 보고 문장 규칙 (R1~R11)

| # | 규칙 | 핵심 |
| --- | --- | --- |
| R1 | 명사형 종결 | 문장 끝을 `~수립`·`~정리`·`~확보`·`~필요`·`~가능`·`~정착` 등 명사/명사형으로 |

| R3 | 개조식 구 나열 | 만연체 금지. 쉼표로 구 병렬, 한 불릿 = 한 호흡 |
| R4 | 두괄식 인용 블록 | 장·절 도입에 `>` 블록으로 핵심 방향 1~2문장 선언 → 불릿·표 전개 |

| R6 | 정량 수치 볼드 | 효과·현황은 수치 + 볼드. "크게 개선" 류 형용사 최소. 계획·구상 단계로 실측치가 없으면 **지표명 + 방향어**까지는 허용(`MTTR 단축 및 운영 품질 향상`) — 지표명 없는 단독 형용사는 여전히 금지 |

### 8.2 과제·방안 서술 3단 골격

> 모든 추진 방안이 따르는 틀. 방안 서술에 그대로 적용.

```
[ Pain Point ]   현 문제·니즈        ← 이탤릭 세부 가능
 개선사항        To-Be 해결책        ← 볼드 키워드 두괄(R2)
 기대효과        정량·정성 효과       ← 수치 볼드(R6)
 ※ 전략 부연     향후 재활용·연계     ← ※ 마커
```

- Pain Point → 개선 → 기대효과 순서 고정. **기대효과 없는 과제 서술 금지**

#### 표 구현형 (방안이 3개 이상일 때)

같은 3단 골격을 세로로 반복하는 대신 4열 표 한 장으로 압축. 열 이름·셀 작성법 고정.

| 구분 | 기존 (AS-IS) | 변화 사항 (TO-BE) | 기대 효과 |
| --- | --- | --- | --- |
| **A. {방안 명칭}** | 현상 ①<br>현상 ②<br>현상 ③ | **{To-Be 헤드라인}**<br>실행 ①<br>실행 ②<br>실행 ③ | {지표} 향상 및 {지표} 단축 |

- **구분 셀** — `A.`·`B.` 알파벳 접두 + 방안 명칭 볼드. 방안을 구두로 지목할 수 있게 함
- **AS-IS 셀** — 문제 현상을 2~3개 나열, 각 줄 명사형 종결(`각 관제 도구를 개별 접속하여 분석`). 원인 분석·해설 금지, 현상만
- **TO-BE 셀** — **볼드 헤드라인 1줄로 결론 선언** 후 실행 항목 2~3줄. 헤드라인은 그 자체로 방안 명칭이 되게 씀
- **기대 효과 셀** — 지표 2개를 `및`으로 묶은 대구 한 줄(`RCA 정확도 향상 및 분석 시간 단축`·`MTTR 단축 및 운영 품질 향상`). 실측치가 있으면 수치로 대체(R6)
- 셀 안에서 현상·실행을 구분 없이 이어 붙이지 말 것 — 항목 경계는 줄바꿈(`<br>`)으로 표시

### 8.3 문서 전체 구성 패턴

```
Summary(성과·현황·핵심방향·토론)
  → 1. 성과(정량 표) → 2. 현황(조직별 표) → 3. 계획(3단 골격 반복) → 4. 토론·의사결정(비교표 + 끝열 의견)
```

신규 과제·구축 계획 보고는 성과 대신 **경과**로 출발하는 변형을 씀:

```
Executive Summary([배경] 현상 → 필요 / [목표] 도달점)
  → 1. 그간의 경과 → 2. 방향성 → 3. AS-IS/TO-BE 표 → 4. 구축 범위 및 향후 계획(단기·향후)
```

- **그간의 경과** 절 골격 = `(기간) 활동 + 산출물 : {출처 링크}` 한 줄 반복. 각 줄 명사형 종결, 실패·한계도 그대로 적어 다음 절 방향성의 근거로 삼음
- **Executive Summary** = `**[배경]** {현상} → **{목적}**을 위하여 {수단}하는 체계가 필요` + `**[목표]** {도달점} 구축` 2불릿. 배경 불릿은 현상과 필요를 `→`로 나누어 씀

- **마지막에서 둘째 = 토론/의사결정, 마지막 = 향후/참고** — 부문보고 불변
- Summary는 **본문의 압축 미러** — 본문 장 제목과 Summary 항목이 1:1 대응
- 토론 장은 **결론 강요 금지** — 선택지·각 부서 의견을 표로 병렬 제시(의사결정은 청중 몫)

### 8.4 어휘·표기 미시 규약

> §2.4(약어 풀이·백틱·볼드)는 그대로 적용. 아래는 임원 보고 추가분.

| 항목 | 규약 |
| --- | --- |
| 라벨 구분자 | **콜론 `:` 이 기본**. 우선순위는 아래 표 참조. 엠대시는 최후 수단 |
| 슬래시 `/` | 이종 병렬 — 제품·시스템명 열거, 선택지, 대안 ("Azure/WhaTap/Datadog", "분석/설계") |
| 가운뎃점 `·` | 동종 병렬 — 같은 범주 항목 나열 ("이벤트·인시던트·로그"). 한 문장에서 `/`와 혼용 금지 |
| 강조 구분 | **볼드** = 키워드·수치·주장 구 / `_이탤릭_` = Pain Point 세부 |
| 임원 존칭 | 본문 인용 시 직책 + '님' (단 "상무님 지시" 표기는 금지 — 미션 룰) |

#### 라벨 구분자 우선순위

| 순위 | 기호 | 쓰는 자리 | 예 |
| --- | --- | --- | --- |
| 1 | 콜론 `:` | 라벨 + 설명 연결의 기본형. 항목·목적·기능 서술 전반 | `**목적:** 담당 서비스 이벤트를 실시간 확인` |
| 2 | 대괄호 `[ ]` | 관점·유형·절 부제 라벨 (R5) | `**[관제·장애 관점]**` |
| 3 | 하이픈 `-` | 용어 정의형 나열의 항목 구분 | `**Metric** - CPU, Memory, TPS 등` |
| 4 | 괄호 `( )` | 짧은 부연·시점·별칭 | `표준 아키텍처(안)`·`(~'26.3Q)` |
| 5 | 엠대시 `—` | 위 넷으로 안 되는 경우만. 표 셀 선두·제목 부제에 한정 | `### Track A — Imply (Lumi AI)` |

> ⚠ **엠대시(—) 빈도 가드** (REF 실측 + 타 부서 원문 대조)
> - **상한 = 1/100줄**. KT IT부문 실제 보고 원문(Biz플랫폼운영센터 AIOps 방향성 2건, '26.7.24)은 **본문 엠대시 0개**, 제목 2곳만 사용. 사내 화법의 기본 구분자는 엠대시가 아니라 콜론
> - 엠대시를 "틀리게" 쓰는 게 아니라 **거의 모든 항목에 반복**하는 빈도가 문제
> - **분산 원칙** — 같은 보충을 한 기호로 통일 말고 위 우선순위대로 분산: ① 라벨 뒤 `:` ② 관점·부제 `[ ]` ③ 짧은 부연 `()` ④ 별개 절 문장 분리(`. 즉 …`)
> - **예외(허용)** — 표 셀 선두 구분자, 섹션 제목 보충(`**제목 — 부제**`)은 REF도 사용. 단 절제
> - **점검** — `grep -o "—" 파일 | wc -l` ÷ 줄수 × 100 ≤ 1 이면 통과

#### 볼드 적용 범위 (R2 상세)

| 형 | 범위 | 예 |
| --- | --- | --- |
| ⓐ 키워드 볼드 | 불릿 첫머리 결론어 1~3어절 | `**분석 자가 수행 전환**: 분석가가 데이터 직접 처리` |
| ⓑ 주장 구 볼드 | 문장 중간, 그 문장이 주장하는 구(句) 전체 | `**서비스별 맞춤형 관제 정보 제공**하여 운영자가 먼저 접속하는 업무 Portal 구축` |

- **선택 기준** — 항목이 라벨 구조면 ⓐ, 서술 문장 안에 주장이 박혀 있으면 ⓑ
- **볼드 경계는 어절에서 끊음** — 조사·어미는 볼드 밖(`**…정보 제공**하여`, `**…사전 감지**하고`). `**…정보 제공하여**`처럼 어미까지 감싸지 않음
- 한 불릿에 볼드는 한 덩어리만. 두 곳 이상 볼드면 강조가 무효화됨

### 8.5 적용 체크리스트 (임원 보고 원고 점검)

> 원고를 문단 단위로 훑으며 점검. 위반 시 §8.6으로 교정.

- ☐ **명사형 종결** — `~합니다/~한다/~것이다` 0건 (R1)
- ☐ **볼드 두괄** — 핵심 불릿이 `**키워드**`로 시작하거나 주장 구 전체 볼드, 어미는 볼드 밖 (R2·§8.4)
- ☐ **개조식** — 한 불릿에 절 3개 이상 만연체 0건 (R3)
- ☐ **정량 근거** — 효과·현황에 수치 동반·볼드 (R6). "크게·대폭" 단독 0건, 수치 없으면 지표명이라도 명시
- ☐ **3단 골격** — 방안마다 Pain Point→개선→기대효과 성립. 방안 3개 이상이면 AS-IS/TO-BE 4열 표 (§8.2)
- ☐ **표 끝열 판단** — 비교표 마지막 열에 의견/방향 (R8)
- ☐ **제목** — 주장 있는 절만 행위 서술형, 수식 분사(뒷받침하는·기여하는 등) 0건, 다단 번호 0건 (R11)
- ☐ **구분자** — 라벨은 콜론 기본, 엠대시 ≤1/100줄, `·`와 `/` 한 문장 혼용 0건 (§8.4)
- ☐ **표기 규약** — 날짜 `'26. 6월`, 기한 `(~'26.3Q)`, 약어 첫 등장 풀이 (R9)
- ☐ **주체 특정** — `우리`·`저희`·`당사` 0건, 조직명으로 지시. 타 팀은 **전체 명칭**, 타 조직의 진척·역량 평가 0건 (core.md §2.9)
- ☐ **완료형 과장** — 아직 수행하지 않은 일을 완료형으로 쓰지 않음. 검증 수치에 전제(PoC 기준) 명시 (core.md §2.9.4)
- ☐ **구조** — 마지막에서 둘째 = 논의·의사결정, Summary가 본문 미러 (§8.3)

  ✓ **분석 자가 수행 전환**: 분석가가 데이터 직접 처리, 전문가 대기 제거.

  ✓ **[배경]** 관제 도구 분산으로 분석 환경 부재 → 장애 대응 지연

패턴 C — 평면 나열 표 → 끝열에 판단 추가
  ✗ | 도구 | 특징 |        ✓ | 도구 | 특징 | 검토 의견/적용 방향 |   (R8)

패턴 D — 결론 없는 도입 문단 → 두괄 `>` 선언
  ✗ 최근 AI 기술이 발전하면서 여러 변화가 일어나고 있습니다. (장황한 배경)

```

### 8.7 임원 보고 어휘·표현 사전

> 실측 + 교정 도출. 새 원고 집필·교정 시 어휘 표준. §2.1 명사형 종결의 임원보고 어휘 보강.

**명사형 종결 어휘** (문장 끝 — `~합니다/~한다` 금지). 서술 대상에 따라 4군으로 나눠 씀:

| 군 | 쓰는 자리 | 어휘 |
| --- | --- | --- |
| 성과·추진 | 계획·성과 서술 | `수립`·`확보`·`정착`·`정리`·`구축`·`도출`·`추진`·`확산`·`전환`·`필요`·`의존`·`좌우`·`부재`·`정체`·`확대`·`단축`·`감소`·`향상`·`개선`·`수행`·`완결`·`축적`·`보존`·`진입`·`중심`·`편중` |
| 기능·역할 | Agent·시스템·도구가 하는 일 (표 역할 셀) | `진단`·`제시`·`요약`·`파악`·`점검`·`전파`·`승인`·`분류`·`검증`·`추적`·`연계`·`집계`·`탐지`·`정규화`·`위임`·`등록` |
| 정의문 범주 | 용어·개념 정의의 종결 (표 개념 셀) | 한정어절 + 상위 범주 명사로 닫음 — `~하는 기준`·`~ 개념`·`~ 데이터`·`~ 레이어`·`~ 체계`·`~ 활동`·`~ 형태의 Agent` |
| 요구·판단 | 비교표 끝열, 검토 의견 (R8) | `~ 필요`·`~ 요구`·`~ 보완 필요`·`~ 확인 필요`·`~ 부담`·`~ 한계`·`~ 가능` |

- 정의문 예 — `Write Once Read Many의 약자로, 한 번 기록한 로그를 보존하는 불변 감사 로그 개념` / `AI 분석 결과의 신뢰도 점수에 따라 자동 실행·승인·보류 여부를 결정하는 기준`
- 기능 서술 예 — `장애 사례를 상관 분석해 원인 후보와 근거를 제시` / `서비스·CI·담당자 기준으로 이벤트를 정규화·요약`

- ⚠ **가짜 명사형 함정** — 명사처럼 보여도 미완결·서술성이라 금지: 방향성 동사형(`~우선`·`출발`·`시작`) → 완결 명사구로 / 형용사 어근(`용이`·`유리`·`가능`) 단독 종결 → 명사구로(`학습 용이` → `학습시키기 쉬운 구조`). 판별: 끝 단어에 "~하다/~되다"를 붙여 형용사·동사가 되면 가짜 명사형

**근거 분류 괄호 라벨** (KT IT부문 고유 화법): `(환경)` 기술·시장 / `(비용)` 비용·효율 / `(트랜드)` 업계 동향 / `(역할)(인력)` 조직·인력 / `(배경)(방향)(성과)(확산)` Summary 머리 / `(비고)` 부연 / `[범주명]` 범주 분류

**연결·흐름 기호** (문장으로 풀지 말 것 — R7): `→` 단계·인과 / `==>` 도식·블록 하단 결론 / `▶` 전환(As-Is ▶ To-Be) / `✕` 요소 결합(범용 도구 ✕ 조직 역량) / `·` 병렬 압축 / `즉` 핵심 재진술

**강조·구조 마커**: `■ 핵심 — …` 장 두괄 1줄 / `※` 전략적 부연 / `√` Summary 체크 / `先·現` 한자 1자 강조(先검증·現 적용)

**상태 칩** (인라인 진행 분류): `✅ 완료` · `🟡 진행 중` · `📅 ~'26. 3Q 목표` · `🔄 진행` · `Quick Win`

**정착된 구문 템플릿** (그대로 재사용):
```

```

- **표기 일관** — 같은 개념은 한 단어로 고정("스스로 수행"을 "셀프서비스/self-service"와 혼용 금지)
- **임원 보고 회피어** — `셀프서비스`(식당 연상) → `스스로 수행` / `통념` → `기존 인식` / `국면` → `상황`·`단계`·`구조`
- **주체 대명사 배제** (core.md §2.9.1) — `우리`·`우리 팀`·`저희`·`당사`·`자사` → 조직명·제품명. 임원 보고는 작성 조직 밖으로 전달되므로 **제3자가 주체를 특정할 수 있어야** 함. Summary 라벨·표 열 이름처럼 짧은 자리가 특히 위험(본문보다 먼저 읽힘) — `(우리 Agent)` → `(AO Agent)`, `AO Agent (우리)` → `AO Agent (서비스플랫폼담당)`. 제3자 회사를 가리킬 때의 `자사`도 누구인지 흐려지므로 `자체` 또는 사명으로 교체(`자사 텔레메트리` → `자체 텔레메트리`)
- **타 조직 서술 한계** (core.md §2.9.3) — 역할·협의 사실까지만. 그 조직의 진척 단계·성숙도 평가는 쓰지 않음(`양측 모두 기획 단계` 류). 거리 두는 지칭(`상대`·`상대 측`)도 조직명으로
- **수사·마케팅 카피 배제** — 슬로건·수사적 대구(`자산이 아니라 체계`·`게임체인저`·`혁신적 도약`·`새로운 패러다임`)는 임원 보고에 부적합 → 사실·구조로 환원(`3단계 등록·배포·통합 체계`). IT 조직다운 담백한 기술 팩트 우선
- **저수준 명령어·도구 축약 배제** — `npx로 설치`·`컨플에 올림`·`깃에 푸시` 류 저수준 표기는 기능 수준으로 추상화 + 기술명 괄호 보조(`배포 패키지(ACP)로 설치`). 판단 기준: 릴리스 노트·기술 블로그에 그대로 실어도 되는 표현인가
- **약어 풀이** — 외부·기술 약어(SDD·AI-DLC·EDA·RFP·GUI)는 첫 등장 1회 풀이 / 사내 통용어(KTSSP 등)는 생략
