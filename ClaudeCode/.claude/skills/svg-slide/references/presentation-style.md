## 1. 그리기 전 — 내용·레이아웃 설계와 컨펌

> 색·폰트·비율보다 **앞선 0순위 단계**. 발표 도식 실패의 대부분은 색·폰트가 아니라 **"무엇을, 어떤 구조로 보여줄지"를 정하지 않고 그리기 시작한 데서** 온다. SVG를 바로 그리지 말고, 아래를 **텍스트로 먼저 설계**한 뒤 **사용자 확정**을 받고 작성에 들어간다.

### 1.1 설계 4단계 (그리기 전, 텍스트로)

| 단계 | 내용 | 핵심 |
| --- | --- | --- |
| ① 메시지 한 줄 | 이 도식이 청중에게 남길 **단 하나의 문장** | 한 장 한 메시지(§2.2)의 출발점 |
| ② 정보 인벤토리 | 그 메시지를 받치는 데 **꼭 필요한 정보 블록을 빠짐없이** 나열 | **여기서 줄이지 않는다** — 필요한 걸 다 적는다 |
| ③ 구조·관계 규정 | 블록 간 관계(흐름·계층·순환·구성비·비교)를 식별 | §2 관계→유형 매핑으로 연결 |
| ④ 레이아웃·시선 동선 | 블록을 **청중 눈이 따라갈 순서**(좌→우·상→하·중심→방사)로 배치 스케치 | 박스/텍스트 묶음의 대략 위치·그룹핑·여백 |

- **②가 핵심** — "정보를 줄이는 것"이 목적이 아니다. 메시지를 성립시키는 정보는 **빠짐없이 담는 것**이 우선. 줄이기는 마지막 수단(§1.3)
- **④는 ASCII 스케치로 충분** — 정밀 좌표 전에, 어느 블록이 어디에 어떻게 묶이는지 거친 배치도면 됨

### 1.2 컨펌 게이트 (확정 후 작성)

> **SVG 코드는 사용자 확정 뒤에만 생성.** 설계를 건너뛰고 바로 그리면, 다 그린 뒤 "담을 내용·배치가 틀렸다"가 드러나 재작업 비용이 가장 크다.

1. §1.1의 4단계를 **텍스트 초안**(필요 시 ASCII 배치 스케치 포함)으로 정리해 **사용자에게 제시**
2. 사용자가 **담을 내용과 배치를 확정**한 뒤 SVG 작성 시작 — **확정 전 SVG 코드 생성 금지**
3. **예외** — 사용자가 "설계 생략하고 바로 그려"라고 명시했거나, 이미 확정된 기존 도식의 소소한 수정(색·문구·좌표 미세 조정)일 때

### 1.3 정보는 줄이기 전에 다시 설계 (§6.2와 연결)

"정보 과밀"은 대개 **정보가 많아서가 아니라 배치 설계가 없어서** 생긴다. 핵심 정보를 함부로 빼지 말고, 아래 순서로 **구조로 먼저 해결**한다.

```
① 배치 재설계   — 그룹핑·계층화·여백 재분배로 공간을 다시 짠다
② 통합          — 중복·부제·역할을 합쳐 블록 수를 줄인다 (정보 손실 없음)
③ 슬라이드 분할 — 한 장 두 메시지면 두 장으로 나눈다 (§2.2)
④ 항목 제거     — 정말 최후에만. 핵심 정보는 끝까지 보존
```

- **빼기는 4번째 카드** — ①~③을 다 시도해도 안 들어갈 때만 ④. 메시지를 성립시키는 정보는 줄이지 않는다
- 글자 크기를 15px 미만으로 낮춰 욱여넣는 것(§6.2)은 ①~④ 어느 것도 아님 — 가독성만 깎는 회피책

## 2. 도식 유형 선택

> §1 설계 다음, 색·비율보다 **먼저** 결정. "무엇을 칠하느냐"가 아니라 "무엇을 그리느냐" — 강조하려는 **관계**가 유형을 정함.

### 2.1 관계 → 유형 매핑

| 보여줄 관계 | 권장 유형 | 구성 요소 |
| --- | --- | --- |
| 순서·흐름·단계 | 박스 + 화살표 (플로우·블록) | `rect` + `marker` 화살표 |
| 계층·소속 | 트리 (조직도) | `rect` + 분기 연결선 |
| 순환·반복 루프 | 원형 배치 + 곡선 화살표 | `circle`/`rect` + `path` arc |
| 시스템 계층·레이어 | 레이어드 띠 | 가로 띠 `rect` 중첩 |
| 구성비·점유율 (≤5항목) | 도넛·파이 | `path` arc (outer+inner) |
| 양·규모 비교 | 막대 / 버블 | `rect` 길이 / `circle` 반지름 |
| 집합·교집합 | 벤 다이어그램 | `circle` + `fill-opacity` |
| 항목 병렬 나열 | 카드 그리드 | `rect` 그리드 |
| 비교·평가 (2축) | 표 / 2×2 매트릭스 | `rect` 격자 |

### 2.2 유형 선택 원칙

- **박스형이 기본** — 순서·구성·시스템 도식 대부분은 박스 + 화살표로 충분. 원형·차트는 그 형태가 메시지에 꼭 맞을 때만
- **원형은 한정 용도** — 순환(루프)·집합(벤)·구성비(도넛)일 때만 사용. 단순 노드를 원으로 바꾸는 장식적 사용 지양
- **도넛·파이는 5항목 이하** — 6개 이상이거나 값 차이가 근소한 비교는 막대가 정확
- **화살표는 흐름 있을 때만** — 방향·인과·순서를 나타낼 때. 장식용 화살표 금지
- **한 장 한 메시지** — 한 도식에 유형 1~2개. 여러 관계를 한 장에 욱여넣지 말고 슬라이드를 분리
- **구체 SVG 템플릿** — 위 유형별 시작 골격은 `pattern-library.md`(관계·의도 → 패턴 선택 매트릭스 + 18종 스니펫)에서 복사해 쓴다. 시각 인덱스는 `../assets/pattern-gallery.html`

## 3. 캔버스·비율

### 3.1 16:9 고정

발표 슬라이드(PowerPoint·Keynote·Google Slides)의 기본값이자 사실상 단일 표준이 16:9 — 빔프로젝터·회의실 모니터·노트북 화면 대부분이 와이드 비율이라 그에 맞춤.

| 용도 | viewBox | 비고 |
| --- | --- | --- |
| **기본** | `0 0 1280 720` | 720p. 발표 도식 표준 |
| 고밀도 | `0 0 1920 1080` | 1080p. 요소 많거나 캡처 후 확대 쓸 때 |

- 두 크기 모두 비율은 동일 16:9 — 좌표 스케일만 1.5배 차이
- `<svg>` 태그에 `viewBox`와 함께 `width`·`height`를 같은 비율로 명기. 셋이 비율 불일치 시 렌더 왜곡

### 3.2 풀블리드 vs 삽입 figure

- **풀블리드**(슬라이드 1장 = 도식 1개) → 16:9 정확히 맞춰 슬라이드를 꽉 채움
- **삽입 figure**(슬라이드 본문 안 그림) → 16:9가 필수는 아니나, 여러 도식의 **비율을 한 종류로 통일**하면 슬라이드 레이아웃 일관. 통일 기준 비율은 16:9 권장

### 3.3 배경 사각형 명시

투명 배경은 슬라이드 테마색이 비쳐 가독성 저해. 캔버스 전체를 덮는 흰 사각형을 **첫 요소로** 배치.

```
<rect x="0" y="0" width="1280" height="720" fill="#ffffff"/>
```

### 3.4 공간 활용·여백 균형

16:9 비율은 고정이므로, **콘텐츠가 캔버스를 균형 있게 채워야** 발표 화면이 비지 않음.

- **의도된 바깥 마진만 허용** — 상하좌우 ~40~48px 마진은 정상. 그 외에 **한쪽(특히 하단)에 쏠린 큰 빈 공간 금지**
- **판정 기준** — 마지막 요소 아래나 한쪽 가장자리에 **100px 이상** 빈 영역이 몰리면 재배치 신호
- **안 차면 콘텐츠를 펼침** — 정보가 적어 캔버스가 비면 블록 높이·요소 간격·폰트(§6.2 상한 내)를 키워 채움. **16:9를 줄이지 말고 콘텐츠를 늘림**
- **§6.2 정보 과밀 가드와 짝** — 과밀(폰트 15px 미만으로 줄임)도, 과소(하단 여백 쏠림)도 둘 다 불균형. 목표는 **본문 15~16px로 캔버스가 적절히 차는 상태**

### 3.5 중첩 박스 경계·내부 패딩

패널(부모 박스) 안에 자식 박스를 넣을 때, **자식의 테두리가 부모 테두리와 겹치면 안 됨** — 두 stroke가 한 줄로 포개져 발표 화면에서 선이 두꺼워지거나 어긋나 보임.

- **내부 패딩 확보** — 자식 박스는 부모 안쪽으로 **상하좌우 최소 16~24px** 띄움. `자식.x + 자식.width ≤ 부모.x + 부모.width − 패딩` (우측), 좌·상·하도 동일하게 성립해야 함
- **좌우 패딩 대칭** — 한 행에 자식 박스를 여러 개 배치할 때 **좌측 패딩과 우측 패딩을 같게**. 흔한 실수 = 좌측 박스 폭과 우측 박스 폭을 다르게 잡아(예 556 vs 580) **우측만 패딩 0**이 되어 부모 경계에 들러붙음. 박스 폭을 통일하거나 마지막 박스 폭을 줄여 우측 패딩을 확보
- **예외 = 헤더 띠** — 패널 상단을 덮는 헤더 띠(같은 박스의 머리 부분)는 부모와 좌우 경계가 **일치해도 정상**(같은 색·같은 도형의 의도된 구성). 경계 겹침 금지는 **다른 색·다른 박스**의 테두리가 포개지는 경우에 적용
- **점검법** — 각 자식 `rect`의 `x+width`(와 `y+height`)를 부모 `rect`의 `x+width`(와 `y+height`)에서 빼 **양쪽 모두 패딩 이상 남는지** 좌표로 계산. QuickLook 썸네일은 16:9를 정사각으로 **우측 크롭**하므로, 우측 경계 확인 시 `viewBox`를 정사각(`0 0 1280 1280`)으로 임시 확장해 렌더하면 가로 전체가 잘리지 않고 보임

### 3.6 타이틀 영역 — 액센트 바

슬라이드 제목을 빈 좌상단에 텍스트만 띄우면 발표 화면에서 시작점이 흐릿함. **제목 왼쪽에 짧은 블루 세로 바**(accent bar)를 둬 시각적 앵커를 주고, 제목·서브타이틀을 바 오른쪽으로 정렬한다.

- **규격** — 제목 묶음 높이에 맞춘 가는 세로 막대. 표준값:

  ```svg
  <rect x="48" y="32" width="6" height="44" rx="3" fill="#4D73BF"/>
  <text x="70" y="56" font-size="27" font-weight="700" fill="#1a1a1a">도식 제목</text>
  <text x="70" y="83" font-size="15" fill="#808890">서브타이틀·한 줄 설명</text>
  ```

- **위치·정렬** — 바는 좌측 마진 `x=48`에서 시작(폭 6px). 제목·서브는 바 우측(54)에서 **약 16px 띄워** `x≈70`에 좌측 정렬. 바와 텍스트의 좌측 라인이 한 세트로 보이게 한다
- **높이** — 바 높이(44)는 **제목 + 서브타이틀 2줄 묶음**을 감싸는 길이. 제목만 있고 서브가 없으면 28~32로 줄여 제목 한 줄에 맞춤
- **색** — 기본 블루 `#4D73BF`(박스 stroke 계열과 동일). 도식 주조색이 보라면 `#6B5FCB` 등으로 맞춰도 무방하나, **한 슬라이드 안에서는 한 색**
- **적용 범위** — 모든 발표용 SVG의 최상단 제목에 기본 적용. 삽입 figure(본문 속 작은 그림)는 생략 가능

## 4. 색상 규칙

### 4.1 하드코딩 원칙 (CSS 변수 금지)

- 모든 색은 **16진수 하드코딩**. `var(--color-text)` 같은 CSS 변수 **사용 금지** — 발표 도구·뷰어가 CSS 변수를 해석 못 해 색이 빠짐
- 배경색 `#ffffff` 고정
- 텍스트 기본 `#1a1a1a`(거의 검정) / 보조 `#333`

### 4.2 박스 스타일

- **파스텔 fill + 어두운 stroke** 조합. 채도 낮은 면 + 진한 테두리로 도형 경계 분명히
- 모서리는 `rx`로 라운딩(8~12 권장) — 발표 도식의 부드러운 인상

### 4.3 표준 팔레트 (계열별 fill·stroke·text 페어)

> 같은 계열 안에서 fill(밝음)·stroke(중간)·text(어두움)를 묶어 씀. 새 색이 필요하면 이 페어 규칙(§4)대로 직접 구성.

| 계열 | fill (면) | stroke (테두리) | text (글자) | 용도 |
| --- | --- | --- | --- | --- |
| 블루 | `#E8F0FE` | `#4D73BF` | `#1a1a1a` | 기본 강조·핵심 박스 |
| 보라 | `#EEEDFE` | `#6B5FCB` | `#26215C` | 보조 강조 |
| 그레이 | `#F3F4F6` | `#A6ADB8` | `#808890` | 중립·배경 패널 |
| 레드 | `#FBEEEE` | `#BF6666` | `#8A3A3A` | 경고·갭·문제점 |

## 5. 명도 페어링 (가독성)

발표는 멀리서·짧게 봄 → 명도 대비가 가독성을 좌우. 색 조합 시 아래 원칙 절대 준수.

- **라이트·파스텔 배경 → 반드시 다크 텍스트**
  - 예: `fill="#EEEDFE"`(연보라) 박스 → 텍스트 `fill="#26215C"`(진보라)
- **밝은 파스텔 배경에 흰색(`#fff`) 텍스트 절대 금지** — 대비 부족으로 글자 안 보임
- **컬러 페어링 원칙**: 같은 계열 색상 중 **가장 밝은 shade → fill**, **가장 어두운 shade → 텍스트**. 중간 shade는 stroke
- 어두운 배경 박스를 쓸 때만 흰 텍스트 허용 — 단 발표 도식 기본은 라이트 배경

## 6. 폰트

### 6.1 폰트 스택 (한글 fallback 필수)

발표 자료는 한글 본문이 기본 → 한글 폰트가 빠진 스택은 한글이 시스템 기본 글꼴로 떨어져 인상 저해. 영문 우선 폰트 뒤에 **한글 폰트를 명시**.

```
font-family="'Pretendard','Apple SD Gothic Neo','Malgun Gothic',
             -apple-system,BlinkMacSystemFont,'Segoe UI',Helvetica,Arial,sans-serif"
```

> Confluence 인라인 다이어그램용 메모리 스택은 `'Anthropic Sans',-apple-system,...`로 **한글 폰트가 없음**. 발표용 한글 도식엔 위 Pretendard 우선 스택 사용. 영문 전용 도식이면 메모리 스택도 무방.

### 6.2 폰트 크기 (발표용 스케일 — 1280×720 기준)

발표 슬라이드는 멀리서 봄 → Confluence 인라인 기준(타이틀 14·본문 12px)보다 **크게**. 1280×720 캔버스 기준 권장값:

| 요소 | 크기(px) | weight | 비고 |
| --- | --- | --- | --- |
| 슬라이드 타이틀 | 26~28 | 700 | 도식 최상단 1줄 |
| 서브타이틀 | 14~15 | 400 | 타이틀 아래 설명 |
| 섹션 헤더(중간 소제목) | 20~22 | 700 | 장표 중간 구획 제목(①·②·③ 등) |
| 본문 | 15~16 | 400 | 일반 텍스트 |
| 칩·라벨 | 12.5~13 | 700 | 박스 안 짧은 라벨 |
| 캡션·주석 | 12~13 | 400 | 부연·출처 |

- 1920×1080 캔버스면 위 값에 **×1.5**
- weight는 강조(타이틀·헤더·라벨) 700 / 본문 400 두 단계가 기본

> ⚠ **정보 과밀 가드** — 핵심 본문을 **15px 미만으로 줄여야** 박스/슬라이드에 들어가면, 폰트가 아니라 **정보 배치가 안 됐다**는 신호. 글자를 줄이지 말 것. 그리고 **정보를 빼기 전에** §1.3 순서를 먼저 밟는다 — ①배치 재설계 ②통합 ③슬라이드 분할, **항목 제거는 최후**. 핵심 정보를 보존한 채 **구조로 해결**하는 게 우선. 칩·라벨 크기(12.5~13)를 본문에 쓰면 발표 가독성 저하.

### 6.3 박스 내부 폰트 위계 (표준)

박스(패널) 안 텍스트는 **제목 1줄 + 개조식 본문 N줄** 구조가 기본. 박스마다 제목·본문 크기를 달리하면 위계가 흔들려 슬라이드가 산만해진다 → 모든 박스가 아래 2단계를 **공유**한다.

| 역할 | 크기(px) | weight | 예 |
| --- | --- | --- | --- |
| **박스 제목** | 20~22 | 700 | `INPUT` · `범위 정의` · 패널명 |
| **도식 노드·칩** | 16~18 | 700 | `agent · 두뇌` · `02-scope.md` 같은 흐름 노드 |
| **개조식 본문** | 16 | 400 | `• KTDS 견적서` · 행위 설명 한 줄 |
| (보조 식별자) | 12.5~13 | 400/700 | `eos-scope · 02` 같은 부연 라벨만 예외 |

- **전 박스 통일** — INPUT·AGENT·SKILL·OUTPUT 등 종류가 달라도 제목은 전부 20~22, 개조식 본문은 전부 16. 한 박스만 키우거나 줄이지 않는다
- **칩이라고 다 작은 게 아니다** — 미니 도식의 칩이 「무엇 → 무엇」 흐름의 **핵심 노드**(그 자체가 메시지)면 본문급 16~18로 키운다. 판별: 그 칩을 지워 도식이 안 읽히면 **노드**(키움), 없어도 뜻이 통하면 **보조 라벨**(작게). 예 — `02-scope.md`·`agent · 두뇌`는 노드(16~18), 노드 옆 `eos-scope · 02`는 부연(12.5~13)
- **보조 식별자만 예외** — 코드명·일련번호처럼 **내용이 아닌 부연 라벨**만 12.5~13 허용. 개조식 '내용'이나 도식 노드를 이 크기로 쓰면 안 됨(§6.2 과밀 가드)
- **공간이 부족하면 정보를 줄임** — 본문·노드를 14·15로 낮춰야 들어가는 박스는 항목 수를 줄이거나 박스/칩을 키운다(폰트를 낮추지 않는다)
- **기준 사례** — INPUT 박스(제목 `📥 INPUT` 21/700 + 개조식 `• …` 16/400)와 MECHANISM 카드의 도식 노드(`agent · 두뇌` 등 18/700)가 가독성 기준점. 새 박스는 이 위계에 맞춤

## 7. 렌더링 방식

- **기본**: SVG 그대로 사용(`show_widget`). 벡터라 확대해도 선명하고 발표 도구에 그대로 삽입 가능
- **PNG 출력**: 사용자가 **PNG 파일 출력을 명시적으로 요청한 경우에만** Python 스크립트로 변환. 기본은 SVG 유지

## 8. 작성 후 점검

> 전제 — §1 설계·컨펌(메시지·정보 인벤토리·배치)을 **사용자에게 확정받은 뒤** 그렸는지 먼저 확인. 그 위에서 아래 8축 0건 확인 후 마감.

- ☐ **비율** — `viewBox`가 16:9(1280×720 또는 1920×1080), `width`·`height`도 같은 비율
- ☐ **CSS 변수** — `var(--` 0건, 모든 색 16진수 하드코딩
- ☐ **흰 글자** — 밝은 파스텔 배경 위 `#fff` 텍스트 0건. 라이트 배경엔 다크 텍스트만
- ☐ **한글 렌더** — `font-family`에 한글 폰트(`Pretendard` 등) 포함
- ☐ **본문 크기** — 핵심 본문 **15px 이상**. 중간 소제목·박스 제목 20~22·개조식 본문 16 위계 고정(§6.3). 미달이면 정보 과밀 → 빼기 전 재설계·통합·분할(§1.3·§6.2 가드)
- ☐ **여백 균형** — 한쪽(특히 하단) **100px+ 빈 공간 쏠림 없음**. 콘텐츠가 캔버스를 균형 있게 채움(§3.4)
- ☐ **박스 경계 겹침** — 패널 안 자식 박스의 stroke가 부모 경계와 **포개진 곳 0건**. `자식.x+width ≤ 부모.x+width − 패딩`(좌우 대칭)을 좌표로 검산(§3.5)
- ☐ **타이틀 액센트 바** — 제목 앞 블루 세로 바(6×44·rx3) 존재, 제목·서브가 바 우측(`x≈70`)에 정렬(§3.6)
